# Shell guard: write jail and role policy

Part of docs/guard.md (the index); the sections below are moved there unchanged.

## Write jail

`kitlib/guard/jail.py` (roots and verdicts), `kitlib/guard/rules_edit.py` `write_jail` and `kitlib/guard/rules.py` `git_jail` (rule `write-jail`). It holds agent sessions only, as `kill-by-name` does (docs/guard-fallback.md "Session mark"): subagents and the marks in `guard_agent_marks` (default `coordinator`, `deep-worker`, `consultant` and `pm`). The owner's unmarked session on Claude and other marks (`plain`, another agent's name) are not held; on Codex every chat is held (docs/guard-fallback.md "Session mark"). Tests: tests/guard/test_jail.py.

- **Write roots** of a session running in `<cwd>` (the hook payload's `cwd`):
  - **its checkout:** the git top of `<cwd>`. In a linked worktree that worktree alone, so the main checkout is outside. A session running in a main checkout gets the whole checkout (the `main-checkout` rule still holds a subagent there). Outside git, `<cwd>` itself, unless it is a drive root or the home folder. No own root at all when that root touches a machine config folder (`jail.own_root`, `jail.touches_config`: on, over or inside either home one, or on or inside the PM repository's `<pointer>/.pm-kit`; the PM repository's checkout, which only holds that folder, stays a root, and `machine-config` refuses the writes inside the folder): a session run in `<config-dir>` would otherwise write the machine config, its guard settings and `ledger_path` among them (tests/guard/test_jail_home_config.py).
  - **its repository's worktrees:** every linked worktree of the repository `<cwd>` belongs to that lies under its main checkout (`jail.sibling`), so a session in one worktree reaches the others, as a session in the main checkout does through its checkout root. A worktree a subagent makes with `tools/new_worktree.py` from a linked worktree is therefore writable. Not the main checkout itself, not the PM data worktree (the guard places it as a main checkout; while it cannot tell which worktree that is, `Ctx.pm_data_error`, no worktree is reached this way), not a worktree that touches a machine config folder (as above), not another repository's worktree or a worktree outside the main checkout, and not a path a link carries out of its worktree (the target is compared after `realpath`). It is not a listed root: the refusal names the roots above and points at `<cwd>`'s own checkout.
  - **temp:** the system temp folder (`Ctx.tempdir`, and `TMP` when it differs), which holds Claude Code's session scratch folders; and the folder the `AGENT_TEMP` environment variable names, when it is set.
  - **data roots:** `.kit.json` `guard.data_roots` (docs/kit-json.md), read from the main checkout only, as every `.kit.json` key is. Each entry is `{path, mode, why}`: `open` (any write), `add-only` (new files only: a write, move or delete of a file that exists is denied; a copy, move or link into the existing folder is judged as `<folder>/<each source's name>`, `rules.copy_into`, when its options are only these: cp `-r -R -a -p -v -n -t`, `--recursive`, `--archive`, `--verbose`, `--no-clobber`, `--target-directory`; mv `-v -n -t` and the same long ones; ln `-s -v -t`, `--symbolic`, `--verbose`, `--target-directory`; install `-v -m -t`, `--verbose`, `--mode`, `--target-directory`. Any other option, or two target directories, is judged as the folder itself, so it is denied. cmd's copy is judged by name only for a source that is an existing file) or `read-only` (no write). A mode holds wherever the folder nests: a read-only folder inside the checkout or temp stays read-only. The kit names no folder.
  - **mark roots:** the machine config's `guard_mark_roots` (docs/kit-json.md), `{<mark>: [{path, mode, why}]}`, adds roots for the main sessions of one launcher mark, compared without case (`jail.mark_roots`, `rules.session_mark`). `path` is absolute or `~/<path>`, read from the home folder; the modes are the data roots' modes. A subagent gets none, not even one of a marked session. A root that touches a machine config folder is dropped ("No root on a machine config folder", below), so no session is given its own guard settings, nor can create the new config file that would replace an old-only one. The schema refuses a reserved mark (`owner`, `subagent`), a relative path and an unknown mode, and a config the strict reader refuses gives no mark roots (docs/guard-core.md "State": the tolerant read keeps no map). The PM's roots (its memory folder, say, or a repository's main checkout whose red landing merges it resets) are set here by the owner: the jailed PM cannot write the machine config. The intended use is folders like those, other repositories' main checkouts above all. A mark root should not cover the account folder `~/.claude` (its `settings.json` registers this hook; the live lock tool is under `tools/machine_lock`) or the kit's own checkout (`boot/hook.py`, `kitlib/guard`): a root there lets the session rewrite the guard itself. Only the machine config folders are dropped by the code. The `lock-state` and `kit-json` rules come first ("Order"), so a mark root never opens the machine lock's state or a `.kit.json`.
  - **No root on a machine config folder:** a root of any kind (checkout, temp, data, mark) that is the home machine config folder (`jail.home_config_dirs`), holds it or lies inside it is dropped unless it is read-only (`jail.roots`, `jail.touches_config`): a data root, `TMP`, `AGENT_TEMP` or the system temp folder at the home folder or above would otherwise let the session write the machine config. So is one that is the PM repository's `<pointer>/.pm-kit` or lies inside it; one that only holds it (the PM repository's checkout, a mark root on it) is kept, and `machine-config` holds the folder (docs/guard-owner.md "Owner machine setup"; tests/guard/test_machine_config.py `PointerFolder`). A read-only root only denies, so it is kept (tests/guard/test_jail_home_config.py). On Linux the user's PM-repo pointer file, `<profile>/.config/pm-kit/pointer` (`jail.user_pointer_file`: `kitlib.platform.linux.paths.pointer_files`, the profile folder from the password database, never `$HOME`), is held the same way: a root that is it or holds it is dropped, so a file tool or shell write to it is a `write-jail` refusal wherever the session runs and no agent can point the kit at another PM repository (tests/guard/test_linux_pointer.py). Windows keeps the pointer in `HKLM`, and `/etc/pm-kit/pointer` is root's: only an administrator writes either, so the guard names neither.
- **Outer bound (rule `dev-drive`):** while the machine config sets `dev_drive` (docs/kit-json.md "Machine config keys") to an absolute path of an existing folder, read the guard's tolerant way (`Ctx.user`, `jail.dev_root`), a jailed session writes only on the Dev Drive, whatever root would otherwise let it write (`rules.dev_drive_bound`, `jail.on_drive`). The bound is checked last, after the jail allows a target: a file tool's target, a shell write target, a git write's checkout, the folder `worktree add` or `clone` makes, and the lander's landing verbs; git reads are not bounded. A target or root compares after `realpath`, so a junction on the drive that points off it is off the drive. A data root (`.kit.json` `guard.data_roots`) or mark root (`guard_mark_roots`) off the drive is dropped while the rule denies (`jail.roots` `dev`): config load does not refuse it, a write into it is refused as `dev-drive`, and every write the jail judges warns, naming the entry, its path and the key to move it in (`rules.jail_view`). A dropped root opens nothing on the drive: when it holds the Dev Drive (a data root `<drive>/` around a `dev_drive` of `<drive>/dev`), a target on the drive is judged by the other roots alone (`rules.in_dropped`). The refusal's `Instead:` writes to a root on the drive (`jail.destination` with `dev`). Temp, `AGENT_TEMP` and the checkout are not dropped: a write there off the drive is refused the same way. A write the guard only guesses at (the folder a program runs in standing for what its code writes, a piped write) is refused under `unplaced` instead, which warns by default (`dev-drive` is in `rules.PLACE_RULES`). With `dev_drive` unset, relative or not an existing folder (the Dev Drive unmounted, a wrong letter), or a config that does not read, the bound is off and every session start says so; the header asks the guard's own question (`jail.dev_root`), so the two always agree (`kitlib/hookrun/header.py` `NO_DEV_DRIVE`). The owner may set `dev-drive` to `warn` or `off` in `guard_rules` (docs/guard-core.md "Rule modes"); under `warn` no root is dropped and each off-drive write warns. Tests: tests/guard/test_jail.py `DevDrive`, tests/hookrun/test_header.py.
- **Paths** compare after `os.path.realpath` and the case fold (`normcase` on Windows), so `..`, symlinks and junctions are resolved: a junction in the worktree that points out of it is outside. On Linux the fold is per mount (`paths.norm`, from `/proc/self/mountinfo`): a case-folding filesystem (vfat, exfat, cifs, hfs and the like) folds, a case-sensitive one (ext4, xfs, btrfs, tmpfs, overlay and the like) does not, and one in doubt (an fstype not listed, or no table) folds for what the guard refuses but not for what it allows: whether a root allows a target compares case-sensitively (`jail.judge`, `Root.strict`), so a case-variant sibling of an allowed root is outside, while a read-only or add-only root, the main checkout and the guarded files match either case.
- **File tools:** Edit, Write, MultiEdit and NotebookEdit, by their target path.
- **Shell writes:** every literal target docs/guard-rules.md "Shell writes" lists. Under bash, `/dev/...` is no file and passes, and on Windows `/tmp/...` stands for the folder `AGENT_TEMP` names, else the system temp folder (Git Bash's mount table is not read). On Linux `/tmp` is itself, a temp root only when it is the system temp folder, `TMP` or `AGENT_TEMP`, and `/c/x` is a path, not drive C.
- **git:** a subcommand that writes is judged by the checkout it runs in (`-C`, a `cd` before it, else `<cwd>`), so `git -C <another repository> commit` is denied and `git -C <a worktree of the same repository> commit` passes. `update-ref`, a push into the repository itself, a `fetch` or `pull` refspec, `symbolic-ref`, `replace`, a `notes` write and the branch, tag, checkout, `worktree add`, `rebase --update-refs`, `remote`, `fast-import` and `filter-branch` forms that write a shared ref are judged from every checkout as well, by `git-shared-ref` (docs/guard-rules.md "Rules"): the refs they write are shared by every worktree. The subcommand is the first word after git's global options, each in `commands_git.GIT_VALUE_OPTS` (`-c`, `--namespace`, `--super-prefix`, `--config-env`, `--exec-path`, `--attr-source`, `--shallow-file`) skipped with the word after it, so `git --attr-source HEAD update-ref -d refs/heads/main` is read as `update-ref`. Reads pass anywhere: `status`, `log`, `diff`, `show` and the other names in `rules.GIT_READS`; `stash list`/`show` (as the first word after `stash`, `rules.stash_reads`), `worktree list`, `remote` (`show`, `get-url`), `reflog`, `notes` and `submodule` without a writing verb; `branch` and `tag` listing; `config` with a read flag (`--get` and the other `rules.CONFIG_READ_OPTS`, `-l`, `--list`) as its own option: before its first word that is not an option and before any `--`, and not as the value of `-f`/`--file`, `-t`/`--type` or another option that takes one (`rules.config_reads`; git stops reading options at the first other word, so `git config a.b --list` sets `a.b` to `--list`, observed with git 2.55); `apply` with `--check`, `--stat`, `--numstat` or `--summary` and no option before `--` but those, `-v`, `-R` and `-p<n>` (`rules.apply_checks`: each turns applying off and only `--apply` turns it on, observed); `patch-id`; `symbolic-ref` with one ref and only `-q`, `--quiet`, `--short`, `--recurse` or `--no-recurse` (`rules.SYMREF_READ_OPTS`: it prints where the ref points; a second name, `-d` or `-m` writes it); `archive` (`rules.archive_outputs`, `--remote` and `--exec` included: only an attacker hides a write there), unless it carries an option the guard does not know or a word that is not literal, or the line may give it a program to run (`rules.archive_filter_set`): a `-c` whose key is not on `rules.ARCHIVE_SAFE_KEY_RE` (`core.quotepath`, `core.autocrlf`, `core.eol`, `tar.umask`, `tar.<format>.remote`; another may name `tar.<format>.command`, a `filter.<driver>.smudge` or `.process`, an attributes file or an `include.path`), any `--config-env`, a word before the subcommand that is not literal, a `commands_env.GIT_ENV_NAMES` variable or a user config folder (`commands_env.HOME_ENV_NAMES`) set on the line, `--exec-path=` or a `PATH` change on the line (`Command.path_env`: they say where git finds a filter's bare program name, as Git for Windows' `filter.lfs.process = git-lfs filter-process`), or a git the text cannot place (below). A change counts when the line sets the name literally (`commands_env.line_env_names`: the spellings of docs/guard-core.md "Git spellings", and cmd's `set` behind the `@` and delimiters (`,` `;` `=`) cmd drops before a command name, as a prefix or as words of their own: `@set PATH=X`, `;set HOME=X`, `@ set GIT_DIR=X`, `commands.cmd_invocation`); cmd's own `path` command, a PowerShell cmdlet that clears or removes an `env:` item, and a name computed at run time are not read (the guard catches honest mistakes, not evasion). git runs a filter in the checkout it reads (observed with git 2.55). Each word is read as bash hands it to git (`\-o` is `-o`, `-\c` is `-c`, `commands.passed`); in PowerShell a word 5.1 may split or drop for a program (a `"` in it, empty, or a blank and a trailing `\`, `rules.ps_native_unsure`, observed) fails closed, as does under cmd a word the C runtime may split apart from cmd (a `"` other than one pair around it, or no valid place in the source to read its quotes from, `rules.cmd_native_unsure`). `worktree add <path>` and `clone <url> <dir>` are also judged by the folder they make, and `archive` by the file its `-o`/`--output` names (also `-o<file>`) wherever it sits before `--` (after it, git reads a pathspec): git's first pass (builtin/archive.c `cmd_archive`) takes no value for the other options, so `--prefix -o README.md` opens README.md (`rules.archive_opened`). The guard also counts, failing closed, the forms that pass does not open (`-o` in a cluster such as `-vo`, a prefix such as `--outp=`). So `git -C <main checkout> archive HEAD | tar -x -C <temp>` passes and `archive -o <main checkout>/a.tar` is denied (tests/guard/test_archive_readonly.py). One exception (`rules.lander_check`): the lander role (agent_type `lander`, or the kit plugin's `<plugin>:lander`, docs/guard-fallback.md "Agent names"; named in the main checkout's `.kit.json` `roles` with `edit_main_checkout: true`, Go-live step 3) may run exactly these commands in a main checkout from its worktree, with `<remote>` and `<main>` the main checkout's `.kit.json` `repo.remote` and `repo.main_branch`:
  - `git fetch <remote>`
  - `git fetch <remote> <main>`
  - `git merge --ff-only <remote>/<main>`

  Each must be alone on its line (`rules.lander_alone`, which reads the event's line again): nothing else, or one literal `cd`, `Set-Location` or `pushd` into that checkout before it, joined by `&&` or `;`. A pipe, a group, a nested shell, `||` or a third command is not alone. git may be spelt `git`, `git.exe` or PowerShell's `& git`, with `-C <main checkout>` or that `cd` before it. Anything else is denied: another option (`--prune`, `--no-ff`, `-s`, `-X`, `--squash`, ...), another ref or refspec (`main:main`, `+main`, `FETCH_HEAD`), a git option before the verb (`-c`, `--config-env`, `--git-dir`, `--work-tree`, `--no-pager`), an environment assignment or wrapper before git (`GIT_DIR=`, `env`), a word that is not literal, any other git write there, a file write there, and every other role. Any main checkout whose own `.kit.json` lets the lander in qualifies, not only the one the lander's session runs in (the PM lands kit branches from its own folder). When a lander's `git fetch` or `git merge` in a main checkout is refused (rule `write-jail`, or `git-main-history` for a merge in a repository that does not set the role), the refusal names the first test that failed, in this order: a `.kit.json` that does not load, `roles.lander.edit_main_checkout` not set (the repository's settings first, since until they allow it every form is refused), not alone, a wrapper or option, the arguments; its `Instead:` is the form to run, or `python -m json.tool "<main>/.kit.json"` when the config is the cause (`rules.lander_refusal`). The lander's own landing command (`land.py`, `gate.py land`) is a python program whose git the guard does not see (docs/guard-fallback.md "Known limits", "write-jail reads the line, not the program"), so it needs no exception. git whose checkout the text cannot place (a variable from docs/guard-core.md "Git spellings" set, `--git-dir`, `--work-tree`, `core.worktree`, `--config-env`, a computed `-C`, whatever the order of `-C`) and that writes is denied for every session the jail holds, the lander included (`rules.git_jail_unknown`): it may be a main checkout, where `symbolic-ref` or `branch -m` would re-point main's HEAD. The refusal names the cause: for a variable or option it says to drop it and run git in the worktree (`rules.git_unplaced`), for a computed `-C` to name the checkout literally. Only a plain read passes (`rules.git_reads` strict): no word that is not literal, except as `rules.strict_dyn_read` allows in bash and PowerShell (any computed word in `rev-parse`, `ls-files`, `cat-file`, `merge-base`, `for-each-ref` and `ls-tree`, which have no option that writes a file; in `log`, `show` and `diff` a computed word only when `rules.dyn_head` reads it as one argument that starts with literal text that is no option, as `"HEAD~$n"` or `"origin/$b"`, or with `--format=` or `--pretty=`, as `--format="$w %h"`, or any computed word after a literal `--end-of-options`, as `diff --end-of-options "$A" "$B"` (not when it is the value of the option before it, as in `log --grep --end-of-options "$B"`: only a first word, one after a non-option word or one after a known no-value option counts); `rev-list` is in this group, as it takes `--output`; `log "$R"`, `log HEAD~$n` unquoted in bash, `"$@"` and a PowerShell array `$f` are denied, and `status`, `describe` and `branch` take no computed word), no PowerShell splat `@a` (`rules.ps_splat`), no `--output` file (abbreviated too) nor `archive -o` (`grep -O` passes: only an attacker hides a write there), and `branch`, `tag` and `config` only with options it names in full, so an abbreviation git expands (`branch --unset-up`) is denied.
- **Not judged:** a target that is not literal under bash or cmd (under PowerShell one is refused from every location, docs/guard-rules.md "Rules"), a command other than git whose directory is unknown, and git whose subcommand the text does not name in a checkout the text places. These meet the rules above them (the `main-checkout` rule fails closed in a main checkout) and the fallback, whose parsed rules include the shell writes and so the jail.
- **Order:** `ledger`, `lock-state`, `hub-secrets`, `owner-delegations`, `machine-config`, `kit-json`, `generated-file` and `main-checkout` are checked first (`rules.edit_target`), so a subagent's edit of a main checkout still reads `main-checkout`.

## Generated files

`kitlib/guard/generated.py` `source(top, rel)`; rule `generated-file` (`rules.generated_file`), checked
with the other edit rules for a file tool's target and each shell write target (docs/content.md "Generated files"). It judges only a checkout
with the kit's layout (`content/roles/` and `tools/render_content.py`, `kitlib.content.oncommit.is_kit`),
the checkout git places the target in, and these paths in it (case folded):

| rendered | its source |
|---|---|
| `hosts/<host>/shell/agents/**` | `content/roles/<role>.md` (the host's agent-name prefix, `kit-` on Codex, dropped) |
| `hosts/<host>/shell/skills/**` | the same file under `content/skills/`; Claude's old copy, a retired folder, too |
| `hosts/<host>/shell/boot/**`, `hosts/<host>/shell/hosts.json` | `boot/`, `hosts.json` |
| `hosts/<host>/shell/plugin.json`, `mcp.json`, `mcp.linux.json`, `hooks/hooks.json`, `hooks/hooks.linux.json`; `.<host>-plugin/plugin.json`, `plugin.linux.json` and `marketplace.json` at the root | `kit.json`, `hosts.json` and `hosts/<host>/adapter/content.py` |

The `agents`, `skills` and `boot` folders themselves count too, so `rm -r` of one is refused. git
that restores, merges or removes these files (`git checkout -- <path>`, `git merge`, `git rm`) has
no write target here (docs/guard-rules.md "Shell writes") and passes this rule: it writes what a commit holds.

The renderer writes these as a process (`python tools/render_content.py --write`, run by hand, by
`tools/commit.py` or by the pre-commit hook), and a python script's own writes are not shell write
targets (docs/guard-rules.md "Shell writes": only `-c` code or a script on stdin counts, and a run PowerShell or Start-Process may hand other words), so the render is never refused.
A repository that is not the kit, a hand-written file in a host's shell (`scripts/`, `mcp/`, the
Claude hub page) and the sources themselves pass. tests/guard/test_generated.py.

## Role policy

`kitlib/guard/rolepolicy.py`, run by `decide` on a call the shared rules allow (a call they refuse is refused as before), the same on every host (ARCHITECTURE.md "Roles"). Lifted from the Codex branch's `guard_adapter` and `kit_adapter`.

- **One switch per repository:** the policy runs only when the main checkout's `.kit.json` sets `guard.role_policy: true` (docs/kit-json.md; default false). With it off no role is held, whatever mode a role file or the `roles` table names, and every call is judged exactly as before. Which repositories turn it on is the owner's call; the kit's own repository has it on.
- **Where a mode comes from:** `roles.<role>.mode` in that `.kit.json` (a key under the role's old or new name counts: `roles.opus-worker` holds `senior-worker`, `config.policy.role_name` and `kitlib.content.names_of`), else the `mode:` line of the role's file, `content/roles/<role>.md` under the kit the guard runs from (`Ctx.kit`; docs/content.md "Role front matter"). `kitlib.content.role_mode` reads the role files once per process and reads an old name as its new one (`opus-worker` as `senior-worker`, `kitlib.content.ALIASES`, the launcher's alias table). A role with neither is not held. When the kit has no `content/roles` (a release built without it) or a role file does not parse, the roles it cannot read are not held and the guard goes on; nothing raises.
- **The kit's modes** (the `mode:` lines of `content/roles/*.md`): `controller` pm, coordinator; `write` weak-worker, worker, strong-worker, senior-worker, deep-worker, topic, docs-writer, helper; `read` analyst, consultant; `test` test-runner; `lander` lander.
- **The role:** a subagent's role (`config.policy.role_name`: `Action.agent_role` when the `roles` table or a role file names it, else `subagent`); a main session's launcher mark when one of them names it; else `main`. Claude Code sends a kit subagent's type as `pm-kit:<role>`; the adapter drops exactly that prefix, so the name the policy sees is the role file's stem (another plugin's prefix names no role). The owner's own session (`rules.is_owner_session`, docs/guard-fallback.md "Session mark") is never held, and the policy reads nothing for it; an unmarked Codex chat is not the owner and is `main`.
- **Modes:** `controller` (pm, coordinator) and `write` (builders) get `role-workdir`, `role-shell` and `role-lock` alone: CLAUDE.md, `.claude/` and the other owner paths stay under the owner-approval rules (`owner.paths`, pre-push), so an owner-approved agent edit of one is still possible. `read` (analyst, consultant) and `test` (test-runner) edit nothing in their checkout and have it read-only to shell; `lander` edits nothing in its checkout (its git landing is `rules.lander_check`'s, as before). All three keep temp and their scratch folder, have the owner paths read-only, and are refused the Blender bridge's `blender_exec` and `blender_render` (`role-blender`).
- **`writes`:** a role file may name repo-relative paths or globs (`writes: [docs/ops/notes.local.md]`; a `*` stays inside one path part) that its `read`, `test` or `lander` role may still edit in its checkout with a file tool, that role alone. No role file uses it now: the consultant's notes file is in agent temp (the launcher's default `--notes-path`, `<agent temp>/<repo>-consultant/notes.md`), which the write jail leaves open. A shell write to such a file stays refused: the jail's roots are folders.
- **Rules:**
  - `role-edit`: a file-tool edit inside the session's checkout by a `read`, `test` or `lander` role, unless its role file's `writes` names the file. An edit outside the checkout (temp, the scratch folder) is the write jail's, as for any session. Its `Instead:` is prose (return the change in the report); with `gate-allow` ("Gate allow") one of the two rules whose alternative is not a command.
  - `write-jail`, with more roots for `read`, `test` and `lander`: every host's owner paths (`hosts.json` profile `owner_paths`: on Claude `CLAUDE.md` and `.claude/`) in the session's checkout are read-only, and for `read` and `test` the checkout itself (not for a file-tool edit of a `writes` file). In a main checkout an owner path that holds the host's worktrees folder (`.claude/` holds `.claude/worktrees`) is left out, so the worktrees under it stay writable. The roots are added to an in-memory view of the `.kit.json`; the file is never changed. A script in temp or the scratch folder (`python <scratch>/check.py`) and output redirected there (`gate.py --full > <temp>/gate.log`) pass. Code the jail cannot read, `python -c` and a script on standard input (`python3 - <<'EOF'`), is judged as writing the folder it runs in: refused in the read-only checkout, allowed from temp, and the refusal's alternative names temp (`jail.destination` skips a root a read-only root holds). A `python -c` that only reads is refused there too (tests/guard/test_rolepolicy.py `test_inline_code_that_only_reads_is_still_refused_in_the_checkout`).
  - `role-workdir`: a shell call whose own working directory (`Action.workdir`, from a host whose shell call names one; Claude's does not) is outside the checkout the session runs in. Another drive is outside.
  - `role-shell` (`shell_gap`): an interpreter that would wait for input on the terminal, nested shells included. Only the interpreter's own options count: they end at the first operand, the script (python, bash, a PowerShell file), the word after `-c` or `-m` (python, bash), after `-Command`, `-File` or `-EncodedCommand` (`-e`, `-ec`; PowerShell) or after `/c` (cmd), so every later word is the program's (`python -m pytest -s`, `python x.py -i`, `bash -c "echo hi" -`, `pwsh -File x.ps1 -n 5` pass). ### Landed scripts

A python script file a subagent runs by its path is not judged as `backlog-raw-write` when it is its repository's landed code (owner Q-2180, "Trust landed code"; `backlogrole.landed_script`): the repository's own tools, such as `python tools/daily_full.py --plan` in a worktree, run as they landed. Only the landing's merge in the main checkout moves the local main branch (`git-shared-ref`, `git-push-main`; git refuses a fetch or push into a checked-out branch), so that branch holds only reviewed code.

- **What counts:** only a script file the command names (`backlogrole.script_file`), never code on standard input, a heredoc, `-c` code or files piped in (`python < f`, `cat f | python`), even when they hold the same bytes.
- **The checks, in order, each failing to "judged as before":** the path is a file in a main checkout or a linked worktree of it, not the PM data worktree, and inside that checkout; the repository's git common dir is one the session may not write (`jail.judge` against its roots), so a repository it made or can rewrite is never trusted, and this is checked before any git runs; the repository has a PM data record (`rules.pmdata_recorded`); the main branch is the main checkout's `.kit.json` `main_branch`, and when that writes none and `<remote>/HEAD` gives it, it is trusted only as `main` or `master`; it is never the linked worktree's own branch; the script's bytes are the blob `git --no-replace-objects cat-file blob refs/heads/<main>:<path>` reads (a replace ref does not stand in), or are once its CRLF line ends read as LF. The remote-tracking main is not read: a fetch moves it. Any error is "not landed".
- **Not widened:** the trust adds no reach that a script a script runs lacks today. A landed script that imports a module the worktree edited, or runs a file the subagent wrote, is not read past the script (docs/guard-fallback.md "Known limits", "Backlog roles and code").
- **Tests:** tests/guard/test_backlog_role.py (`LandedScript`, and `LandedScriptReplaceRef` on real git).

## Batch files and cmd.exe

Windows runs a `.cmd` or `.bat` file in `cmd.exe /c`, which reads the whole command line again before the batch file sees it: `&`, `|`, `<` and `>` run or redirect another command, `^` escapes, a `"` toggles quoting, `%` expands a variable, `(` and `)` open and close a block, `!` expands one under delayed expansion, and a line break ends the line. PowerShell, Git Bash and Python's `subprocess` quote an argument only when it holds a blank, so `kit status 'a&whoami'` hands cmd.exe `a&whoami` bare and whoami runs. Rule `cmd-reparse` (`kitlib/guard/rules.py` `cmd_reparse`) refuses such a run. No mode names it, so it denies (docs/guard-core.md "Rule modes").

- **The run:** `commands.batch_run` reads the program word from the text alone: a base name ending `.cmd` or `.bat` (any case, any path, either slash, a trailing dot or space dropped), cmd's `call <batch file>`, and the bare kit command `kit` with no extension. The kit command is the `kit.cmd` shim on the PATH, and no file is looked up, so a bare `kit` is caught even when no `kit.cmd` is on the PATH: it fails closed, as intended. PowerShell's `&`, `Start-Process -ArgumentList`, a nested `cmd /c`, `/k` or `/r` text, cmd's `start`, a `bash -c` text and `xargs` are read as for any program. In cmd's own text the program word is also read cut where cmd ends a command name (`commands.CMD_NAME_ENDS`): at `,`, `;`, `=`, `(` and `/` (OBSERVED, `cmd /c` on a scratch batch file: `args.cmd,hi x`, `args.cmd;hi`, `args.cmd=hi`, `args.cmd(hi`, `args.cmd/hi` and `args/hi` each ran it with the rest of the word as its first argument, and `call;args.cmd` and `call,args.cmd;hi` called it; `@` and `+` end no name: `args.cmd@hi` and `args.cmd+hi` were not found). So `cmd /c "kit,status x^&y"`, `call;kit` and `kit.cmd,status` are batch runs; the word is read as written as well, and a quoted one only so. A program the line computes (`& $p`) is not read.
- **Git Bash's start:** `/usr/bin/start` is a script, `"$COMSPEC" //c start "${@//&/^&}"`: it hands every word to cmd.exe's `start`, escaping only `&`. So cmd.exe reads each word before the program does, whatever the program, and a batch file it starts reads them a second time, undoing the `&` escape (OBSERVED, Git Bash `start //b //wait` on a scratch Python script and batch file that print their arguments: for the script `'50%OS%'` arrived expanded, `'a^b'` as `ab`, `'a>f'` made the file `f` and printed nothing, `'a|sort'` and `'a<f'` arrived as `a`, and `'a&ver'` arrived unchanged; for the batch file `'a&ver'` ran `ver`). `commands.bash_start` reads a Git Bash `start` (any path) for the rule: every word after `start` is judged as a batch file's argument is, the program is the first word after start's options (`//b`, `//wait`, `//d <dir>`) and a title (an empty word, or one with a blank, which Git Bash quotes and `start` takes as the title). PowerShell's `start` is `Start-Process`, read as above.
- **The arguments:** a word holding a character of `shell.CMD_REPARSE` (`shell.cmd_unsafe`): `& | < > ^ % " ( ) !`, carriage return and line feed; a computed word, whose value cmd.exe reads; an unquoted PowerShell splat (`@a`); in bash, a word with an unquoted, unescaped `*`, `?` or `[` (`commands.bash_glob`), which bash fills in with file names that cmd.exe then reads, so a file named `x&whoami` would run whoami (`'x*'`, `"x*"`, `x\*` and `$'x*'` are literal and pass; PowerShell and cmd pass a wildcard to a native program as written); and any run `xargs` makes, whose arguments come from its input. PowerShell's `--%` passes the rest of the line through unread, so the words after it are judged as written. `,`, `;`, `=` and the other delimiters only split the arguments, which the batch file's own `%1` reads, and are not refused (OBSERVED: probed on a scratch `kit.cmd`, a `,;=` word arrived unchanged).
- **What was probed** (OBSERVED, on a scratch `kit.cmd` and `gradlew.bat` that print their arguments, Windows 11, Python 3.14): from Git Bash `'-^C'` arrived as `-C`, `'50%OS%'` expanded, and `'q"r' 'a&echo INJ c'` ran `echo INJ`; from PowerShell a word with a line break lost every word after it; a Python `subprocess` list `[..., '--tests', 'a&whoami']` ran whoami. From PowerShell `!` arrived unchanged, as delayed expansion is off under `cmd /c` by default; the Command Processor `DelayedExpansion` registry value can turn it on (INFERENCE, not probed), so `!` is refused as well.
- **Order:** the rule runs last, after each command's other rules, `brace-limit`, `busy-wait` and, on an unclean line, the fallback (`rules.shell_command`, `late`), so a refusal another rule owns (`hub-owner-verb`, `owner-tool`, `backlog-role`, a write rule) answers first.
- **Who:** every session, the owner's own included: the hazard is cmd.exe's, whoever types the line.
- **Instead:** for the kit command, the same words through python and `tools/kit.py`, which no cmd.exe reads: `kit status -C <dir> 'x&y'` gets `python "<kit>/tools/kit.py" status -C <dir> 'x&y'` (each word re-quoted by `rules.shell_word`; a computed word, a splat or a word holding a line break as `<value>`; a PowerShell `--%` dropped; a bash wildcard kept as written, since through python no cmd.exe reads the names bash fills in). A Git Bash `start kit ...` gets the same line, run without `start`. Every such line runs clear of the rule. For another program the advice is prose: run it directly (python, node, the exe a batch file starts; without `start`), or give it words without cmd.exe's characters and no unquoted wildcard.
- **Allow rules:** an allow rule is matched after the guard has judged the call, so no allow rule passes a command this rule refuses. The land allow lines also deny `^`, `!` and `)` in the `kit land` spelling (docs/allow-rules.md).
- **Limits:** a program the line computes (`& $p`, `$X args`); a batch file `find -exec` runs; a batch file on the PATH named without its extension other than `kit` (`npm`, `npx` and other shims: PATHEXT is not looked up); a line the parser cannot read, which reaches this rule only for the commands it did parse; a batch file run by a tool the line starts (`gate.py`, code python runs; `machine_lock.py run` and `background` are no gap: every .bat or .cmd they start, by its path, by a bare name CreateProcess finds (the current folder included), with a trailing dot or space, or found for a name with no extension, goes through a cmd.exe line they quote themselves, so `run -- x.cmd 'a&b'` passes `a&b` literally, and an argument holding `%`, `"` or a line break is refused, kitlib/lock/run_cmdline.py `script_command`); a program path that itself holds one of the characters; and a Git Bash `start` of a URL or an exe with an `&` in a word, which reaches an exe intact (OBSERVED above) but is refused all the same, as every `start` word is judged alike (`start 'https://x/?a=1&b=2'`: open it another way, or with no `&`).
