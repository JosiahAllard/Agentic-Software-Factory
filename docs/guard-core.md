# Shell guard: output, modes, hosts and parsing

Part of docs/guard.md (the index); the sections below are moved there unchanged.

## Output

- **Allow:** the hook prints nothing and exits 0, except after a plugin refresh, when the folder the session's header named is gone or the session was last named a folder at least an hour ago (docs/plugin-source.md "Layout", `headers/`): then it prints the line naming the kit folder now in use (`kitlib.host.headerfollow`) as `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": ...}}`, with no `permissionDecision`, so Claude Code's own permission flow runs as for an empty answer (`hosts/claude/adapter/host.py` `tool_context`; Codex's adapter has none, so Codex gets no line). A warned allow ("Rule modes") carries that line after its warning, on a line of its own.
- **Deny or ask:** it prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny"|"ask", "permissionDecisionReason": ...}}` and exits 0. The same refresh line can ride along as an `additionalContext` beside the decision; the reason is never changed.
- **Reason format:** `<what and why> Instead: <the exact command to use> [kit guard: rule=<rule> role=<main|subagent>]`. The role is what the event said (on Claude, `agent_id` present or not; `Action.agent`). The self-test reads it. The command after `Instead:` is also the Decision's `instead`.
  - After `Instead:` comes one command, ready to run, with no prose after it. Any explanation goes in the sentence before it, which ends with `:` (tests/guard/test_rules.py `test_rows` checks this for every row).
- **Unguarded tools:** a tool no rule can refuse (any tool but Edit, Write, MultiEdit, NotebookEdit, Bash, PowerShell, Read, Grep and `mcp__*`; Glob among them, as a names search reads no token's text: `hosts.json` `claude.hook.guarded_tools`) is allowed before kitlib is imported, read by `boot/hook.py` with json alone (`skips`; tests/guard/test_entry.py `Unguarded`, which also holds the list equal to the adapter's tool tables and `MATCHER`). It fails toward the guard: a payload that is not JSON or not an object, a tool name that is missing or not a string, and hook data it cannot read or of the wrong shape all go to the full guard (a missing `hosts.json` or host entry blocks the call), never to an allow.
- **Guard error:** if the guard fails on a guarded tool, it denies with rule `guard-error` (fail closed; `kitlib.host.hookmain.run`).
  - This includes a `kitlib.guard` that will not import and a payload the adapter cannot parse: hookmain imports the guard inside its `try` and has the adapter render the deny. Its `Instead:` reruns the hook on the event (`python "<kit>/boot/hook.py" claude PreToolUse < event.json`).
  - If the adapter or hookmain themselves will not import, or the answer cannot be written, the hook exits 2, which Claude Code also reads as a block.
  - Test: tests/guard/test_entry.py breaks each import.

## Refusal log

Every deny the hook answers adds one JSON line to `<pm_data>/audit/refusals.jsonl`, `<pm_data>` being the machine config's `pm_data.path` (`kitlib/guard/refusal_log.py` `record`). The owner reads it to count which rules refuse which roles, without asking an agent to keep a log.

- **Who writes it:** `kitlib.host.hookmain.run`, for every host's hook, after the answer text and before the hook exits, whatever made the deny (a rule, `guard-error`, `guard-timeout`, the host's own screen). On Codex the kit-tool broker writes it too (`hosts/codex/adapter/runtime.py` `evaluate_bound`), for a deny and for its own error (`host-runtime-error`); Codex has no ask, so an ask is logged there as a deny. An allow and a warning add no line, nor does an ask on a host that keeps it (Claude Code).
- **Fields,** in this order (`refusal_log.FIELDS`): `utc`, `host`, `rule` (`unknown` when the deny names none), `role` (`main` or `subagent`, as the guard judged the Action), `agent_role`, `agent`, `session` (the launcher's `PM_KIT_SESSION_NAME`), `tool`, `kind`, `repo` (the folder name of the call's main checkout, read with no git child; `-` for any other layout and for a name that is the user's profile folder or `USERNAME`), `instead_given`. An absent value is `-`. A call of several Actions is logged by its first.
- **Never in it:** the reason, the command, the path, the working directory or the Instead text.
- **Concurrent hooks:** each append holds a lock (`kitlib.fs.treelock`) on `.refusals.lock` in the audit folder, so lines never interleave. Nothing on the way starts a process, so a slow or hung git cannot hold a deny up; that is why the lock is `kitlib.fs.treelock` and not `kitlib.git.lockplace`, which would ask git where the checkout is first.
- **Best effort:** no `pm_data`, a machine config that does not read, the lock still busy after 1 s, or a failed write adds no line and never changes the verdict or the exit code. The host reads the answer only when the hook exits, so the log's time (up to `refusal_log.BOUND`, about 1.55 s) is added to the hook's. Under the kit's tests a lookup of the real home (`HomeFenced`) adds none.
- **The folder** is the backlog audit log's (docs/backlog.md "Audit log"), left untracked; `pm-data-audit` refuses agents' own edits there (docs/guard-rules.md "Rules"). The hook's append is not a tool call, so no rule judges it.
- **Known limits:** only the kit guard's denies are logged (not the host's own permission system or classifier, an ask the owner declines, or a kit tool's own REFUSED exit); no kit tool reads the log yet; a session the launcher did not name logs `-`; a deny's hook takes up to about 1.55 s longer (`refusal_log.BOUND`); a block before kitlib loads (`boot/hook.py`, `boot/kitboot.py`) writes no line; the `role` field is the judged Action's, so in a marked session on a host with no subagent identity it can differ from the tag in a `guard-timeout` or `guard-error` reason.
- **Tests:** tests/guard/test_refusal_log.py; tests/host/test_hookmain.py `RefusalLog`; tests/codex/test_runtime.py `BoundGuard`.

## Rule modes

`kitlib/guard/modes.py`. Every refusal goes through `rules.refuse`, which asks the rule's mode:

- **deny:** the refusal stands, as its rule's verdict (deny or ask).
- **warn:** the call goes ahead, and the refusal's reason reaches the agent after `[kit guard warning] ` (`rules.WARNING`; the Decision is an allow with rule `warn`, `rules.WARNED`). Claude gets it as the hook's `additionalContext`, with no `permissionDecision` (`hosts/claude/adapter/host.py` `WARN_CONTEXT`); Codex shows nothing for a warned allow. A warning quotes at most 120 characters of the shell command it is about (`rules.CITE_MAX`): a backtick quote of the command's text, or of a part of it, that is longer is cut there and ends ` [...]` (`rules.ELIDED`, `rules.cited`); the `Instead:` text and the rule tag stay whole, and so does a deny or an ask, which quotes the full command as before. The checks after a warned refusal still run, so a later deny still decides. Several warnings on one call are joined (`kitlib.host.hookmain`).
- **off:** the call goes ahead, and nothing is said.

The kit's modes are `modes.DEFAULTS`; a rule it does not name is deny:

- **warn:** `unplaced` (below), `unreadable`, `git-alias`, `heavy`.
- **off:** `wrapped-gate`, `busy-wait`.
- **deny, kept:** owner-only tools and files, `hub-owner-verb` on a parsed hub tool run or an unreadable line naming the hub tool, the hub's secrets, the machine config (`machine-config`), the ledger, PM data, lock state, `.kit.json`, generated files, gate results (`gate-result`), destructive git in a main checkout, `branch -D`, forcing or deleting main, `core.hooksPath`, owner identity, the owner's delegation list (`owner-delegations`), kill-by-name, an agent's shared stash in a linked worktree (`git-stash-shared`), git that python or node code on the line runs (`interpreter-git`), the backlog's roles, raw writes and audit log (`backlog-role`, `backlog-raw-write`, `pm-data-audit`), who lifts a branch's gate budget (`gate-allow`), a brace expansion the guard does not write out (`brace-limit`), file-tool edits of a main checkout, and the write jail's outer bound (`dev-drive`, docs/guard-jail-roles.md "Write jail").

The owner sets a rule's mode in the machine config's `guard_rules` (`{"<rule>": "deny"|"warn"|"off"}`; docs/kit-json.md "Machine config keys"), and only there: never `.kit.json` or another file a branch carries, so a branch cannot loosen the rules it is judged by. A value that is not one of the three is ignored, and a config that does not read leaves the defaults (`modes.resolve`).

- **unplaced:** a write the guard cannot place (a computed or unread target, code given on the line, a git or .NET call whose directory the text does not tell, a computed `-C`, a computed `git worktree remove` target, a computed push refspec with no `--force`, `--delete`, `--no-verify` or literal `+` or `:`, git on a jailed session's unreadable line) is refused under `unplaced` instead of the placing rule (`rules.unplaced`, `rules.PLACE_RULES`: `main-checkout`, `write-jail`, `git-main-history`, `git-restore`, `git-checkout`, `git-reset-hard`, `git-clean`, `git-stash`, `git-bulk-add`, `git-commit-all`, `dev-drive`), with the same reason and alternative. Those rules still deny a write that resolves literally into a main checkout or outside an agent's folders, and so does a write git cannot place inside a `.git` folder, or git pointed elsewhere by `GIT_DIR`, `--git-dir`, `--work-tree` or an environment change the guard cannot read (`write-jail`). An agent session's .NET call with a computed path is refused under `write-jail` where `unplaced` would only warn (docs/guard-rules.md "Shell writes").
- **gate-result:** an agent session's literal write into a repository's gate result folder (`<git common dir>/kit-gate-result/`, `rules.gate_result`), which only the gate writes, is denied; `Instead:` is `python "<kit>/tools/gate.py" wait-result <branch> --tip <sha>`.
- **Tests:** tests/guard/test_cheap.py (each mode, the defaults, the owner's overrides, the kept denies).

## Hosts

The guard judges a neutral `kitlib.host.Action` and answers a `kitlib.host.Decision` (ARCHITECTURE.md "Host contract"); no module under `kitlib/guard/` reads a host's payload or writes its output.

- **The hook:** `boot/hook.py claude PreToolUse` (the one entry of every host) hands Claude's adapter, `hosts.claude.adapter.host.ADAPTER` (the module `hosts.json` names), to `kitlib.host.hookmain.dispatch`, which runs `kitlib.host.hookmain.run`: the event JSON is parsed by `hosts/claude/adapter/events.py` `parse`, judged by `kitlib.guard.decide(action)`, lowered by `kitlib.host.degrade` when the host cannot show an ask, and rendered by the adapter's `render` (nothing for a plain allow, the warning for a warned one, the JSON in "Output" for a deny or an ask), with the refresh line added by `tool_context` when there is one ("Output"). The fail-closed deny, an optional deadline (rule `guard-timeout`; Claude passes none) and the settings entry (`hookmain.command_line`, the one place a hook command line is written) are hookmain's, the same for every host.
- **What Claude's adapter reads:** `tool_name` sorts the call: a file tool (Edit, Write, MultiEdit: `file_path`; NotebookEdit: `notebook_path`) is an `edit`, Bash and PowerShell a `shell` (`command`, its dialect, `run_in_background`), Read and Grep a `read` (`events.READ_TOOLS`: Read's `file_path`; Grep's `path`, absent meaning `cwd`, with `Action.params` `{search: contents, filter: <Grep's glob>}`; Grep's `pattern` is not read), `mcp__*` an `mcp` call, anything else, Glob included (a names search reads no token's text), `other`. `cwd` as sent. `agent_id` is `Action.agent`; `agent_type`, for a subagent only, is `Action.agent_role` with one kit plugin prefix dropped (docs/guard-fallback.md "Agent names"). `PM_KIT_ROLE` is read from the hook's environment, as before.
- **Host facts the rules need** arrive as Action fields or from `hosts.json`, never as host names in kitlib: the role a subagent runs as (`agent_role`), the shell dialect, whether the call is backgrounded, the host's form of the same edit at another path (`retarget`, for an `Instead:` line), and the lock MCP's tool names (the host profile's `mcp_tool_format`; docs/guard-fallback.md "Lock MCP").
- **Paths:** every path the guard folds to compare, key or make canonical goes through `kitlib/guard/paths.py` `norm` (on Windows the rules are unchanged; on Linux the case fold is per mount, docs/guard-jail-roles.md "Write jail" "Paths"). A command line's text (drive letters, quoting) is the shell parser's, not a path rule: on Linux (`paths.posix`) `shell.resolve_path` reads a word starting with `/` as absolute and any other in the folder the line is in (no drive, share or `/c/x` mapping) and reads each `..` from where the links before it lead, as the kernel does (`paths.physical`: with a link `d` to `/x/src`, `d/../f` is `/x/f`; a Write or Edit tool path is read the same way), bash's `cd` is `cd`, `pushd` or `popd` by its exact name (`CD` and `chdir` move nothing, an assignment before it is passed over) and `cd /d` goes to the folder `/d`; the folder a cd moves to is kept as a real path (`shell._linux_cd`), with a flag when it was entered through a link (its text, or the folder before it, was not its real path): a cd with no `..` is the real path of its text, whether or not the folder exists yet (bash's `-L` and `-P` readings land on the same folder), so `cd d && echo x > ../f` with a link `d` to the main checkout's `src` writes the main checkout's `f`; a cd with a `..` is unknown after a cd through a link (bash folds it from a `$PWD` the guard does not keep), or when the real path of the reading bash's default `cd -L` makes (`..` folded from the text) is not the real path of the text read physically (bash falls back to the unfolded text when the folded folder is missing), and otherwise is that real path (`cd -P` is read physically, with no flag); a nested shell started in the folder keeps its flag; a folder `env -C` or Start-Process `-WorkingDirectory` names is kept as its real path too (`shell.chdir_real`), and is unknown when it is no existing folder, or when it is the starting command's own folder reached through a link (a bash started there keeps the inherited `$PWD`); a line naming `CDPATH`, `SHELLOPTS`, `BASHOPTS`, `cdable_vars`, `set -P` or `set -o physical` anywhere leaves the folder of every cd it runs unknown, in its nested shells, evals and substitutions too, unless the cd's place starts with `/` and holds no `..` (none of them redirects it), and so does a `pushd +N`/`-N`; a cd place holding `*`, `?` or `[` is unknown on both systems; a write after a cd left unknown is `unplaced` (warn by default), bash drops every unquoted backslash (`\.\./x` is `../x`), `/` is a root as a drive root is (`rules.is_root`), and a ledger path is placed when it starts with `/` (`context._placed`). The guard is declared ready on Linux (`kitlib.guard.READY_PLATFORMS`; tests/guard/test_linux_paths.py runs on Windows through the platform seam).
- **Tests:** the guard tests build Claude payloads and decide them through the adapter (`tests/guard/claudehost.py`); tests/guard/test_entry.py runs the hook end to end.

## Parsing

`kitlib/guard/shell.py` tokenises Bash and PowerShell, and `cmd /c` text. `commands.py` reads the result: the program each command runs. `commands_nested.py` reads the text a nested shell runs and holds `read`, which parses a line whole; `commands_env.py` reads the environment a command sets; `commands_git.py` reads what a git call acts on.

- **Seen as text, not commands:** quotes, here-docs and PowerShell here-strings.
- **Seen as commands:**
  - `;`, `&&`, `||` and `|` split commands;
  - `$(...)`, backticks, a PowerShell argument in `( )` (one computed word, `shell._Scan.ps_paren_arg`; docs/guard-rules.md "Rules") and `powershell -Command "..."` (`/Command`, `–Command`; after a switch powershell.exe does not know (any switch outside `commands_nested.PS51_SWITCHES` and `PS51_ALIASES`, pwsh's value switches included; after `-i`, `-in` or an `-EncodedArguments` prefix the next word is read both as its value and as the command, `PS_VALUE_EITHER`; past `PS_FORKS_MAX` of them on one reading path the line is flagged `a powershell switch line with too many readings` and each further one is read as taking no value), which starts its command, both that text and a later `-Command` or standard input, each reading kept once and parsed on its own (`commands_nested.expand`): `commands_nested._nested_text`; `-File -` (any prefix of `-File`, whatever words follow it) reads its script from standard input as `-Command -` does, so text piped into it is parsed as a nested command and judged by the same rules, and a pipe the guard cannot read makes the line unreadable; after a switch powershell.exe does not know, `-File -` makes the line unreadable, as `-Command -` there does, and the words from that switch on are still judged as its command), `bash -c`, `cmd /c` (`//c`, `/k`, `//k` too, as Git Bash passes them) bodies are parsed again as nested commands;
  - the command after find `-exec`, `-execdir`, `-ok` or `-okdir` (up to `;` or `+`) is a nested command at find's working directory (`-execdir`/`-okdir`: at an unknown one), its words that hold `{}` computed;
  - a `trap` handler is a nested command at the trap's working directory, or at an unknown one when the line holds `cd`, `pushd`, `popd` or `Set-Location` anywhere (`commands_nested.LINE_CD_RE`); a `mapfile`/`readarray -C` callback is a nested command;
  - `env -S <string>` is a nested command;
  - a shell (`cmd`, `bash` and the other `commands.BASH_SHELLS`, `powershell`, `pwsh`) that `Start-Process` (`saps`, `start`) starts runs its `-ArgumentList` as a nested command, at the `-WorkingDirectory` when one is given (`commands_nested._sp_shell_text`): Start-Process hands it one command line, the elements joined with spaces, so for `cmd` the rest of that line after `/c` (`/k`, `/r`) is the text, read once with its outer quotes and once without; `bash` and `powershell` read their usual `-c`/`-Command` text from the words each element splits into (`commands._split_list`). The list is every word of an array, given by position or after `-ArgumentList` in its space or colon form (`-ArgumentList:'/c','echo x'`), up to the next unquoted, non-computed dash word (`commands._ps_param_word`; a quoted `'-NoProfile'` element is the child's), and a program given by position after `-ArgumentList` is the last word it took (`commands._start_process`). The common parameters (`-Verbose`, `-Debug`, `-ErrorAction`/`-ea` and the other `commands.PS_COMMON_VALUES`) and `-PSPath` (FilePath's alias) are parameters, never the program or a list word; a colon with nothing after it (`-FilePath: cmd`, `-WorkingDirectory: <dir>`) takes the next word. Start-Process resolves `-WorkingDirectory` as a wildcard path, and a bare `C:` or a drive-relative `C:x` against that drive's current location, so a value the guard cannot place exactly (`commands.sp_workdir_unplaceable`: those, a `*`, `?`, `[` or backtick, a device path, a Git Bash `/c/x` spelling), and a computed one (`$x`, `(Join-Path ...)`), leave the nested line no directory and its write is refused as one the guard cannot place. These readings follow PowerShell's binding closely, not exactly, so a parameter word they cannot place makes the line unreadable (below);
  - any other program `Start-Process` starts with a `-WorkingDirectory` (git, python, cp and the rest) runs in that folder (`commands.run_dir`, read as above): `commands_git.git_call` takes it as the directory git starts in, so `Start-Process git -ArgumentList 'commit',... -WorkingDirectory <main>` from a worktree is a commit in the main checkout. The shell-write rules (docs/guard-rules.md "Rules", `rules.shell_writes`) judge a program's own targets (the working directory a `python -c` or a script writes, cp's operands) from both that folder and the command's own directory, refused when either is a main checkout; git, and a `git-*` program, gives none there, its writes being the git rules' (tests/guard/test_start_process_workdir.py): a worktree workdir never lets a write pass that the command's own directory refuses, so `Start-Process python -ArgumentList 'x.py' -WorkingDirectory <wt>` typed in the main checkout is refused, while the same git call is not. For a main-checkout workdir typed in a worktree the `main-checkout` alternative is the same call with `-WorkingDirectory "<wt>"`. A computed workdir, or one `commands.sp_workdir_unplaceable` names, gives no folder: git there is git whose directory the text cannot tell, and the program's writes are ones the guard cannot place. A redirect and `-RedirectStandardOutput`/`-RedirectStandardError` stay placed from PowerShell's own location, which the workdir does not move (tests/guard/test_advice_workdir.py);
  - `cd`, `Set-Location`, `pushd` and `env -C <dir>` move the working directory for the commands after them.
- **Wrappers:** `env`, `command`, `exec`, `nohup`, `nice`, `time`, `timeout <n>`, `stdbuf`, `sudo` and `xargs` are skipped with their options (`time -p`, `nice -n 5`, `stdbuf -oL` and so on). The program after them is read. After `xargs -I`, `-i` or `--replace` (`commands.xargs_opts`), every later word that holds the replace string is computed (`commands.fill_words`): the program word and `sh -c` or `env -S` text too. The first `git` word in its tail is the program.
- **Redirects:** recorded per command with their targets.
- **Arguments the shell rewrites:** brace expansion, ANSI-C strings (`$'a\tb'`) and a bash backslash in a word are read as the words the shell produces. Every unquoted brace group of a bash word is written out, nested groups too, in bash's order (`{a,b}{1,2}`: a1 a2 b1 b2; `{x,{y,z}}`: x y z). A word that would give more than `shell.BRACE_LIMIT` (256) words is not written out: the parse is unclean (docs/guard-fallback.md "Fallback"), the word is one computed word, as a variable would be, and rule `brace-limit` refuses the line (docs/guard-rules.md "Rules"; kitlib/guard/shell.py `_brace_group`; tests/guard/test_shell.py `BraceExpansion`, tests/guard/test_delegfile.py). Brace groups bash expands that the guard leaves as written: docs/guard-fallback.md "Known limits".
- **Git spellings:** `-C`, `-c`, `--git-dir`/`--work-tree`, `--config-env` and git's place and config variables are read; long options are matched by unique prefix, and options that take a value skip it.
  - The variables (`commands_env.GIT_ENV_NAMES`): `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`. One counts when set before the command (`=` or bash `+=`), through `env`, by `export` and the like (with or without a value; not a `-p` listing of `declare`, `typeset` or `local` such as `declare -p GIT_DIR`: `export -p` and `readonly -p` with a name still count, and not bash's or PowerShell's `set`, where `set -- GIT_DIR` sets `$1`: cmd's `set` counts, `commands_env.exporter_args`), `$env:`/`${env:}` (`=` alone or in the same word), `Set-Item`, `Set-Content`, `Add-Content` or `New-Item -Name` on `env:`, a `Rename-Item`/`Copy-Item`/`Move-Item` to an `env:` name, or a `SetEnvironmentVariable` call (not a string that names it, as a commit message or `Write-Host "..."`; a `$( )` in a string is a call) (`commands_env.git_env_set`). Set anywhere in the line, nested text included (`eval`, `bash -c`, `env -S`, `Invoke-Expression`, a `source` of `/dev/stdin`), it leaves every git of the line unplaceable (`commands_env.mark_git_env`), whatever the order. One exception: `GIT_INDEX_FILE` set alone before a git, as a prefix or through `env` (`GIT_INDEX_FILE=<tmp> git read-tree`), reaches only that git and the text nested in it, so the line's other git is placed as written, unless the line may define a function or an alias (`commands_env.git_env_prefix`). A name is read as the shell passes it: a backslash bash drops inside it (`export GIT_D\IR=`) is dropped (`commands.said`, `commands.passed`).
  - Only literal assignments are read (`commands_env.git_env_set`, `commands_env.line_env_names`, `commands_env.ps_env_targets`). A name the text computes (`export $V=`, `local -x $1=`, `Set-Item "env:$n"`, cmd `set %V%=`) and any other way to change the environment (`declare -n`, `set -a` with a `source` of a file, `alias`, a `trap`, `read`, a leading backslash `export \GIT_DIR=`, a splat, script text PowerShell compiles, `Start-Process -Environment`, an `env:` item renamed or copied to another name) is not read (the guard catches honest mistakes, not evasion).
  - A `$env:VAR` that starts an item path (`Set-Content "$env:TEMP\x.txt"`, `Copy-Item a.txt $env:TEMP`) is a read. A line with no git is not affected.
  - Once one of these, `--git-dir`, `--work-tree`, `core.worktree` or `--config-env` makes git unplaceable, a `-C` before or after it does not place it again (`commands_git.git_call`).
  - Every git word is matched in the form the shell produces, the subcommand and options included, not only the program word.
  - A subcommand the text does not spell out (a variable, a substitution) makes the parse unclean. So does such a word in an option position that the git rules read.
  - Put `--` before a variable path, so it is not read as an option.
- **Unclean parse:** the parse is unclean when the text holds something the tokeniser does not model:
  - an unclosed quote, substitution or heredoc, a PowerShell `<#` with no `#>` (`shell._Scan.tokens`), or a `case` statement;
  - an encoded command, or a shell, `iex` or `Invoke-Expression` reading its commands from a pipe;
  - `iex`/`Invoke-Expression` of a computed value (`iex ("git " + "stash")`, or `"git $s" | iex`);
  - a shell or `source` reading a process substitution (`bash <(...)`, `source <(...)`);
  - a non-literal `bash -c`, `powershell -Command`, `cmd /c`, `eval` or `env -S` text, `trap` handler or `mapfile -C` callback;
  - a shell `Start-Process` starts with a computed `-ArgumentList` element (an `@(...)` array included);
  - a `Start-Process` (`saps`, `start`) parameter word that names no parameter of it or names more than one (`-Bogus`, `-e`), or a switch whose `-Name:` is followed by a space (`-Wait: $true`), with or without a program (`commands._start_process`, its `unread`; with no program, a `commands.Unread` that only `commands_nested.expand` gets, so `rolepolicy.lock_verb` still sees a call with no program);
  - an unquoted `--` in a `Start-Process` call (every later word positional), a splat (`Start-Process @p`, `Start-Process cmd @p`: `commands.PS_SPLAT_RE`), or `--%` between its words (the rest of the line passed as written; `commands.PS_STOP_PARSING_RE`), each in any of the dashes `shell.PS_DASHES` (`commands._sp_unreadable`);
  - a `cmd` word before its run switch, typed or passed by `Start-Process`, that holds `/c`, `/k` or `/r` anywhere but is not that switch alone (`/cecho`, `/q/c`, `;/c`, `,/c`, `=/c`, `x/c`, `"/c"`; `commands_nested.CMD_RUN_HIDDEN_RE`, searched, not matched at the word's start), since cmd splits its switches at `,`, `;` and `=` as well as spaces; or a typed `cmd` word before its run switch that is computed (`commands_nested._shell_text`);
  - a program named by a variable or a substitution;
  - a git subcommand or read option that is not literal;
  - a brace expansion, ANSI-C escape or backslash in a program name;
  - a `cmd` `if` statement or `for ... do` loop;
  - more than `commands_nested.MAX_NESTS` (64) nested shell texts in one line (`commands_nested._nest`): each powershell reading may be a powershell line that forks again (`pwsh -i pwsh -i pwsh ...`), so the line's total is capped; a reading is not merged with the same text under another outer command, whose chain the rules read.

  The rules still run on what was read, then docs/guard-fallback.md "Fallback" runs.

Tests: tests/guard/test_shell.py.

## State

Every rule is a read-only check of real state. `kitlib/guard/context.py` `Ctx` gathers what the rules read, so tests can hand them a fake machine.

- **Place:** `kitlib.git.repo.classify`'s answer for the working directory or the target path: MAIN, LINKED, NONE or UNKNOWN.
  - `kitlib/guard/place.py` reads it from `.git`, gitdir and commondir files, so a call starts no git child. It reads the common config and, while that turns `extensions.worktreeConfig` on, the work tree's own `config.worktree` after it, as git does (the last `core.bare` wins). Any shape it cannot read the way git would (a bare or `core.worktree` repository, any other extension, `[include]` or `[includeIf]`, a `core.repositoryformatversion` above 1, a config line git refuses or continues onto the next, a broken gitfile, a path inside a git directory, a junction, symlink or subst drive on the way, a folder another user owns, a discovery variable such as `GIT_OBJECT_DIRECTORY`, any error while reading) goes to `repo.classify`.
  - Tests: tests/guard/test_fsplace.py asks both on real repositories; tests/guard/test_place_decisions.py decides every rule row with each and requires the same decision.
  - The PM data worktree (docs/pm-data-branch.md "Guard place and commit hooks") counts as MAIN, though git calls it LINKED: `Ctx.place` answers MAIN for a linked worktree whose top is the machine config's `pm_data.path`. Only when the machine config has no `pm_data` does the record decide: a linked worktree whose HEAD is `ref: refs/heads/<branch>` of the `kit-pm-data.json` record in its git common dir. When the strict reader refuses the machine config for another key, `pm_data` is read and checked on its own. The main-checkout rules then apply there, and a refusal names no new worktree to make (agents do not work in it). `git push` and `git worktree remove` act on the repository the data worktree shares with the kit, so from it they are judged by the kit's own `.kit.json` (refused when it does not load), and the data branch alone by the data worktree's. A main checkout is never changed. Fail closed (rule `pm-data`, subagent writes): a machine config whose `pm_data` does not read denies every one; a linked worktree whose record or HEAD does not read denies those aimed at or run from a linked worktree of that repository. Tests: tests/guard/test_rules.py `PmDataPlace`.
- **Config:** `.kit.json` of the main checkout a path belongs to, via `kitlib.config.load`. A worktree's own `.kit.json` is never read, so a branch cannot loosen its own rules. The one exception is the PM data worktree, which counts as MAIN: its own `.kit.json` is read (none there: the defaults, under which a subagent may not edit it).
- **PM data record:** `Ctx.pm_root` reads the root commit from the record in the git common dir of the machine config's `pm_data.path` (none when the machine config names no `pm_data` or that repository has no record; a record or config that does not read, or a `pm_data.path` git cannot place, is an error). Only `rules.data_copy` reads it, and fails closed on that error. The guard runs no git of its own for these rules: an alias in git's config is not looked up, and whether a repository is a copy of the data or shallow is not checked (the guard catches honest mistakes, not evasion).
- **Lock:** held only when `MACHINE_LOCK_RUN` names a run that `kitlib.lock.run.nest_check` accepts: an ancestor of this process, alive, and holding. The variable alone is never proof.
- **Gate-OK record:** `kitlib.records.gate_ok.verify_record(root, sha)`, the record in the dev drive's record folder, or, only with no `dev_drive`, its `.git` copy (docs/gate-records.md "Gate-OK record", "Where the records are"). The record must name a `config_rev` in that commit's history, and its gate config hash must be that of the `.kit.json` "gate" the `config_rev` commit holds (docs/gate-records.md "Gate-OK record"). A record without `config_rev`, or made under another gate config, does not count.
- **User config:** the machine config (docs/kit-json.md "Machine config keys"), for `ledger_path`, `ledger_dir`, `guard_mcp_prefix`, `guard_mcp_tools`, `guard_agent_marks` and `guard_mark_roots`, read tolerantly (a value that is not a string or a list of strings, such as `guard_mark_roots`, is dropped when the strict reader refuses the file). A file the strict reader refuses still yields an absolute `ledger_path` and `ledger_dir` (a relative one read against the PM repository), so the ledger and its rulebooks stay protected. A file that cannot be read, is not JSON or is not an object, or a `ledger_path` or `ledger_dir` that is not a path string or is blank (the key is then unset), or one that is not absolute once read (`C:books`), or a `ledger_dir` that exists and is not a folder (a trailing separator dropped first) (both still held as given), denies every subagent write (rule `ledger`, fail closed; `context._ledger_checked`, on the strict answer too). While such a fault leaves a ledger key unread (a blank or non-string key, a relative one with no PM repository, a file that cannot be read, or a `BAD` location whose pointer config cannot be read: `Ctx.user()` sets `ledger_unread`), the guard cannot place the ledger, so it asks the owner (ASK, rule `ledger`, `rules.ledger_unread`; a deny on a host without ask) about every edit and shell write of a main session, a target it cannot place included (one a worktree's write would pass with: `rules._write_from`, `rules.find_exec_writes`), and its git path writes (`rm`, `mv`, `restore`, `checkout-index`, `checkout` with paths; tree forms and moves only where `rules.ledger_wide_binds` binds), and denies a subagent's, git path writes included (`rules.ledger_git_unread`). The ask comes last: any other refusal of the call (a held ledger path, a protected file, `main-checkout`, `write-jail`, the git rules, the role policy's) wins over it (`edit_target`, `ledger_git`, `rules.Asked` in `shell_command`, `shell_writes` and `decide`, which still runs `rolepolicy.screen` after an ask); a ledger key that is still read keeps its paths denied for every session (tests/guard/test_ledger_dir.py `UnreadTest`). A `ledger_dir` not made yet, or outside the PM repository, is accepted. The file is the one `kitlib.config.user.locate` names, taken once per call (`Ctx.config_location`): the PM repository's `.pm-kit/config.json`, with `local.json` for the `LOCAL_KEYS`, never a home folder's file while the PM repository has one; a config still only in the home folder (`UNMOVED`), a home copy still beside the PM repository's files (`LEFTOVER`) or a location it cannot tell (`BAD`) denies every subagent write too, and an `UNMOVED` file, or for `LEFTOVER` the PM repository's `config.json`, is still read for its `ledger_path` and `ledger_dir` (`LEFTOVER`: those two keys only; for `BAD`, those two keys only, from `<pointer>/.pm-kit/config.json` when the PM-repo pointer's value is absolute (`Ctx._bad_ledger_keys`; a file there that cannot be read, is not JSON or is not an object adds nothing, and a ledger key there that is not a non-blank string is not taken; tests/guard/test_ledger_dir.py)), so the ledger, its rulebooks and its digest stay protected for every session (docs/kit-json.md "Moving the machine config folder"). The PM repository's machine config folder, `<pointer>/.pm-kit` (`jail.pointer_config_dir`: the PM-repo pointer's value as stored, `Ctx.pm_repo_pointer`; none with no pointer or a relative one), is held beside the home ones (docs/guard-jail-roles.md "Write jail", docs/guard-owner.md "Owner machine setup"), whichever folder the guard reads its config from.

## Size ceilings

Each `kitlib/guard` module has a line ceiling, and the guard has a total, in `CEILINGS` and `TOTAL_CEILING` of `tests/guard/test_size_ceiling.py`. The test fails on growth past one, on a module with no entry, and on a ceiling more than 5% above its count. Raising one is a deliberate edit.
