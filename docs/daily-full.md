# daily_full

`tools/daily_full.py [-C DIR] [--plan | --summary] [--force] [--out DIR]` runs every non-manual gate step in full (each step's `daily_cmd` when it has one, else its `full_cmd`, else its `cmd`; docs/gate-run.md "Steps"), on `"daily_full".ref` (default `<remote>/<main branch>`), in a detached worktree of its own (default `<worktrees_dir>/daily-full`). Logic: `kitlib/dailyfull`.

- Opt-in: it refuses (exit 2) unless `.kit.json` "daily_full".enabled is true. The kit never schedules it. A repository that wants it daily registers the schedule itself.
- It moves only a clean linked worktree of its own. A worktree of `.` or the main checkout, a folder that is not a registered linked worktree, or a tree with uncommitted files is recorded red `infra` with the reason (for a dirty tree, the file names). Nothing is cleaned, reset or switched.
- One run at a time per tree. Before it fetches, a run takes the tree's lock (`kitlib/fs/treelock.py`), an OS byte-range lock on `<git common dir>/kit-tree-<name>-<hash>.lock`, and it holds the lock until its result is written, on every exit. A second run finds the lock held and exits 5 with `daily: busy: held by pid N since T`. It does not touch the tree and records nothing. The system drops the lock of a holder that exits or is killed, so the next run takes over and says `took over`.
- The fetch and switch come before the machine-lock booking, not inside it. `runner.gated` takes the planned steps and loads the hook checks before it books, and both come from the tree at the ref. Only a run holding the tree's lock moves the tree, so a run waiting for its slot never moves a tree another run is gating.
- Each run fetches, puts the worktree at the ref, and loads the gate from the ref's own `.kit.json`. All steps then run in one slot of `"daily_full".kind` (default `daily-full`) through `kitlib.gate.runner.gated`, waiting up to `"daily_full".max_wait` seconds. A failing step does not stop the run.
- Every run writes `<out>/<stamp>/result.json`, where `<out>` defaults to `<gate log dir>/daily`. The fields are `verdict`, which is green, red or skipped; `sha`; `steps`; `red`, which lists the failing step names plus `infra` when the run could not start; `skipped`, the steps that did not run; `error`; for a skip, `reason` and `cause`; and, with staging on, `promotion` ("Promotion"). A run in which no step ran (every one SKIP) is red `infra`, never green.
- Unchanged commit: after the fetch, if the latest run that ran (skips do not count) is green at the ref's commit, the run is a recorded skip with cause `unchanged`, prints `daily: SKIPPED (unchanged) - ...` and exits 0. The recorded results under `<out>` are the state; there is no other file. A red latest run, or a green one at another commit, runs. `--force` runs regardless. `--summary` shows these skips as `skipped (unchanged since the last green run)`, not as a problem.
- A step's own machine-lock booking nests in the run's slot and takes nothing more. The module isolation run is such a step: a `daily_cmd` of `module_map.py --isolate` (docs/module-map.md "Isolation runs").
- A lock refusal is a recorded skip, not a red. The cause is one of busy, timeout, lock-unavailable, reserved or hold.
- `--summary` prints the status lines from the recorded runs:
  - the last verdict, with its failing steps;
  - the skips in a row;
  - STALE, when the newest attempt is over `"daily_full".stale_hours` old.

  As a preflight report hook it is `daily_full:summary_lines`.
- Exit codes: 0 green or skipped, 1 a step red, 2 usage or off, 4 the tree or its gate could not be readied (recorded red) or a promotion was not made, 5 another run holds the tree (nothing recorded). A lock usage refusal, such as an unknown kind, is exit 2 and recorded red.

## Promotion

With `.kit.json` `"staging".branch` set (docs/gate-landing.md "Staging branch"), landings move only the staging branch, and two runs move the main branch: the daily run below (`kitlib/dailyfull/promote.py`), and between daily runs the diff-selected promotion run (`tools/promote.py`, started by the hub's `staging-promote` job; docs/modules/staging-design.md). Both push through `promote.promote` below; `kitlib/dailyfull` never imports `kitlib/staging`. Staging off, the run is exactly as above: no `promotion` field, no line, no push.

- **Where the setting comes from.** After its fetch the run reads the `"staging"` section from `<remote>/<main>` as fetched (`promote.staging_read`: `kitlib.config.overlay_staging` on a copy of the config), never from the working tree or the ref under test, so a commit on staging cannot turn promotion on. When `<remote>/<main>` does not resolve, or git cannot show its `.kit.json`, promotion is off and the run is as it was (fail closed). When the overlay raises a config error (a section there that is not well formed, or the overlay's own second read of the file failing), the run is recorded red `infra` and exits 4. Whenever that read succeeded, the run's settings (its ref: `"daily_full".ref`, by default the work base) are resolved again from it, staging on or off: a staging section only in the main checkout's working tree tests `<remote>/<main>` and promotes nothing.
- **The daily record.** A green run on `<remote>/<staging>` writes S's daily record first (`write_daily_record`: `gate_ok.record_tested_pass` with kind `daily`, base the `<remote>/<main>` sha), the record the pre-push guard asks of a push to main with staging on. A record that cannot be written (or a kit without `record_tested_pass`) is `not-promoted` with the reason, and nothing is pushed. An `unchanged` skip relies on the record its green run wrote.
- **What it pushes.** A green run, or an `unchanged` skip, at commit S promotes S itself, never a later staging tip: `git push --quiet <remote> S:refs/heads/<main>`, with no force, no lease, no `--no-verify` and no delete, a 600 s timeout and `NETWORK_ENV` (a credential prompt fails instead of waiting). A red run promotes nothing. Before pushing it fetches again in the daily worktree and checks the shape: S not on `<remote>/<staging>` is `off-staging` (so is a `"daily_full".ref` other than `<remote>/<staging>`); `<remote>/<main>` already holding S is `current` (no push); `<remote>/<main>` with commits not on S is `diverged` (no push; the count is named).
- **What the push did** is read back from the remote (`git ls-remote <remote> refs/heads/<main>`), never inferred from git's exit code. The remote's main at S is `promoted`, also after a push that reported a failure; a main that moved on past S is `current`; one still behind S is `not-promoted`, with git's first stderr line (or `git exited 0`); one that went elsewhere is `diverged`. Any other answer (none, or a commit this checkout cannot place) is `unknown`. Nothing falls through to success.
- **The record and the exit.** `result.json` gains `promotion`: `{status, main, from, to, why}`. The run prints `daily: PROMOTED <main> <from>..<to>`, `daily: promotion: nothing to do - <why>`, or `daily: PROMOTION <STATUS> - <why>`. `promoted` and `current` exit 0; `not-promoted`, `unknown`, `diverged` and `off-staging` exit 4. `--summary` adds `daily     PROMOTION <STATUS> at <dir>: <why>` while the latest recorded promotion is one of those, until a later one is `promoted` or `current`.
- **The hook.** The push goes through the repository's pre-push hook like any other push: a hook that refuses is `not-promoted`. The kit's pre-push runs only where `core.hooksPath` names the kit's `githooks/`, and the kit sets it only when no value is set at any level (`kitlib/worktree/prep.py`, "Hooks"). On a machine where it is unset, no kit pre-push sees the promotion, and the remote's own branch protection is all there is.
- **When a promotion is due** between daily runs is no longer the daily run's: the `--if-due` form is retired, and the count and age thresholds are `"staging".promote_after_landings` and `promote_after_hours` (`kitlib/staging/changes.py`; docs/modules/staging-design.md "The trigger").
- **Local main.** The daily run moves neither the main checkout's local main nor its working tree (the promotion run does sync it, under the landing lock; docs/modules/staging-design.md "Promotion"). The tools that read the main checkout's working tree (new_worktree through `load(main)`, and daily_full's own settings) see a promoted `.kit.json` change only once the owner runs `git merge --ff-only <remote>/<main>` there. While local main is behind, `--summary` and the report hook add the read-only line `daily     local <main> is N behind <remote>/<main>: git merge --ff-only <remote>/<main>`.

Tests: `tests/dailyfull/test_promote.py` (the hook and the race on real git), `tests/dailyfull/test_dailyfull.py`.

## Bisect

With `"daily_full".bisect` set (docs/kit-json.md), a red run looks for the commit that turned its red steps red, still holding the tree's lock (`kitlib/dailyfull/bisect.py`). Its keys: `max_probes` (default 5, at most 50; 0 turns the bisect off), `prefix` (the record id prefix; unset, nothing is filed) and `session` (the session the filed record carries). Unset, nothing is bisected.

- Only a red of steps is bisected: a red `infra`, or a run with an `error`, is not.
- The search runs over `git rev-list --first-parent G..S`: S is the red run's commit, G the commit of the latest earlier green run that is an ancestor of S. No such green run: `not run: no earlier green run is an ancestor of <sha>`.
- The first probe is S itself. Green there, the verdict is `did not reproduce: possible flake` and nothing is filed. Red, a binary search finds the first red commit, at most `max_probes` probes in all; a cap reached first names the range the culprit lies in.
- A probe switches the daily worktree to the commit and plans that commit's own gate, logging to `<log dir>/bisect-<n>-<sha10>`. A commit whose gate lacks a red step counts as green for it. Each probe then runs in one of two ways:
  - Failing tests only, when every red step's log at S names its failing unittest tests and nothing in it is uncovered: the same parse as the targeted rerun (`kitlib/gate/rerun.py` `cover_step`; docs/gate-rerun-checkout.md "Targeted rerun"), of kit_tests and unittest logs. In one machine-lock slot of that commit's `"gate".kind` it runs `setup` if the gate has one, then each failing class with `python -m unittest -v <class>`, in the tier it failed in (`KIT_FAKE_GIT`), one `class-<i>.log` each (the targeted rerun's slot, `rerun.run_classes`). A class still running after the test runner's per-unit limit (in the kit, kit_tests' `UNIT_TIMEOUT`; elsewhere `"tool_tests".unit_timeout`) is ended, and the probe is inconclusive. The probe is red when one of S's failing tests fails or errors again, or a fixture of its class or module does (`setUpClass`, `setUpModule` and the like: its tests never ran), or when its class cannot be loaded though the commit's test file defines it. A test the commit does not have yet (no file, no class, no method) counts as green, so a culprit that adds a failing test is found. "Defines" reads the commit's source for `class <Name>`: a test renamed inside the searched range, or a class the file binds by import or assignment, looks absent there, so check a narrowed culprit against that. The narrowed probe assumes `unittest <class>` plus the tier's variables reproduce the setup the suite gives that test: an inference, the same one `gate.py --rerun` makes.
  - The whole red steps (and `setup`) otherwise, through `runner.gated` in a slot of `"daily_full".kind`: a log that does not parse, one with an uncovered failure (a test that could not be loaded, a TIMEOUT unit, a step that timed out), or a gradle or dotnet step (its failures carry a `runner`; a probe runs unittest classes only, and a gradle step's reports are not read here).
- When S's failing tests pass alone, a flake is not said yet: the same probe also runs the whole red steps at S (logs in `bisect-1-<sha10>-step`). Red there, the rest of the search runs whole steps; green there too, the verdict is the flake. That whole-step run is the cost a narrowed probe would have saved: one full run of the red steps, only for a red whose failing tests pass alone, within the first probe (the cap counts probes, not runs).
- A switch, config or plan failure (a hook module that exits while it loads among them), a lock refusal, a stop, a failed setup, or a red step or failing class that did not run, or ran past its limit, stops the bisect as `inconclusive: <why>`. The worktree is put back at S afterwards.
- The run's `result.json` gains `bisect`: `{good, bad, culprit, probes, verdict, mode}` (each probe `{sha, verdict, red}`; `mode`, once a probe ran, `tests: <n> class(es)`, or `whole step: <why>`, `whole step: narrowed green at S` after the case above), plus `filed` (the record id) when one was filed. The run prints `daily: bisect: <verdict> (<n> probe(s))`.

When a probe reproduced the red and `prefix` is set, the red is filed through the backlog library, every store check included, as `<prefix>-DAILY-RED-<SHA10>` (`kitlib/dailyfull/file.py`). SHA10 is the culprit's, or S's when only a range was found. The scope is the paths the culprit changed against its first parent, or `none`. A repository on the implicit default store files in the PM data branch's store. Filing is idempotent: an id already held is not added again, and a priced record is never priced again.

The record is always priced at priority 2, `priority_by` agent, in the same call: an agent's own price never takes priority 1, and the PM or the owner promotes it. No machine config key changes the price; the removed `daily_red_ruling` is refused as an unknown key (docs/kit-json.md "Machine config keys"). Tests: `tests/dailyfull/test_bisect.py`.

## The schedule

The kit registers no task for it (above); the repository's owner does. A task whose program is `python.exe` is a console program started by a process that has no console, and Windows gives such a program a new console and shows its window (`kitlib/proc/job.py`, "No console window from a parent without a console"); for a task that runs as the signed-in user, that window is on the desktop. For no window, the task's program is `pythonw.exe` and its first argument the carrier, `tools/no_window.py`:

```powershell
$py = python -c "import os, sys; print(os.path.join(sys.base_prefix, 'pythonw.exe'))"
if (-not $py -or $py -match '\\WindowsApps\\' -or -not (Test-Path -LiteralPath $py)) { throw "no pythonw.exe outside WindowsApps: $py" }
Register-ScheduledTask -TaskName '<task name>' -Trigger (New-ScheduledTaskTrigger -Daily -At <HH:mm>) -Action (New-ScheduledTaskAction -Execute $py -Argument '"<kit>\tools\no_window.py" python "<kit>\tools\daily_full.py" -C "<main checkout>"' -WorkingDirectory '<main checkout>') -Settings (New-ScheduledTaskSettingsSet -StartWhenAvailable -Priority 7) -User $env:USERNAME -RunLevel Limited
```

`-Priority 7` is BELOW_NORMAL, Task Scheduler's own default, stated so it is a choice and not an accident: every process the run starts inherits it, and since the lock's pinned slots keep other lock runs off its cores, it yields only to unpinned work on those cores.

A task that is already registered keeps its trigger and settings and gets only the new action:

```powershell
$py = python -c "import os, sys; print(os.path.join(sys.base_prefix, 'pythonw.exe'))"
if (-not $py -or $py -match '\\WindowsApps\\' -or -not (Test-Path -LiteralPath $py)) { throw "no pythonw.exe outside WindowsApps: $py" }
Set-ScheduledTask -TaskName '<task name>' -Action (New-ScheduledTaskAction -Execute $py -Argument '"<kit>\tools\no_window.py" python "<kit>\tools\daily_full.py" -C "<main checkout>"' -WorkingDirectory '<main checkout>')
```

- `tools/no_window.py PROGRAM [ARGS...]` starts PROGRAM, waits for it and exits with its exit code (`kitlib.proc.spawn.carry`), whole: a 32-bit code above 0x7FFFFFFF, as a crash gives (0xC0000005), is passed on as the negative number with the same bits (`kitlib.proc.spawn.exit_code`), so whoever started the carrier reads the same eight hex digits (`tests/proc/test_no_window.py` `CarrierTest` measures that with a real `pythonw.exe`; not measured in Task Scheduler itself). The task's last result is therefore `daily_full.py`'s. Its own exit codes: 2 when no PROGRAM is named, 127 when PROGRAM cannot be started. With no PROGRAM it prints `USAGE: pythonw no_window.py PROGRAM [ARGS...]` on stderr only when its starter gave it one; a scheduled task gives none, so it prints nothing there. So that a failed start is not silent, an exit of 127 and an exception out of the carry each append one JSON line to `kit-console-incidents.log` in the kit's work temp folder (`kitlib.proc.console.note_carrier_failure`: `time` (UTC), `how` `carrier-fail`, `pid`, `exe` (PROGRAM's file name, never its arguments), `why` (the exit code, or an exception's type only); `KIT_CONSOLE_INCIDENT_LOG` names another file, which the tests use). With no work temp folder, or an unwritable log, there is no line and the exit code is unchanged. A PROGRAM that itself exits 127 gets the line too.
- PROGRAM's `TEMP` and `TMP` are the agents' temp folder when the carrier's environment names one in `AGENT_TEMP` (`kitlib.proc.spawn.agent_temp_env`): a task inherits the user environment, whose `TEMP` is on the system drive, and so does a detached landing or lock run (`kitlib.lock.detach`, started through the carrier by `kitlib.landing.submit` and the machine lock). The folder is made when missing. When `AGENT_TEMP` is unset, empty or not an absolute path, or the folder cannot be made, PROGRAM gets the environment unchanged; the carrier's own environment is never changed. A task registered from an older kit folder runs that folder's carrier until it is registered again. Tests: `tests/proc/test_no_window.py` `AgentTempEnvTest`.
- `python` as PROGRAM is the `python.exe` in the folder of the `pythonw.exe` that runs the carrier; any other PROGRAM is started as named.
- `pythonw.exe` has no console, so the carrier starts PROGRAM with `CREATE_NO_WINDOW`: a console with no window. Everything PROGRAM starts in turn shares that console, so the whole run opens none. Run from a console (`python tools/no_window.py ...`) it adds nothing and PROGRAM shares that console.
- `$py` is the `pythonw.exe` of the base install of the `python` the line runs (`sys.base_prefix`), never a path lookup: `Get-Command pythonw` gives the Microsoft Store or Python install manager alias under `WindowsApps` when that folder is first on `PATH`, and a task must not run that. The second line throws, so nothing is registered, when `$py` is empty, is under `WindowsApps` or is not a file. The kit's own task lines do the same in Python (`kitlib/schedtask/pythonw.py`, used by `kitlib/worktree/task.py` and `kitlib/hubsite/autostart.py`).
- The kit's own scheduled tasks use the same carrier: the worktree sweep (docs/worktree-remove.md "The scheduled task"), the agent temp sweep and the procwatch task (docs/machine-setup.md "Extras") and the launcher's sign-in task (docs/launcher.md "Autostart").

Every start in the kit's own code follows one rule, so a kit program run with no console (a hook under `pythonw.exe`, a task without the carrier) opens no window for what it starts: it goes through `kitlib.proc.spawn` (`run`, `call`, `popen`) or `kitlib.proc.job` `Job.start`, which add `CREATE_NO_WINDOW` only when the process has no console and the caller chose no console of its own, or it passes `creationflags=` itself. `tests/proc/test_spawn_sites.py` reads the source and fails on a start that does neither and has no row, with its reason, in that test's `EXEMPT` table.

The backstop for every other start in a process that has imported `kitlib` (a bare `subprocess` call, a `multiprocessing` child, a test): `import kitlib` installs `kitlib.proc.console`'s hook on `_winapi.CreateProcess`, which `subprocess` and `multiprocessing` both start through. The first start whose flags make no console choice, in a process with no console, first gives the process a console with no window (`AllocConsoleWithOptions` with its no-window mode; where Windows does not export it, attach to the console of a helper started with `CREATE_NO_WINDOW`). That child and every later one share it, so none opens a window. When no console can be had, each such start gets `CREATE_NO_WINDOW` instead. A start that names a console choice is passed on as it is. The import loads no `ctypes`. Each console it makes is logged as one JSON line (time, how, pid, exe, argv, the child's command line, the parent's pid and exe) in `kit-console-incidents.log` in the kit temp folder (docs/test-tools.md "Temp folders"; the OS temp folder for a process that never loaded `kitlib.config.user`), so a kit process that ran with no console can be found; the command lines are masked and shortened by `kitlib.proc.console.redact_command` (the program and its first six words, each cut to 120 characters, secrets masked; the rules are in that module), and a log that cannot be written never stops the start. `tests/__init__.py` imports `kitlib` first, so every test process has the hook. A console with no window takes no typed Ctrl+C, and no kit code sends one, but a child on it could, and would end a `pythonw.exe` process given a console this way at once (exit `0xC000013A`); so the hook also registers a console control handler that takes Ctrl+C and Ctrl+Break for that process only. Its children on the console get them as before.

Tests: `tests/proc/test_spawn.py`, `tests/proc/test_no_window.py` (real `pythonw.exe` runs), `tests/proc/test_spawn_sites.py` and `tests/proc/test_console.py` (the hook).

Not ported: per-piece red mapping and the hold after two reds, a custom step list, deferred steps, and owner-reservation reads beyond the lock's own exit 11. Tests: `tests/dailyfull`.

## Open

- Each repo runs redfirst.py and daily_full.py from the kit with `-C`. redfirst runs without `"redfirst".runners` in that repo's `.kit.json` (the defaults: docs/redfirst.md); written runners replace the defaults. daily_full needs `"daily_full".enabled` true plus a schedule the owner registers; the kit registers none. Repo-local copies retire only once the gaps in "Not ported" are decided.
- Kit self tests: `tools/kit_tests.py --select` and `--jobs` (docs/test-tools.md "kit_tests") install nothing; kit briefs book `--kind test --cores 2` for kit suites, and kit landings gate with `--select`. For the daily full run, add `full_cmd` (running `--full`) to the kit-suite gate step and enable `daily_full` in `.kit.json`.
