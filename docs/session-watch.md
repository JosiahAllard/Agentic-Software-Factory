# Session watch

The hub server's `session-watch` job (`kitlib/hubjobs/session_watch.py`) is the machine's one session watcher. Every 60 seconds it polls the session checks, `kitlib.pmwatch` `Watcher`, on the code the hub loaded, and pushes their events to the PM, at most one job push per run (docs/hub-push.md "Timed jobs"): BGFAIL (a background lock run failed), LOCKNOTICE, USAGE and RESET, IDLE and STOPPED, REMOTE, LIMIT, and ERROR (a check that failed three times in a row). Each check keeps its own timer inside the Watcher. The event lines are free text, so they never go in a push: the job's note (GET health `jobs.session-watch.note`) lists the last 20 it pushed, with their times. The plugin export and the hub's own stale code are other pushes, `job plugin-refresh behind` and `job hub stale-code` (docs/hub-push.md "Timed jobs"). The Claude-only parts (`~/.claude*/projects` transcripts, the `custom-title` record, the `~/.claude/machine-lock/alerts` default) live in `hosts/claude/adapter/claude_host.py`, the seam the host seam (ARCHITECTURE "Hosts") lifts out; the job finds them through the default host's adapter (`session_watch.host_module`), and a host without them runs no job. The state keys (`usage`, `bg_alerts`, `lock_notices`, `idle`, `idle_nolog`, `rc_lost`, `limit_stalled`) live in `kitlib.pmwatch`.

The job's state is its own file, `<state_file>.hub.json`. It is loaded at the first run and replaced whole after every poll. A fresh file is a silent baseline: sessions already quiet and alerts already there are recorded, not reported (REMOTE and LIMIT keep no baseline). A hub restart reads the file back, so nothing is reported twice. The state is written after the push, so a write that fails never swallows the run's events. A check that raises is the Watcher's own failure (ERROR on its third in a row). A failure outside the checks (the config, building or starting the Watcher, the state write) is the job's: health counts it, and its third in a row pushes `failing` (kitlib.hubsite.jobs).

The PM learns whether the job is watching from two places. The hub push worker pushes `watcher down` once when a job it saw healthy stops being healthy (docs/hub-push.md "Push notifications"). The PM session-start hub line says `session watch up`, `starting`, `down` or `none` (docs/pm-start.md, the hub block). Both use one rule, `kitlib.pmwatch` `session_job_healthy`: the job's health block shows fewer than 3 failures in a row (`SESSION_JOB_FAILS`) and a success (`ok_at`) at most 300 s old (`SESSION_JOB_STALE_S`). A job that only skips (no `sessions_file`) has no success, so it is never healthy.

## Stopped sessions

A session that `launch.py stop` ended with no successor reads `STOPPED <name> at <iso>`, once per stop, and never `IDLE` (a stopped session keeps its `sessions.json` entry, so the idle check would otherwise report it as a quiet one). The job reads the launcher's `stop.log` in the folder of the sessions file (`kitlib.pmwatch` `stop_log_reader`; the line `kitlib.launcher.stop` writes, `successor '-'`). The newest stop of the name counts, and only while it is not older than the session's newest transcript activity: activity after the stop means the session was started again, and a quiet one then reads `IDLE` as before. A stop with a successor, a missing `stop.log` and a stop of another name leave the idle check as it was. The first run records a stopped session in the `idle` baseline as `[time, "stopped"]`, silently. Code: `kitlib.pmwatch` `idle_events`, `idle_baseline`.

## Remote Control link

A running session can lose its Remote Control link (a network outage) and go on working locally: nothing in it says so, and the owner, who is remote, loses it from the web app. The `REMOTE` check reads Claude's session registry, `<config folder>/sessions/<pid>.json` (the folder `kitlib.launcher.pipes` reads), whose `bridgeSessionId` holds the Remote Control session id and is null while the link is down. It watches the names in `sessions.json` (as the idle check does) and the PM's own, `pm-session` (`kitlib.launcher.stop.PM_RC_NAME`). For each name it takes the newest record whose pid runs with the recorded creation time. It gives `REMOTE <name> link lost: the session runs, its Remote Control link is down (pid N)` once per episode when that record's `bridgeSessionId` is null, the session started more than 3 minutes ago (`RC_GRACE_S`: a new session is null until it connects), and the process was started with `--remote-control` under that name (a `--no-remote-control` session has no link to lose; the process list is read only when some session looks unlinked). `REMOTE <name> link back` follows once when the field holds an id again. A record without the field (an older CLI) and a session inside the grace period leave the state as it was; a session that is gone, or now runs as another process (stopped and started again under the same name), drops out, so the new one starts clean. A record whose name is not text is skipped. Unlike the idle check it keeps no baseline: a link already down when the job first runs is reported then. State key `rc_lost`: one `<name> <pid> <creation time>` entry per session reported lost. The check runs on the idle cadence (the Watcher's `idle_poll`, 300 seconds). The PM tells the owner through the hub; the job posts no question itself.

Known limit: the CLI rewrites the record when the session's status changes, so a null is fresh, but an id can be stale. A quiet session that has written nothing since its link dropped still shows the old id, so it is reported late, when it next writes its record, or not at all while it stays quiet. A busy session, and the PM, are reported within one pass of their next write. Inferred, not observed: a session whose Remote Control the owner turned off from inside it (`/remote-control`) most likely also reads null and is reported as `link lost`; the field does not say why the link is down. Code: `kitlib.pmwatch` `rc_events`, `rc_check`; the reader `hosts/claude/adapter/claude_host.py` `rc_records`. Tests: tests/pmwatch/test_rc.py.

## Weekly RESET

`RESET account <n>` needs a weekly drop of 20 or more points to hold for two readings in a row: the first low reading is held for one poll (`kitlib.pmwatch` `merge_usage` keeps the old week and records `drop`), so one stray low reading between two high ones raises nothing. The five-hour figure is read only when the host gives one (it may be null).

## Usage-limit stall

A session that reaches its account's weekly limit stops with its process still running: it looks like an idle one. `LIMIT <name> account <n> stalled at the weekly limit until <iso> (pid <p>)` tells the two apart, once per stall. A session is stalled when all three hold:

- Its process is live: the newest registry record of the name whose pid runs with the recorded creation time, as in "Remote Control link". The names are the same too: sessions.json's and the PM's.
- Its account's stored reading is at the limit: `seven_day` at 100%, or at 99% and stale (`kitlib.pmwatch` `at_limit`; a reading refreshes only while a session works, so it can stop short of 100). The registry is one real folder the accounts share, so it says nothing of the account: the account is the one whose `launcher.accounts` folder holds the session's transcript (`account_folders`), the copy written last if several do. A session whose transcript sits in no account's folder, such as an org's, has no reading and no LIMIT.
- The newest thing the session did is the CLI's usage-limit API error, and its reset still lies ahead.

The reader goes by the entry's structured fields, never its display text: `isApiErrorMessage` true, `apiError` `usage_limit_reached`, and `rateLimitType` `seven_day` in `apiErrorParams.rate_limit_info` (else `quotaLimits`), with `resetsAt` from the same place. `apiErrorStatus` is not asked for: a subagent's entry has none. The tests' fixture, tests/pmwatch/usage_limit_entry.jsonl, is two real entries, one of each kind. Only the weekly window counts (the owner's rule), so any other `rateLimitType`, an unknown one included, reads as no stall. No real five-hour entry has been seen, so its value is not known.

A subagent's entries live in its own file, `<id>/subagents/agent-<agent id>.jsonl`, not in the main transcript, so a main session waiting on a stalled subagent shows nothing in its own file. Such a session counts as stalled. The reader takes the newest conversation entry (type `user` or `assistant`) of the main transcript and of the subagent file written last, and the later of the two by timestamp decides, the main one on a tie. So an older limit entry followed by anything newer, in the main transcript or another subagent, is no stall: the session recovered or moved on. A `resetsAt` in the past is no stall either. Records of other types after the entry (a title, say) are passed over. Inferred, not observed: which of them the CLI writes after a limit entry. If either file cannot be told, because a tail line does not parse or the newest line is longer than the tail, the whole reading is no stall until the next pass: the other file does not decide alone.

The check runs on the idle cadence and reads no registry or transcript unless some account is at the limit; then it reads the transcript directly, through the record's `weekly_stop`, only the last 64 KB of each file (`TAIL_BYTES`). Like `REMOTE` it keeps no baseline: a session stalled when the job first runs is reported then. State key `limit_stalled`: one `<name> <pid> <creation time> <reset>` entry per session reported, dropped when it no longer reads stalled, so a later stall fires again. LIMIT can lag the stall by more than an hour. The usage reading can be one `usage_poll` old (600 seconds), and an account whose reading stopped at 99% and still reads fresh waits for the reading to turn stale (`STALE_MINUTES`, 60). No early trigger on the burn slope is built: the owner keeps it off until the slope is measured.

`rc_check` hands the check to the `Watcher` as its `limit` attribute, so the job runs it beside REMOTE. Code: `kitlib.pmwatch` `at_limit`, `limit_events`, `limit_check`, `account_folders`, `Watcher`; the readers `hosts/claude/adapter/claude_host.py` `newest_entry`, `weekly_reset`, `weekly_stop`, `rc_records`. Tests: tests/pmwatch/test_limit.py.

## Config

The machine config (docs/kit-json.md "Machine config keys"), key `pm_watch`. The key keeps its name from the retired standalone watcher:

```json
{"pm_watch": {
  "sessions_file": "<launcher state_dir>/sessions.json",
  "state_file": "<local-app-data>/pm_watch/state.json",
  "alerts_dir": "<home>/.claude/machine-lock/alerts"
}}
```

`<home>` and `<local-app-data>` stand for absolute paths: the user's home and `%LOCALAPPDATA%`.

With no `sessions_file`, every run is a skip (`pm_watch.sessions_file is not set: nothing to watch`), so the job is never healthy. Usage is read in-process by `kitlib.pmwatch.usage` from `kitlib.launcher.usage` (`launch.py usage`, docs/launcher.md "Usage") with the machine config's `launcher` settings. Without a `launcher` key (`kitlib.pmwatch.launcher_configured`), the job reads no usage and gives no USAGE, RESET or LIMIT. `state_file` defaults to `%LOCALAPPDATA%\pm_watch\state.json` (`kitlib.pmwatch.default_state_file`); the job writes `<state_file>.hub.json` beside it. `alerts_dir` defaults to the host's alerts folder. The lock notices come from `machine_lock.notice.dir` (`kitlib.pmwatch.configured_notice_dir`). A config the home fence or the location check refuses fails the run (docs/kit-json.md "Moving the machine config folder").

`Watcher` calls `kitlib.pmwatch` `preload` when it is built. That imports the modules the checks would otherwise load on their first pass (`kitlib.launcher.settings`, `kitlib.launcher.usage`, `kitlib.launcher.pipes`, `kitlib.launcher.stop`, `kitlib.proc.process`, and the host's own `PRELOAD`), so a landing that writes the checkout cannot give the running job a mix of old and new code. New watcher code runs only after a hub restart, and the hub's stale-code push says when one is due (docs/hub-serving.md "Stale code").

## Limits

- A first run that hangs shows as `starting`. The pm-start line says `session watch starting (no run yet)` while the job's block shows no finished run and no failure, and it does not warn. The push worker never pushes `watcher down` for a job it has not seen healthy. GET health gives no server uptime, so neither can bound that window. A job whose first run never ends stays `starting` until the hub restarts. The job's `running` field and its `last_at` in health show it.
- While the hub is down, nothing watches. On restart the job reads its saved state, so an event that happened in the gap is reported at the first run after it, not lost. A stall or link loss that ended inside the gap is not reported.
- The Remote Control field and the usage-limit readers have the known limits given in their sections above.
