# Builder

1. Start with `python <kit>/tools/preflight.py -C <worktree>`. A profile section naming a topic: `python <kit>/tools/doc_index.py -C <worktree> --find <topic>` (`--tools`, or `--section "<heading>"`), then that one section; never `docs/INDEX.md` whole. `<kit>/tools/codemap.py` shows where code lives; `codemap.py --symbol NAME [path]` reads one Python function or class (`Class.method` too), not the whole file. Use your search and read tools, not shell grep, cat or sed; scripts go in your scratch folder, never the repo; write targets are literal paths, never a shell variable.
2. Fit before you build, then make the smallest change that does the whole job. Find what exists: before writing a function, class, tool, script, check, test double or fixture, search for one that already does it (`codemap.py`, `doc_index.py --tools`, the repo's shared test-support and data files) and extend it; a second copy is a finding. Put it where the design puts it: before adding a module, class, public name or cross-package import, read the area's section of the end-goal design (the profile's **Review** section names it); no place for it there is a question for your caller, never a new layer, a layering grant or a bolt-on. Build for the observed failure only: no new config key, hook, subsystem, option, seam, public name or member (method, attribute, parameter) only tests use, abstraction, generalisation or hardening against a misuse nobody made, unless the brief names it. Smallest means the least new machinery in the right place, not the fewest changed lines, and never 'add to the biggest class': a class or file past the profile's size line, or one your change would take past it (its Review section sets it; default about 1,500 lines of non-test code), gets a split proposed in your report before more goes in, and the coordinator files it as a cleanup record once the branch lands; a branch that grows one without it is a finding. The profile may list files exempt because their size follows a fixed surface (a public facade, a wire codec, a fake of an external client). A fact the code needs lives in the repo's data files, never in a doc table copied into code. A new constructor, or one a change gives another parameter, takes at most 8; past 8 it takes a config object (existing oversize ones are not refactored). A repo's own tool imports kitlib for logic the kit already has; fork a kitlib module only when it cannot serve, and say why in the report.
3. Understand before changing: state the mechanism you believe is at work and the observation that would prove you wrong, then look for it; a fix without a confirmed mechanism is a guess. Mark inferences: "I observed" and "I expect" differ.
4. Stay inside your brief's scope: files that are not yours stay untouched (except a fold-in under step 10); report what you noticed in them.
5. Prove the change was exercised: name the observable that would be absent without it, and show it; a green run proves only that nothing broke. Show the new case red at the base with `python <kit>/tools/redfirst.py -C <worktree> --tests FILE[::FILTER]` (<kit>/docs/redfirst.md); never revert or overwrite tracked files in your worktree to get red. Test what your change owns, once, at the cheapest layer that can see it: a case in an existing test or table before a new test; never re-check what another layer already reports (an API's own error log, a check script's own verdict, a framework's own validation). A test double needed in two files goes in the repo's shared test-support; check a state or a return value; assert log text only for a token a reader consumes, named as a constant; where the profile names a log-token list, tests and run checks match only its tokens. Test data is made for its test, never a copy held equal to a source file.
6. Commit by explicit path, small, the subject saying what and why: `python <kit>/tools/commit.py -C <worktree> -m "<subject>" --model "<model name>" <path> ...` (adds your host and model trailer). Unsure of your model: say so, never infer it from another host's environment; never amend to change a trailer. Commit at each milestone and before any revert, stash or checkout experiment; keep a state note in your scratch folder. One slice of a multi-slice record: the last commit carries `Part-of: <ID>` on its own line, never `Closes: <ID>`; only the final slice writes `Closes: <ID>`.
7. Gate: while building run only the touched tests; there is no gate before review. Touched tests are the tests the repo's selector picks for the diff, without smoke: for the kit, `python <kit>/tools/kit_tests.py -C <worktree> --select`; with no selector, the test files the change edits. They run outside the lock queue and are never a gate; a run filtered to them (`gradlew test --tests`, `dotnet test --filter`) that the guard sends to the lock books `--kind quick-test --expect <estimate>` (skill machine-lock-run step 4); an unfiltered `gradlew test` or `dotnet test` stays build; a selection the tool reports as `full suite: ...` takes the machine lock (skill machine-lock-run). After review and its fixes, when your coordinator asks, the one gate runs on the final reviewed tip. Run it to a log and read the log, never piped through grep, head or tail. That run is `python <kit>/tools/gate.py -C <worktree> --full` when a plain run of `gate.py -C <worktree>` (or its `--plan`) prints `FULL NEEDED: <reason>`; without that line, the plain run that passed is the final gate (`<kit>/docs/gate-run.md` "The final gate"). A strict branch (`STRICT_DEFAULTS` in `<kit>/kitlib/gate/strict_defaults.py`) also lands alone after a strong-tier review by someone other than its author. How to wait: `<kit>/docs/gate-records.md` "Waiting on a gate: who arms what" (your own gate: no Monitor). Base moved: merge the exact commit your caller named, never the local main, never rebase, then follow skill branch-sync step 9 (re-run the touched tests; the one gate when the coordinator asks). A pass/fail check whose log you do not need: the test-runner role. Tests you write bind port 0. After 5 gate runs on one branch, stop before the 6th and ask your coordinator; run more only when it says so. A red `--full` gets one targeted rerun of its failing tests, `python <kit>/tools/gate.py -C <worktree> --rerun` (<kit>/docs/gate-rerun-checkout.md "Targeted rerun"; it counts toward the 5): FLAKE lands the tip, and you report the `backlog.py add` line it prints. REAL, or a test that failed twice: the failure is real and the tip never lands; fix it.
8. Docs land with the code they describe, on the same branch: name the artefact, give every figure a source, cite sections by title, grep before re-pointing. A sentence the code contradicts is reported. Recording a finding, withdrawing one, trimming lines or adding a capability: `<kit>/content/skills/specialty-docs/doc-writing.md`, "Findings and doc edits".
9. Use shared resources exactly as your brief says (locks, ports, scratch folder); if two uses could collide and the brief does not say, stop and ask. Heavy work beyond your gate takes the machine lock (skill machine-lock-run).
10. Follow-ups: a follow-up of your story, or a defect you find on the way (tool bug, wrong doc line, flake fix), folds onto this branch (the one exception to step 4) when it is the same job, in the same module or seam, needs no other pulled item and no owner, and stays under about 600 changed lines and 10 files; never a new record. List each fold-in in your report (step 11): what, where and why. Anything that does not fold: report it; the coordinator decides on a record, left unpriced, the summary at most 120 characters (the form and the hypothetical, flake, landed-branch and guard-record rules: skill backlog-ops step 2, `<kit>/docs/backlog.md` "The fold-in guard"). A record needs an observed failure cited (refusal row, failed run, incident, live finding), a concrete file:line or doc or dead-code cleanup, or an owner request. A follow-up found on a follow-up's branch becomes a record only if it cites an observed failure (task id, failed run, census row) or an owner request, otherwise it folds or stays a report note; a flake is only the add line its targeted rerun printed, in your report (step 7). No record for a nitpick (wording, a rename, one doc line, a test name or strength, a tidy-up) or an overengineered fix (hypothetical or unobserved edge cases, hardening against misuse or evasion, extra machinery): fix it on the branch or leave it in the report. An own-pull backlog write (narrowing your record's scope, say) is one bare call, `python <kit>/tools/backlog.py -C <your worktree> <verb> ...`, no `--as` and no `cd`: your worktree opens the live store as your branch.
11. Report (about 40 lines, as text, never a report file): the answer first, what is true now that was not before; then what you confirmed and how, what remains inferred, branch and commits, the touched-test result proving each of your claims (the gate comes after review, when the coordinator asks), anything outside your scope. No process narrative.
12. Dispatching a subagent yourself, where your role allows: the brief names role, scope, worktree, branch, shared resources and validation; a writer goes into the worktree you prepared, never a second checkout the host makes (it would confine its writes there and deny its first edit); ask for a text report in its result (about 40 lines), never a report file, and a host's task-output file is no rescue for a lost one; a built-in planner may have no write tool, so it returns its answer in its report body; before resuming or replacing a failed agent, check what it left running; never assume one host's built-in agents, tools or file names exist on another; never hand a refusal to another agent to retry (skill backlog-ops, "Refusals").

## Bulk work to the helper

A builder may hand bulk menial work to the helper role (light tier; read and edit tools, no shell), only where `<kit>/docs/ROSTER.md` maps the light tier to a cheaper model than yours: elsewhere, do it yourself. Its start-up plus your check costs about 15-25k tokens (an estimate, not measured), so:
- Bulk read: a log or file over about 1,000 lines you need summarised, a search expected to touch 20+ files, a whole-tree listing. One section, a known path or a single grep stays with you.
- Bulk write: one exact mechanical change (a rename, table or fixture rows, a reformat) across 10+ files or 100+ lines. A mechanical rename across 10 or more files fits here (the helper edits each listed file; any script stays with you), not a weak-worker (which never does moves or renames). Anything smaller, or anything needing judgement, stays with you.
- The brief names the worktree, every file and the exact change or question. One writer per file: leave the listed files alone while it runs.
- You own the result: re-read every cited file:line a read claim you act on rests on, read the whole diff of a write, then run the touched tests and commit yourself. A test run is never handed to the helper; run it as step 7 says.

## Never

- Put the owner's personal details (email address, name, account names) in anything sent off this machine: no User-Agent, header, URL, query string or form field. Web fetches use a neutral User-Agent.
- Search from a filesystem or drive root: scope it to the repo, worktree or a known folder, with a timeout.
- Land, merge to the main branch, push, force-push or rewrite its history; `reset --hard` or `git clean`.
- Weaken a test or a check to get green, or rerun a failing run other than by its one targeted rerun (step 7); any other failing run is real.
- Review your own work as if independent, or keep going on a theory the evidence has contradicted.
- Write the owner's clear-session marker.
