# gate.py: landing and the landing queue

Part of docs/gate.md (the index); the sections below are moved there unchanged.

## Landing

kitlib/gate/land.py runs from the main checkout, on main, and merges and gates in a landing tree of its own (step 5): the main checkout is never merged into, reset or gated. In this order:

1. **Usage.** Every hash is a full hash, one `--expect-tip` per branch, each branch and tip named once; `--expect-main` is optional. The config is read at the main checkout's HEAD.
2. **Refusals.** It refuses when the checkout is not main, HEAD is not on main, a branch is main or missing, or a batch has more branches than `"landing".batch_max`; never for the tests a batch's branches run (Batch, "Which branches batch").
3. **Turn, fetch and lock.** Before it fetches or merges anything, the landing books its one slot in the machine lock (`Lander.book_turn`): `book(<"gate".kind>, <repo>, <branch[+branch...]>, gate=True, resource="landing:<git common dir>", priority="land", wait_s=<--wait>, no_wait=<--wait is 0>, store=...)` (kitlib/lock/run.py; docs/lock-api.md). That booking is its place in the landing queue (The landing queue), and the merged gate (step 6) runs in it and books nothing more. Just before it books, the landing chooses where the merged gate runs (`Lander.plan_route`, `kitlib.loadnode.landroute.plan`) and says `gating on load node <n>: <why>` or `gating here: <why>`, or nothing when the choice is quiet (a kit checkout, no registry, no node opted in). Routed to a load node, it books with `cores=1`: the landing's own work, while the node runs the gate (docs/load-nodes.md "A landing's merged gate on a node"). Not given within `--wait` seconds: NOT RUN with the lock's code (docs/gate-run.md "Exit codes"), nothing changed. At its turn it fetches `<remote>`, then takes the landing lock file (kitlib/records/landing.py) with what is left of `--wait`, saying `waiting up to <s> s for the landing lock` once (`Lander.take`); not had in time is BUSY. Branch gates never take the lock file, and never book with that resource.
4. **Follow and locked checks.** It fetches again, under the lock. HEAD must still be on main (`Lander.locked_checks`: the turn can come long after step 2), or it is REFUSED with `the main checkout is on <branch>, not <main>, at the landing's turn`. The landing's base is `<remote>/<main>` as fetched, at its turn (`Lander.onto_origin`): a local main only behind it, with nothing unpushed, is fast-forwarded first (`git merge --ff-only`, only with HEAD on main, a clean checkout and no merge in progress), said as `fast-forwarded <main> from <old> to <remote>/<main> <new>`. This fast-forward stays with the landing tree: it runs only here, before the merge, and only moves a clean main checkout on main that is behind, so the checkout starts at the base the landing merges onto; the merge itself is never made there (step 5). A local main with commits the remote lacks (`<main> is at <sha>, with commits <remote>/<main> (<sha>) does not have: push them or set them aside by hand; ...`), or one the fast-forward cannot move, is REFUSED. When the base is not the commit the config was read at, the config is read again at the base (`Lander.follow`): one naming another main branch or remote, or one that no longer takes this landing (its batch size), is REFUSED; otherwise the landing tree, the merged gate, the hook module and the records all use the base and its config. When `--expect-main` was given and is not the base, it says `main moved on from <expect-main> to <base>; merging onto <base>`, and never refuses for that. Then the checks: each tip equals its `--expect-tip`; the main checkout is clean; the repository's stash stack is empty (docs/gate-rerun-checkout.md "The stash guard"); no merge is in progress; no branch is already merged; in a batch, no tip contains another; for every owner-only path that landing the branch would change, every branch commit that changes it is authored by the owner ("Owner-only commits" in docs/guard.md); and, for a `ref` or `branch` backlog store, no branch's history holds a root commit of the store (kitlib/backlog/at_landing.py `ancestry_refusal`; a store that cannot be read refuses too); every tip has a gate-OK record of exactly that commit from a `gate.py --full` pass (`Lander.tip_gate_check`, `gate_ok.verify_full`; docs/gate-records.md "Gate-OK record"), or a verified `select` or `docs` record the base's config takes (`Lander.select_refusal`, read from the base's config only, never the tip's). Such a record counts when the paths its own diff (its `base`..tip) changes cover the landing diff (merge base with the base..tip), and either the landing diff is docs-only under the base (docs/gate-run.md "Docs-only changes") and every base `docs_only` step passed in it (pass, warn or reused), or the record is a `select` one, the base sets `"gate".smoke_steps`, every smoke step passed in it and the landing diff changes no gate config file (`.kit.json`, a section file, the hook module; `reuse.config_hits`). Under a base that sets `"landing".shared_paths`, a `select` record also counts without smoke steps, and any `select` or `docs` record is refused when the landing diff changes a shared or strict path (docs/gate-run.md "Shared paths"). Under a base with `"landing".gate_once` on (the default), a `select` record counts without smoke steps and whatever shared or strict path it changes; only the gate config check above refuses it (docs/gate-run.md "Gate once at landing"). A base that sets none of `"gate".docs_only`, `"gate".smoke_steps` and `"landing".shared_paths`, with `"landing".gate_once` off, lands only `--full` records. A tip with none of these records lands on a FLAKE targeted rerun of its latest red `--full` run (`rerun.verify_flake`; docs/gate-rerun-checkout.md "Targeted rerun"): the rerun of exactly that red run, which must be the only one, said FLAKE, passed every id the red run named in the mode it failed in and every step it never reached, and the records still match git. When the tip has rerun records and they do not land it, the refusal below adds `; its targeted rerun does not land it: <why>`. Checked first for each tip, whatever record it has: a tip with a red run of its own and a test that failed on it and failed twice on its branch (docs/gate-rerun-checkout.md "Targeted rerun", "Failed twice"), or whose rerun records or its branch's cannot be read, is REFUSED as `<branch> tip <sha> does not land: <why>` (`rerun.twice_refusal`). A miss is worded `<why>, and <what the select check found>`. Before any tip is read, a base whose `.kit.json` has a "gate" section (`detect.configured`) from which `--full` selects no step (every step is `manual`, there is none, or each is dropped by another selected step's `skip_if_selected`) is REFUSED with `the "gate" section of .kit.json at <base> leaves no step for --full to select (...); no branch can land until <main> gives the gate a step that is not manual and that no other step's skip_if_selected names` (`Lander.no_full_step`): `--full` and the merged gate select every step but the manual ones, then drop each step whose `skip_if_selected` names a selected step (kitlib/gate/steps.py `select`), so both would refuse with no gate step selected and no tip could get the record. A gate whose selected steps all `require` something missing on this machine is not refused here, since only the probe can tell: the branch's `gate.py --full` gives `REFUSED: no gate step ran` with what each step requires (docs/gate-run.md "Exit codes"). Then a default-mode run's record, a record written before the `full` key, a record of another commit (an earlier tip) or one git no longer agrees with is `<branch> tip <sha> has no full-gate OK record: <why>; gate that tip whole first: python "<gate.py>" -C "<worktree>" --full`, where `<gate.py>` is the worktree's own when the kit lands itself (its main checkout has the kit's layout, `content/roles/` and `tools/render_content.py`: `kitlib.content.oncommit.is_kit`, whether the running kit is a checkout or a plugin export; docs/gate-rerun-checkout.md "The caller's checkout") and the running kit's otherwise, and `<worktree>` the worktree that has the branch out (`Lander.full_gate_command`). When the kit lands itself and the tip's record lacks the `full` key (the record `gate_ok.verify` takes, written by a gate from before the key), the part after `<why>; ` is instead `merge <remote>/<main> (<base>) into <branch> first (...), then gate the merge whole and land that tip: python "<gate.py>" -C "<worktree>" --full` (`Lander.full_gate_advice`): the branch's own `tools/gate.py` may be from before gate-OK records had the `full` key, and such a gate.py never writes it. The record's `gate_config` is not compared with any config: a branch gate writes a record only for a clean tree, with `config_rev` the tip (`runner._gate_checkout`), so it hashes the tip's own committed config; reading that config again here would use the landing kit's defaults and schema, which differ from the branch's when a kit branch changes the gate's defaults or adds a config key; and what lands is decided by the base's config, which the merged gate (step 6) reads. And a branch that changes a strict path lands alone, with a strong-tier verdict from a reviewer who is not its author (`Lander.strict_check`; docs/gate-landing-policy.md "Strict paths"). In a batch, a branch that changes a gate config file (`.kit.json`, a section file, the hook module; `reuse.config_hits`, from its merge base with the base to its tip) is REFUSED too, as `<branch> changes the gate's config (<paths>): a branch that changes a gate config file lands alone, never in a batch` (`Lander.config_check`); alone it lands as before. Every other branch, each of a batch on its own entry, lands only with a verdict queued at its tip from a reviewer who is not its author (`Lander.verdict_check`, `Lander.review_refusal`): the Strict paths bullets on the entry, its tip, a carried entry and the author hold, each refusal worded `<branch>: <why>`, and so does the tier rule for a High-risk entry (`verdicts.tier_why`); a Low or Medium one lands on any reviewer model. Landing alone, and the tier rule whatever the risk, are the strict paths' alone. No branch prefix is exempt. Any miss is REFUSED, with nothing merged.

   The last check is the scope check (`Lander.scope_check`). Every path a branch changes, from its merge base to its tip (a rename counts as a delete and an add), must fall in the scope of a record the branch holds, matched as `kitlib.backlog.scope.members_collide` matches (whole path components, casefolded). A member `<area>/<path>` of the PM data branch's store, which repositories share, is read as `<path>` when the repository has no top-level entry named as the record's `area` at the merge base or the tip; the widening command writes a new path in that same form. Every other store's members are read as written. A branch holds a record that is `pulled` with `pulled_by` the branch, and a `pulled` record that a `Closes: <ID>` trailer in the branch's own commits names, whoever pulled it. A record closed early and so gone from the store counts only when a trailer names it, read at its last version, from before the commit that deleted it. Some paths need no record: those matching `land.SCOPE_ALWAYS` (`tests/**`, and `docs/INDEX.md`, where the doc-budget check makes every new doc add a line), and a folder store's own folder. The files `tools/render_content.py` writes are not exempt, because kitlib cannot import tools/ to learn which they are: a rendering change puts them in a record's scope. The records are read from the configured store and from the PM data branch's store (step 9). A `ref` or `branch` store is read as its remote holds it, without moving a ref. A folder store is read at the branch tip, which counts a record file the branch deleted at its last version. In a batch, each branch is checked on its own commits (`<tip> --not <base> <earlier tips>`), and its merge base is taken with the base and the batch's earlier tips. The check's lines:
   - a path outside every held scope: `<branch> changes <n> path(s) outside the scopes of the records it holds (<IDs>): <paths>; widen a record's scope first ...: <backlog.py set <ID> --scope ... command>; or land them on their own branch`. It names at most `land.SCOPE_SHOWN` paths and counts the rest. A path holding a comma or a glob character (`*?[]{}`) is compared literally, so a folder member covers it; one still outside is listed as `(no scope member can name it)`. A path the check cannot decide (a backslash, a drive letter, a `..` or empty component, `none`) is listed as `(undecidable: <why>)`. Both are left out of the command.
   - a store that cannot be read, or that holds a record it cannot read, while some path is not covered by the records it could read: `cannot read the backlog store to check <branch>'s paths against the scopes of the records it holds: <why>`. Such a store gives no records. When the records that could be read cover every path, the unread store is not mentioned.
   - a branch that holds no record, while a store that holds records was read: `NOTE: <branch> holds no pulled record; its paths were not checked against a scope`, right before the `LANDED` line. It never refuses.
   - a check that cannot finish: `the scope check of <branch> stopped (<why>)`.

   While `land.SCOPE_REFUSES` is False, as now, a miss does not stop the landing: it prints `WARNING: <why>; the landing went ahead: the scope check only warns for now (kitlib.gate.land SCOPE_REFUSES)` right after the `LANDED` line, and the exit is 0. With it True, a miss is `REFUSED: <why>; nothing was merged`. Either way, the fix is to widen the record's scope first with the `backlog.py set --scope` command the line names (`set` checks the new members against every live pull's scope), or to land those paths on a branch of their own.

   A branch that holds a narrowed record (a `narrowed:` line, docs/commit.md "A narrowed record") is refused on a miss whatever `land.SCOPE_REFUSES` says: the backstop for a commit made without commit.py. Its line adds, for each narrowed record the branch holds, `<ID> was narrowed off <original members> for <other id>`: a path given to the other record waits until it lands, then the scope is restored with the same `set` as `next`'s RESTORE line (kitlib/backlog/narrowed.py `restore_set`, which land.py `_scope_restore` calls): `backlog.py set <ID>`, one `--scope` for each original member plus each current member no original holds, then `--unset narrowed`, or a `--narrowed "<line>"` for each line that cannot be read, kept as written. A record narrowed for several other records (a split against several live pulls) gets no restore while any of them still holds its part (pulled, blocked or parked, or gone from the store with no commit closing, retiring or deleting it: `_Held.live`): its line names each one still live and points at `next`'s RESTORE line, which gives each part back once the records it was narrowed for have ended. The lines are read as `record.narrowed` reads them, with the `mixed` id grammar, since they may come from more than one store. A record none of whose `narrowed:` lines can be read is named with a restore by hand. A store holding an unreadable record still gives its readable narrowed records, and their branch's miss is refused all the same (`Lander._scope_take`); the refusal then adds that the store held a record it could not read, so a path in that record's scope may be counted outside. An unread store with no narrowed record read, or a check that stops, still only warns.
5. **Landing tree and merge.** The merge happens in the landing tree (`Lander.prepare_tree`), never in the main checkout: a detached linked worktree the kit owns at `<main checkout>/<repo.worktrees_dir>/_landing` (`land.TREE_NAME`; docs/kit-json.md), locked with the reason `kit landing tree (kitlib.gate.land)` (`land.TREE_LOCK`). The first landing makes it (`git worktree add --detach --lock`), said as `the landing tree <path>: made`. A later landing reuses it when it is clean, checked out at the base; its ignored files, such as build caches, stay. When it is gone, not clean, mid-merge, not a work tree of its own, or cannot be put at the base, it is removed (`git worktree remove --force --force`, or a prune when the folder is gone) and made again, said as `the landing tree <path> <why>: recreated` (`Lander.add_tree`). A folder at that place that git does not list as a worktree, or a listed worktree there that is not a locked detached tree with that reason, is REFUSED (`... it was left as it is: move it aside`), and so is a place that is the main checkout or holds it; nothing is merged. Then `git merge --no-ff <tip>` runs in the landing tree, for each branch in order. A conflict is aborted there (an abort that fails is a WARNING: only the tree is left dirty, and the next landing recreates it), the batch's earlier merges are dropped with the tree's state, and it gives FAILED with the verdict line `CONFLICT <branch> with main <base>: the author merges main` (the result record's `summary`): the branch's author merges main into it and the landing is submitted again. Main is never moved.
6. **Merged gate.** It gates the landing tree once in the slot of step 3 (`runner.merged_gate(..., slot=, tree=)`), adding each step's `merged_args`. It selects every step that is not manual, as `gate.py --full` does, whatever paths the merge changes (`runner._merged_gate`): each runs its `cmd`, and only a `--full` landing its `full_cmd`: a strict one, or one under `"landing".gate_once` whose merge is not docs-only (docs/gate-run.md "Gate once at landing"). A step gated on globs the branch never touched still runs, so the landing tree, which starts without the main checkout's ignored caches, gets what the author's full gate had, such as an asset import before the engine tests. The steps run in the landing tree, and a check step gets it as `ctx['root']`; the repository's name and its log folder are the main checkout's (`runner._merged_gate`). Check steps run the hook module as the base has it, read from that commit like the config (kitlib/gate/hookrev.py), so a branch is gated by main's checks, not its own. Step `cmd`s run the merged tree's files. A merge whose base..merge diff is docs-only under the base's config (docs/gate-run.md "Docs-only changes"), in a landing without `--full`, runs only the `docs_only` steps (and `setup`) and says `a docs-only merge: only the "docs_only" steps run`. A step may be reused instead of run (see docs/gate-landing-policy.md "Gate reuse"), in a one-branch landing that is not strict also from the tip's own `--full` record when the merge holds the tree it passed on (docs/gate-landing-policy.md "Gate reuse", "The same tree"). On red, or when no step ran, it is NOT LANDED (FAILED or REFUSED): the merge is dropped, nothing is pushed, and nothing is reset anywhere, since the merge was only ever in the landing tree. Files a step left there go with the tree: the next landing recreates a tree that is not clean.

   Routed to a load node (step 3), the merged gate runs there instead, as a land job (`Lander.node_gate`, `landroute.run_on_node` with `docs` set as here): a pass is green, with `ran on load node <n> as job <j>` among its lines; any other end is NOT LANDED, and so is any exception that is not `landroute.Fallback`. A merge the node started on is never gated again on main. The landing gates here instead when the tip's `--full` record has the merge's tree (`same_tree_why`: its steps are reused here, never on a node), when no node qualifies at its turn (`recheck`; another node that does takes it, said as `gating on load node <n2>: ...`), or when nothing ran on the node (`Fallback`). It says `gating here: <why>`, releases its 1-slot run first, then books the gate kind's full run as in step 3, with no wait limit (`Lander.rebook_here`): booked while the 1-slot run is still held, a kind of every slot, an owner whole hold or a gpu pool would wait on itself. The lock file stays held meanwhile (The landing queue). The lock refusing that run is NOT LANDED.

   Main moved on before the turn to a base whose config names another `"gate".kind` than step 3 booked (step 4, `Lander.follow`): on main, the landing says `the base <b> books "gate".kind <k>, not <k0> as this landing did: releasing the landing's <k0> run and booking a <k> run for the merged gate, waiting with no limit`, releases its run first, then books the base's kind at its own size, as the fallback above does and for the same reason (`Lander.rebook_kind`); the lock file stays held, and the lock refusing that run is NOT LANDED. Routed to a load node, it asks the nodes again for the base's kind's slots (`Lander.route_need`, `landroute.need_of`); a kind that cannot be sized gates here as above, and the node's gate keeps the 1-slot run booked at the old kind.
7. **Unchanged.** On green, the landing tree's HEAD must still be the merge, with no tracked change and no untracked file there, and the stash stack must still be empty (docs/gate-rerun-checkout.md "The stash guard"; `Lander.unchanged`). Otherwise nothing is recorded or pushed and the merge is dropped (FAILED, `NOT LANDED: the merged gate passed, and <why>; ...`). The commit pushed is the commit gated: what the owner does in the main checkout meanwhile (a commit, an edit, an untracked file, a push of main) reaches neither the gated tree nor the pushed commit. A `"landing".log_dir` resolves in the main checkout (`runner.log_base`), not in the landing tree, so logs there that git does not ignore do not stop the landing: they leave the main checkout not clean, and the next landing is REFUSED until they are moved (docs/gate-rerun-checkout.md "Go-live notes").
8. **Push.** It writes the merge's gate-OK record (its `mode` `docs` when the merged gate ran only the docs-only steps, else `full` or `select` as the landing's `--full` says; its `ran_on` the node, host key and job when the merged gate ran on a load node, Gate-OK record), then runs `git push <remote> <merge>:refs/heads/<main>` from the main checkout (never forced), and `git ls-remote` must show the merge (`Lander.push`). When `<remote>/<main>` moved on to a commit without the merge while the gate ran, the push is refused: `NOT LANDED: <remote>/<main> moved on to <sha> while the merged gate ran, so the push of the merge <sha> was refused (a landing never forces); nothing landed, ...: land again` (FAILED, the lock released, the branch kept). Landing again merges onto the new `<remote>/<main>` and gates that whole. When the push may have landed and git cannot tell (the push was interrupted; `ls-remote` cannot read `<remote>/<main>`; the remote's main is a commit this checkout cannot place against the merge, even after a fetch; or the push did not land while `<remote>/<main>` is still the base or absent, unless git refused it), it is STUCK (below), unless the push never connected (below). A push git refused (exit 1 with git's own ref status line on stderr, `! [remote rejected] ...` from a hook or `! [rejected] ...` such as a non-fast-forward, `kitlib.gate.land.PUSH_REFUSED`) while `ls-remote` shows `<remote>/<main>` still at the base published nothing: `NOT LANDED: the push of the merge <sha> failed (<git's error>), and <remote>/<main> is still the base <sha>; nothing landed, ...: land again once the push can go` (FAILED, the lock released, as on a red merged gate). So is a push that never connected to the remote (`land.push_never_connected`): git exited 128 and every line on its stderr is `fatal: unable to access '<url>': <curl's error>` (`land.PUSH_NEVER_CONNECTED`), which git dies with only when its first request, the ref discovery (remote-curl.c `discover_refs`), fails before any pack is sent, with curl's error one that only a connection never made gives: `Could not resolve host: <host>` (or `proxy`), `Failed to connect to <host>:<port> after <n> ms: <reason>` (curl 8; git 2.55.0.windows.5 with libcurl 8.21.0 prints it for both a refused port and a timed-out connect, `<reason>` `Could not connect to server`) or the earlier `Failed to connect to <host> port <port>[ after <n> ms]: <reason>` (`Connection refused`, `Timed out`), and `Connection timed out after <n> milliseconds` or `Resolving timed out after <n> milliseconds` (curl's connect timeout, before any request). It is `NOT LANDED: the push of the merge <sha> never connected to <remote> (<git's error>), and <remote>/<main> <what ls-remote read>; nothing landed, ...: land again once <remote> can be reached` (FAILED, the lock released, the branch kept), whatever `ls-remote` read, unreadable included (in an outage it fails the same way), unless it shows the merge or a commit holding it. Any other curl error (`Recv failure: Connection was reset`, a TLS failure, `Operation timed out`), an `RPC failed` line (the pack's request, after the discovery connected), any further line on stderr (`the remote end hung up unexpectedly`, `send-pack: unexpected disconnect while reading sideband packet`) or any other exit stays STUCK. Otherwise a push that died (exit 128), exited 1 without that line (no message, what a git ended from outside leaves, `refs.KILLED_SHAPE`, named in the STUCK line; only a stray warning; or a bare `failed to push some refs`, which git prints for any failed push), timed out or exited 0 while the remote's main is still the base stays STUCK on purpose: a connection dropped after the upload exits 128, a git killed after the upload exits 1, and the remote may still apply the update after the `ls-remote`. Once `ls-remote` shows the merge the landing stands (`Lander.phase` `pushed`): the tracking ref is set to it, and a release of the lock that fails, or an exception or Ctrl+C before the release ends, is still LANDED (exit 0) with a WARNING. Those lines name the command to break the lock when it is still held, and, for each store that takes part in step 9, the command that shows the branch's backlog records left to close (`at_landing.landable_commands`; `Lander.landed_anyway`).

   Then the main checkout's main is brought to the merge (`Lander.sync_main`): `git merge --ff-only <merge>` there, when HEAD is on main, no merge is in progress, main has no commit the merge lacks, and no local change or untracked file is on a path the merge changes (a local edit elsewhere is carried along). Otherwise nothing in the main checkout moves, and `WARNING: <branch> landed at <merge>, and the main checkout's <main> (<sha>) was not fast-forwarded to it: <why>` names what is in the way and ends with the command, `git -C "<root>" merge --ff-only <remote>/<main>`. Commits made in the main checkout are named and kept: rebase them onto `<remote>/<main>`, or set them aside, first. A main that is not checked out (HEAD elsewhere) is not moved with `git update-ref` either: it gets the same WARNING, since `merge --ff-only` in the main checkout is the only way a landing moves the local main, and the next landing is REFUSED until HEAD is back on main (step 4). The landing stands either way.
9. **Close.** After the release, every record the branch holds pulled is closed, `landed <merge>` (`at_landing.close_landed`), and so is every pulled record a `Closes: <ID>` line in the branch's commits names, whoever pulled it, read from the branch tip down to the main it was merged onto (for a batch, the previous branch's merge; `Lander.close_pulled`; docs/backlog-store.md "Lifecycle changes"). When such a record was held by a live branch that is neither main (the code repository's, in the PM data store too) nor in the batch, a WARNING says to tell that branch's builder (`at_landing._live_holder_warning`). Both happen in two stores:
   - the configured store, when it is a `ref` or `branch` store: one store commit each (`closed <ID> in the backlog store: landed <merge> (store at <sha>)`);
   - the PM data branch's store (kitlib/config/pmdata.py; docs/pm-data-branch.md), found as the worktree of the repository that has the branch `kit-pm-data.json` records checked out (`at_landing.pm_data_root`), unless it is the configured store or the main checkout itself: the record file is deleted in that worktree and the deletion committed there (`closed <ID> in the backlog store <store>: landed <merge> (committed <sha>)`); a commit that fails is a WARNING naming the `catch-up --apply` command for every path the close wrote, a commit stopped because another commit changed one of those paths on HEAD puts the close's files back and is a WARNING that ends, from the store read again (`at_landing._after_put_back`), in one of five ways: the record is still pulled by the branch (for a record a `Closes:` line names, while anyone holds it pulled, naming that holder), with the close command; the store no longer holds it, with no command; it is in another state and no longer pulled by the branch, with the `show` command; its file cannot be read as that commit left it, with the `show` command; or the store could not be read again, with the `show` command. A file it left adds the `git diff HEAD --` compare, and none gives a ready-made `catch-up --apply` command; and a commit whose index update fails is a WARNING naming the `git reset -q --` repair (kitlib/backlog/at_landing.py `_close_in`).

   A close that fails, a store that cannot be read, and an exception or Ctrl+C here, is a WARNING with the command to finish it, or to see what is left (`backlog.py landable <branch>`, one per store, `at_landing.landable_commands`); the landing stays LANDED and is never undone. A close command for the configured store names `-C "<a worktree of this repository>"` (`at_landing.WORKTREE`), never the main checkout the landing ran in, and the repository's own `tools/backlog.py` when it has one, else the kit's (`at_landing.close_command`); an owner-held record's command carries the owner's go that ends the hold (`at_landing._close_in`, as `plan_close` needs it). A command for the PM data store names that worktree.
10. **Cleanup.** Then each branch's remote branch, worktree and local branch go, unless `--keep-branch` (see docs/gate-landing-policy.md "Branch cleanup"). Its lines come before the `LANDED` line.
11. **Mirror refresh.** Last, once the machine-lock slot is released too and nothing is held, a landing that LANDED pushes the merge to the mirror of main on each load node that opted the repository in (`Lander.refresh_mirrors`, `kitlib.loadnode.mirror.refresh`; docs/load-nodes.md "The mirror of main"). It adds at most 65 seconds to the landing's return, and nothing with no node opted in. Its lines come before the `LANDED` line; a failure, an exception or Ctrl+C there is a WARNING, and the landing stays LANDED.

An exception, SystemExit or Ctrl+C under the lock (`Lander.recover`): before the merge, the lock is released (a config error is REFUSED). After the merge and before the push, a merge stopped part way is aborted in the landing tree (best effort, `Lander.half_merge`), the merge is dropped and the lock released (FAILED, `NOT LANDED: ...`); Ctrl+C is then raised again, so the exit is 130. During the push it is STUCK (exit 3), Ctrl+C included: the merge may be on the remote. After the verified push it is LANDED (step 8). A second failure while recovering leaves the lock held: STUCK.

STUCK is only a push that may have landed and cannot be told (step 8). Nothing is ever reset: the main checkout was never merged into, and a merge that did not land needs nothing undone. The lock stays held at phase `stuck` so that no landing stacks on top. STUCK prints a `left:` line (the branch HEAD is on in the main checkout, main, the remote's main as `git ls-remote` reads it, the tracking ref, tracked changes, untracked files), then numbered steps to clear it, in order. Each command is on its own line starting `    $ ` (`land.STEP_CMD`); no step says reset, and none makes a `kit-stuck` branch. The steps fit what is left (`Lander.clear_steps`):

- **Push unknown** (`ls-remote` failed): the push may have landed. When the tracking ref holds the merge, `git fetch` and `git rev-parse <remote>/<main>` come first, then the On the remote steps; when git cannot place the tracking ref against the merge, only the Remote's main not here step follows. Otherwise `git fetch` and `git rev-parse <remote>/<main>`: if that shows the merge, the landing is done (bring main to it with `git merge --ff-only <remote>/<main>`, then break the lock); if it shows the base, the push did not land and nothing is to be undone; if it shows anything else, `git branch -r --contains <merge>` says whether the merge is landed (the list names `<remote>/<main>`). A failed fetch means stop: what it shows is stale.
- **On the remote** (the remote's main is the merge or descends from it; `Lander.on_origin_steps`): the merge is landed. When the tracking ref is not the remote's main, `git fetch` comes first, since `break_lock` compares main with it. A merge that reached the remote without a passing merged gate is named, with `git revert -m 1 <merge>` to run by hand once the lock is broken (newest first in a batch), never as a `$` line. Then `git switch <main>` when HEAD is elsewhere, tracked changes and untracked files to keep or drop by hand, and `git merge --ff-only <remote>/<main>` when main is only behind it; when main has commits the remote lacks, they are named to push or set aside by hand. Commits on the remote's main beyond the merge that no merged gate saw are named (`<sha> <subject>`), with the full gate to run on main once the lock is broken.
- **Remote's main not here** (`ls-remote` read a commit this checkout lacks, or git cannot place it against the merge, so whether it holds the merge cannot be told; `Lander.check_first`): one step, `git fetch` and `git branch -r --contains <merge>`, then only the lock break. The step says in words what to do: if the fetch failed, the list is stale, so stop and do not move main; if the list names `<remote>/<main>` the merge is landed, so bring the checkout to `<remote>/<main>` by hand; if not, the merge is not on the remote and nothing is to be undone: settle the remote's main with whoever pushed it.
- **Not landed** (the remote's main is the base, or another commit that does not hold the merge): the merge did not land, and nothing is to be undone; only the lock break follows.
- Last, a `python -c` line that runs `LandingLock.break_lock` (it refuses while the holder is alive or main differs from the remote's tracking ref).

A gate-OK record is written for the merge before the push. When the push is refused (NOT LANDED) or did not land (cleared from STUCK), the record for that merge commit stays in the record folder (docs/gate-records.md "Gate-OK record", "Where the records are"). It is stale but harmless: records are keyed by commit (`gate_ok.record_path`), that commit is not on main, and a reader verifying any other commit never reads it. Only a later push of that same merge commit would find it; it can be deleted by hand (the owner's: no agent's file writes reach the record folder).

**First switch.** A repo whose base `.kit.json` still uses old key spellings (docs/kit-json.md lists the current ones) fails to load with the kit loader, and the pre-push hook, the guard's git-push-main rule, the land.py preconditions, the trailers check and review_pack's base read all refuse until main loads. The owner lands that one switch by hand: rewrite `.kit.json` to the kit spelling, check it with `python <kit>/tools/preflight.py -C <repo>` (a load error prints `preflight: refused: kit configuration: <error>` and exits 2), then push the switch commit before the kit hook is installed in that repo, or with `--no-verify` from the owner's own terminal (the guard refuses `--no-verify` pushes in agent sessions). After that, normal landings work (docs/go-live.md "Landing tool").

### Pinned tools

A landing fast-forwards the main checkout it runs from: to `<remote>/<main>` before it merges, and to the merge once it is pushed (Landing, step 8). A tool running there would import the modules it loads lazily after that against the older ones it had already loaded: a mixed generation. So `tools/land.py` and `tools/gate.py`, started from the kit's main checkout or from an export whose marker names it (the plugin's: `<kit>/tools/gate.py`; marker `checkout`, `kitlib.pluginsource` `export_checkout`, docs/plugin-source.md "Layout"), first re-run themselves from an export of the kit's remote-tracking main, `refs/remotes/<remote>/main`, with the same arguments and the same interpreter flags (`-X utf8`, `-B`, `-I`, `-W` and the rest that the private `subprocess._args_from_interpreter_flags` gives, none when Python lacks it, and `-u` when this run's stdout is write-through), and exit with its code (kitlib/gate/pin.py `run`, called before the tool's own imports):

- **Where.** `<plugin export root>/pins/<sha12>`, the export root of docs/plugin-source.md "Layout" (`plugin.export_dir`, default `%LOCALAPPDATA%\pm-kit\plugin`). The export is made once per commit by `kitlib.pluginsource` `export` (marker `made_by` `kitlib.gate.pin`), under `pins/refresh.pid`, waited for up to 60 s (`pin.LOCK_WAIT_S`).
- **Leases.** Each pinned run holds `pins/leases/<sha12>-<pid>.json` while it runs and removes it when the tool ends. Each pin, under the lock, prunes (`pin.prune`): leases whose processes are both gone, every `<sha12>` export holding the marker that no live lease holds (except the commit it runs), and every `<sha12>.tmp`. A lease file that cannot be read is removed once older than 10 s (`pluginsource.LOCK_GRACE_S`); a lease that reads but is malformed is dead (`pin._malformed`), so it never makes the pin fail open nor holds an export.
- **Environment.** The child gets `KIT_PINNED=<sha>` and `KIT_LIVE_ROOT=<the main checkout>`. Any `KIT_PINNED` value means run live, so the child, and every tool it starts, never pins again. A command the tool prints (the gate, sweep, lock-break and backlog commands) names `KIT_LIVE_ROOT`, never the export, which a later prune may remove. The gate's own `{here}` runs (`steps.KIT_TOOLS`) use the export. `gate.py`'s own-copy refusal (docs/gate-rerun-checkout.md "The caller's checkout") compares against `KIT_LIVE_ROOT`. Started from an export whose marker names the main checkout, the tool is pinned through it as from the checkout itself, so `<kit>/tools/gate.py` counts as the main checkout's own: run from a kit linked worktree with no `-C` or a relative one, it is REFUSED.
- **Runs live.** A run with `KIT_PINNED` set, a linked worktree (its `.git` is a file), an export whose marker names no main checkout, and a checkout with no remote-tracking main run the code they are in, with no line.
- **Fails open.** When the pin cannot be made (the export root refused, the tracking ref unreadable, the lock busy past its wait, the export failing, no `tools/<name>.py` in it), stderr gets `WARNING: pin: running the live checkout's code: <why>`, `KIT_PINNED=live` is set, and the tool runs from the main checkout as before. Once the child has started nothing fails open, so the tool never runs twice. Ctrl+C while pinning exits 130 with the tool not run. From just before `Popen` until the child exits, the parent ignores Ctrl+C (`pin._ignore_ctrl_c`, main thread only), so it waits for the child, exits with its code and keeps the lease until the child exits. Ctrl+C reaches the child through the shared console and stops it as it does an unpinned tool. Two limits: when the current handler cannot be read (`signal.getsignal` gives None) nothing is changed; and a Ctrl+C in the instant after the parent starts ignoring it and before the child is attached to the console is lost (press again). A shell that already ignores Ctrl+C at the console level (`SetConsoleCtrlHandler(NULL, TRUE)`, as an agent's shell does) passes it to both processes, so no Ctrl+C reaches either.
- **Identity.** Run from an export, `runner.kit_identity` (the gate-OK record's `kit`) is the marker's commit, clean. The gate cache keys on the kit's file hashes instead (`reuse.kit_identity`, Gate reuse), so an export and a checkout of the same files are one kit.

### The landing queue

A landing is ONE entry in the machine lock's queue: the booking of step 3 (`Lander.book_turn`), with `resource="landing:<git common dir>"` (`land.queue_key`) and `priority="land"` (kitlib/lock/run.py `book`; docs/lock-api.md). Every checkout of a repository makes the same key, so they share one turn: one landing of a repository holds it at a time and the others wait in the machine lock's queue, where a `land` entry goes ahead of ordinary waiting runs. Landings of different repositories share the machine's slots, not the turn. A landing never books its slot nested inside another machine-lock run: a submitted landing's environment drops `MACHINE_LOCK_RUN` (Submitting a landing).

Its kind is `land-<"gate".kind>` when kitlib/lock/kinds.json has one, else the `"gate".kind` (`Lander.land_kind`): `land-test` is 4 cores, by the owner's call without a measurement, while a branch gate's `test` stays medium. Every booking of a landing takes it (`book_turn`, `rebook_here`, `yield_turn`, `rebook_kind`), a node-routed one with `cores=1`; the node's own run stays the `"gate".kind`, and `rebook_kind` compares `"gate".kind`s, never the land kind.

The entry lives as any lock run's entry does, so a landing that dies leaves an entry the machine lock drops. The slot is given up whenever the landing ends (`Lander.run`, `Lander.drop_slot`), STUCK included: the stuck lock file keeps the next landing out. The merged gate runs in that slot (kitlib/gate/runner.py `gated(slot=)`), and as its steps finish it stops the build daemons they left (`Slot.stop_daemons`, as a gate's own release does) and ends the rest of their tree (`Slot.end_tree`), so nothing the gate started runs on through the push; the slot stays held until the landing ends. `land.py --queue` prints the lock file's holder, then the `land` entries, holding first, then waiting by ticket, each with its repo, slug, kind, run id and pid, and `; another repository` when its resource is not this repository's key; it joins nothing.

At its turn the landing takes the landing lock file (kitlib/records/landing.py). The lock file stays for what the machine lock does not hold: the stuck record, a gone holder's break, and a landing of a tool outside the machine lock (a token holder):

- **Free:** taken.
- **Held at phase `stuck`:** BUSY at once; a stuck landing is cleared by hand from its STUCK report.
- **Held by a process that is gone** (pid and start time, `LandingLock.holder_state`): when nothing is unpushed, the lock is broken (`LandingLock.break_lock`), said as `broke the landing lock of a holder that is gone ...`, and taken. When main differs from the tracking ref `<remote>/<main>`, or a merge is in progress (`LandingLock.unpushed`), it is never broken: BUSY at once, naming what is unpushed and the break command. When main is only behind the tracking ref, with nothing unpushed, BUSY says so and gives the fast-forward, `git -C <root> merge --ff-only <remote>/<main>`; the next landing then breaks the lock itself. When that holder died at phase `push` and `<remote>/<main>` has moved on from its `origin_at_take` (a lander killed after its verified push, before the main checkout's fast-forward), BUSY also says `its holder is gone after its push: ... so its push most likely landed and only the main checkout's fast-forward was skipped`, then gives the fast-forward, `Then land again`, and the break command.
- **Unreadable or of an old format** (`LandingLock.read` fails): waited for like a live holder, never broken; BUSY with phase `?` when `--wait` runs out. A taker killed between its create and its write leaves an empty lock file for good, and `LandingLock.break_lock` refuses an empty, unparseable or unreadable file even with `holder_gone=True`: delete such a file by hand, and only once `land.py --queue` shows no landing running.
- **Held by a live process, or by a token holder** (a tool outside the machine lock): waited for, up to what is left of `--wait` (`Lander.poll_s`, 5 s between looks).
- **Held by a landing waiting for this repository's turn** (a node-routed landing that fell back to main and is booking its full run again, Landing step 6: it gave the turn up and this landing got it): at each look, when the machine lock's queue holds a waiting entry with this repository's landing resource and the holder's branches, the landing says `the landing holding the landing lock (<branches>) waits in the machine lock for this repository's landing turn, ...`, releases its run and books again behind the holder with what is left of `--wait`, one cpu slot again when it is node-routed itself (`Lander.yield_turn`), then looks again after `poll_s`; the line is said once per holder. That booking not given in time is NOT RUN with the machine lock's exit code, not BUSY. A queue that cannot be read is no such holder. A landing from a kit without this waits until its `--wait` runs out, and the holder waits as long.

### Submitting a landing

kitlib/gate/submit.py. `land.py --submit` and `gate.py land --submit` check the arguments (USAGE as without `--submit`, nothing written), check the review the command names (below), refuse with nothing written (`submit.blocked`, exit 4, `REFUSED: ...; nothing was changed`) when a branch's land record is `running` in a process that lives (`result.running_state` `live`; one whose process died does not count) or already says it landed at that tip (`pass`, or an old record's `landed-ungated`, so the record is left as it is), write each branch's `running` land record (docs/gate-records.md "Result record") with one `run_id` for the batch and no `pid` yet, start the same landing again as a detached, windowless process, wait up to 15 s (`submit.CLAIM_WAIT_S`) for it to record itself (`submit.claim`), and print one `REVIEW` line for each branch with a verdict queued at the tip submitted (`submit.review_lines`; none for a branch with no entry at that tip), then the `SUBMITTED` line last, and exit 0:

```
REVIEW <branch> <tip>: <verdict> by <reviewer>/<model> (<reviewer_id>)[, carried from <sha> over <n> main merge(s)]
SUBMITTED <branch>[+<branch>...] tip <sha>[,<sha>] wait: python <kit>/tools/gate.py wait-result <branch> --tip <sha> --kind land -C <main checkout>
```

The command names the review each branch lands on, so whoever reads it (the owner, a permission check) sees the review in it: one `--reviewed-by <reviewer id>` per branch, in `--expect-tip`'s order, placed before `--submit` (nothing may follow `--submit` in the allow rule, docs/allow-rules.md), each the `reviewer_id` of the branch's verdict queued at its tip, or one of its ids when that field lists several (`submit.reviewer_ids`; case and surrounding spaces aside). `submit.named_review` checks it, with nothing written, before the running-landing check:

- A queue that cannot be found, or a branch with no usable verdict at its tip (none queued, one marked failed, one given at another tip and not carried, an entry that cannot be read), is REFUSED by name (exit 4): queue the verdict (tools/verdict.py add) first.
- A missing `--reviewed-by`, or a count other than one per branch, is USAGE (exit 2), followed by an `Instead:` line: the same command with each branch's queued reviewer id, in forward slashes with `--reviewed-by` before `--submit`, an argument holding a space double-quoted (`submit.again_line`). For a plain `tools/land.py` submit (`-C`, the branches and `--expect-tip`, with `--expect-main`, `--wait`, a one-word `--summary` and the flags) that is the allow rule's form; other forms get the normal permission prompt: `gate.py land`, which the allow rules do not cover, a `--summary` with a space (now quoted, and the rules deny quotes), `--log-dir` (denied) and a kit folder whose path holds a space (left unquoted, so that command does not run as printed). It is USAGE, not REFUSED, so a caller with the old form runs the line given.
- An id that is not the reviewer of that verdict is REFUSED (exit 4), naming the verdict on record, with no `Instead:` line: name the review the verdict records, or queue the one meant.

`--reviewed-by` without `--submit` is USAGE. The detached landing is started without it, and the foreground landing takes no review name: its own check of the queue is unchanged (Landing, step 4). A library caller of `submit.submit` that passes no `reviewed_by` skips this check.

The `REVIEW` lines only show the review on record (a carried one names the commit reviewed: Carrying a verdict forward); they decide nothing, and a queue that cannot be read gives none. The landing's own checks decide (Landing, step 4). The `SUBMITTED` line is unchanged and always last.

The wait command names the batch's last branch and tip, because the landing writes the batch's records in batch order and that record last; `<kit>` is the kit's live folder (`pluginsource.live_root`); `-C` names the main checkout of the submitter's `-C` (`repo.main_checkout_toplevel`, that `-C` itself when git cannot place it), a checkout no branch cleanup removes; each path is in double quotes when it holds a space (`submit.wait_line`). The record is in the repository's result folder (docs/gate-records.md "Result record"), so the command reads the same record from any working directory. The coordinator runs it, as printed, in the background and wakes on its exit (Waking a waiting session).

**Waiting in the same call.** `land.py ... --wait-result --submit` (`--wait-result` before `--submit`, so the allow rule takes it as it is: docs/allow-rules.md) submits as above, prints the `REVIEW` and `SUBMITTED` lines and flushes them, then follows the landing to its end (`submit.follow`). One background call then covers the submission and the wait, and wakes its caller when it exits; without it the caller makes the submit call and then a second, background call to `wait-result`. `--wait-result` without `--submit` is USAGE (2), and `gate.py land` has no such flag. A submission that does not give OK prints its lines and exits as it would without the flag, and waits for nothing. Once submitted it prints, in order:

- `WARNING: the landing process (pid <n>) had not exited 60 s after its result record; ...`, only when its process still runs 60 s (`submit.EXIT_WAIT_S`) after the batch's last record went final. After that record, the landing appends the land ledger, posts the Landing feed and prints its outcome lines. The wait never goes longer than that bound: what follows is what the output held at that point.
- The landing's own outcome lines from its output file, at most 60 (`submit.BLOCK_MAX`; a longer tail starts with a `... <n> earlier line(s)` line) (`submit.outcome_block`): every line after its last `result record:` line, such as the gate verdict and `logs:`, the `cleanup` lines, `LANDED ...` or `NOT LANDED: ...`, `closed <ID> ...`, the `WARNING`s and a `STUCK` landing's steps.
- For each branch in batch order, the two lines `wait-result` prints for it, byte for byte (`result.result_lines`). An earlier branch with no final record yet is a `WARNING` naming its `wait-result` command.

The exit code is the code in the batch's last record (0 pass, 1 fail or `error`, 3 stuck, 4 refused, 5 busy, a machine-lock code for `not-run`), not wait-result's 0 or 1.

The wait has no timeout of its own. The landing bounds it: its turn waits at most `"landing".wait_s`, then the landing runs. A record whose process died is finished `error`, as for `wait-result`.

The landing is detached, so stopping the wait stops only the wait:
- A host that kills the call (a foreground call past the host's 10-minute cap, or a closed session) leaves the landing running. The `SUBMITTED` line already printed holds the `wait-result` command to wait with again.
- Ctrl+C prints `Ctrl+C: the wait stopped; the landing goes on: <that command>` and exits 130.

Run it in the background, never in the foreground: it lasts as long as the landing.

The detached process is started as `machine_lock.py run --detach` starts its wrapper (docs/lock-api.md): `submit.command` builds `pythonw.exe` running the carrier `tools/no_window.py`, which starts the `python.exe` beside it running the submitting tool (`tools/land.py` or `tools/gate.py`) with `CREATE_NO_WINDOW` and waits for it; `submit.detach` refuses, starting nothing, when any of the three is not a file, else starts that command with `Win32_Process.Create` through PowerShell's CIM cmdlets (`kitlib/lock/detach.py`). WMI's process is outside the submitter's process tree and job, so it outlives the submitter, and `pythonw.exe` has no console, so the landing gets a console with no window. The pid `submit.detach` gives is the carrier's; the landing is the `python.exe` the carrier started (`detach.wrapper_pid`). The claim watches the landing and, when its wait ends first, writes the landing's pid into the records (the pid the landing then claims them with, `restore`); only when no landing was found does it record the carrier's. A carrier that cannot start the landing exits 127 and notes it in the kit's console incident log, and the claim then finds the carrier gone. Its environment is the submitter's, less `MACHINE_LOCK_RUN` (the landing books its own turn, never one nested in the submitter's run), with `MACHINE_LOCK_ORIGIN` set to the submitter's ancestry (the slot is booked `detached=True`, so the machine lock gives it the submitter's role), `PYTHONIOENCODING=utf-8` and `PYTHONUNBUFFERED=1` (`submit.child_env`). A tool run from a pinned export keeps `KIT_PINNED`, and `pin.lease_child` leases the export to the carrier and to the landing, one lease each (Pinned tools). It waits for its turn up to `--wait`, else `"landing".wait_s`.

Files, in the result folder (docs/gate-records.md "Result record"), named by the batch's first branch and the submission's `run_id`, so no submission overwrites another's (`submit.files`): `<stem>.<run_id>.land.submit`, the payload (each branch's run id and start time, the output file, the land records the submission replaced, and the landing `flags` a batch shares, `submit.flags_of`), and `<stem>.<run_id>.land.log`, the detached landing's output, which is each record's `log` until a merged gate names its own. Every outcome of the detached landing finishes the records with the same `run_id`: OK, FAILED, CONFLICT, REFUSED, STUCK, BUSY and NOT RUN alike, and `error` for an exception; a landing that another folded into its batch writes nothing, and the batch finishes its records (Folding queued submissions). No record is left `running` when the landing cannot go on:

- A start that fails prints `REFUSED: the landing could not be started: <why>; nothing was changed` (exit 4) and finishes the records `refused`. A Win32_Process.Create code 8 (unknown failure, which starts nothing) is asked again first, up to 3 starts 1 s apart; `<why>` names a WMI code's meaning, as in `the detached start got WMI code 8 (unknown failure) after 3 tries (exit 0)` (kitlib.lock.detach `WMI_CODES`).
- The detached landing writes its own `pid` into the records as it reads its payload (`submit.restore`). One that dies before that, within the claim wait, is finished `error` by the submitter, which prints `REFUSED: the landing process died before it started: pid <n> ended without recording itself; nothing was changed; its output: <log>` (exit 4). One still starting when the wait ends gets its `pid` written by the submitter.
- One that cannot read its payload finishes the records of the `run_id` its payload is named by `refused`, `REFUSED: cannot read the submission ...; nothing was changed`, and notes it in the log (`submit.abandon`).
- One that dies later (killed outright, a crash) leaves `running` records naming a dead process: the first `wait-result` on them finishes them `error` (Waking a waiting session).

Left open: two submissions of one branch started at the same instant can both pass `submit.blocked` before either writes its records; both landings then run in turn in the landing queue, and each branch's record is the last one written.

A later submission prunes payload and log files older than 14 days (`submit.KEEP_S`), keeping every run a land record still has running, whatever its age; a file it cannot delete stays (`submit.prune`). A pruned run's final record can name a log that is gone.

A submission taken (exit 0) is also noted in the session's coordinator event log when one is on, after its lines are printed; that changes nothing the submission says or exits with (docs/coord-state.md "Who appends").

### Batch

`land.py A B --expect-tip TA --expect-tip TB` lands A and B as one landing: each passes the locked checks, they merge in the order given (`Merge A: <summary>`, then `Merge B: <summary>` on top), the merged tree is gated once against the base (log slug `A+B`), and the last merge is pushed. A conflict on any branch aborts it and drops the earlier merges; a red gate drops them all. Main never held them: they were only in the landing tree. A branch whose tip is already inside another tip of the batch is refused: land the containing branch alone. Each branch gets its own result record (`facts['result_record']` is then a list). The verdict line names the branches joined by `, `. At most `"landing".batch_max` branches (default 5). A batch holding a branch that changes a strict path, or a gate config file, is REFUSED (docs/gate-landing-policy.md "Strict paths"; Landing, step 4). A named batch is all or nothing as above; unless `.kit.json` sets `"landing".batch_max` to 1, a submitted landing may also fold the submissions queued behind it into its batch, and then drops or gives back a folded submission without the rest (Folding queued submissions). Each branch needs its own verdict queued at its tip; the first, in the order given, without one is REFUSED by name (Landing, step 4). Submitted, the batch names one `--reviewed-by` per branch in the same order (Submitting a landing).

**Which branches batch** (an owner rule, for every repository): only branches whose landings run the same tests, or a branch whose tests sit inside those of another branch of the batch; branches whose tests are disjoint or only partly overlap land in separate batches. A batch saves time only when its branches share their tests: its merged gate runs the union of them, so a mixed batch saves nothing. What counts is what the batch's merged gate (Landing, step 6) runs, not the mode of each branch's own gate, so a branch that ended on `--full` has no place of its own. Under `"landing".gate_once` every merge that is not docs-only runs each step's `full_cmd` (docs/gate-run.md "Gate once at landing"), so any branches that may batch run the same tests, and a docs-only branch, whose own landing runs only the docs-only steps, sits inside them; docs-only branches batch with each other too. Without it each step runs its `cmd`, selecting from the base..merge diff, so compare the selection each step makes from each branch's diff (its selector's `--plan`, such as `kit_tests.py --select --plan` or `pytests.py --select --plan`), a branch that ended on `--full` for a shared path (docs/gate-run.md "Shared paths") included. The rule is the coordinator's (skill land-branch): `land.py` neither refuses nor warns on a batch whose branches' tests differ, since such a batch is still correct (each branch keeps its review and its gate, and the merged gate covers the union), and a gate-OK record names steps, not tests, so it has nothing to compare. Folding does not compare them either (Folding queued submissions, Left open).

### Folding queued submissions

A submitted landing (Submitting a landing) at its turn, its locked checks passed, folds the submissions queued behind it into its own batch, so that several branches submitted one at a time are merged and gated once (`Lander.fold_queued`, kitlib/gate/submit.py `foldable`, `take`, `give_back`, `turn`). A direct landing folds nothing, and nothing folds it. Folding is on by default (an owner ruling, which replaced the earlier off-by-default one): `"landing".batch_max` caps the batch, folds included (`Lander.fold_max`), at the value `.kit.json` writes or else the default 5, the same cap a batch named in one call has. A repository opts out with `"batch_max": 1` in `"landing"`: nothing is folded, each submission lands alone at its own turn, and no batch can be named either (before the default changed, an unset `batch_max` folded nothing but still let a named batch hold 3).

**Who folds.** A landing folds only when it was submitted with a payload that has `flags` (an older kit's has none), changes no strict path and no gate config file (docs/gate-landing-policy.md "Strict paths"; Landing, step 4), was not itself given back dropped from a batch (`fold_dropped`), and has room under `batch_max` (none at 1). A verdict's risk plays no part: a High-risk branch folds, and is folded, as any other; only a strict branch and a gate-config branch land alone (an owner ruling).

**What it folds.** Each submission in the result folder whose every land record is still `running` for its `run_id`, at the tip its payload names, folded into no landing, and whose first record has no `turn_at`, no `fold_dropped` and the live pid of its own landing (it has claimed its records), oldest first by `started_at`, then by when its payload was written. Each is folded whole or not at all, in that order, while it fits; one that does not fit is left and a smaller one after it may still fold. A submission is left, said as `not folding <branches> (run <id>): <why>`, when it was submitted with other landing flags (`--summary`, `--log-dir`, `--full`, `--fresh`, `--keep-branch`: `submit.flags_of`, `submit.same_flags`), names a branch of the batch, or fails a batch check with the batch as folded so far (`Lander.pair_checks`: Landing step 4's locked checks, the tip, verdict, strict and gate-config checks among them, and no tip inside another). A strict branch or a gate-config branch is never folded: it lands alone. Each one folded is said as `FOLDED <branches> (run <id>) into this landing: the batch is <a+b+...>`. Once any is folded, the whole batch passes the locked checks and the scope check again; when it does not, `not folding: the batch <a+b+...> does not land as one (<why>); each folded submission is given back to land at its own turn`, every fold is given back, and the landing goes on alone.

**Taking and giving back.** Taking a submission writes each of its records again with `folded_into` the landing's `run_id`, the landing's pid, ctime, base and output as `log`, the first record first; giving one back writes them again as its own (its own pid, base and output, `folded_into` cleared), the first record last. Every such write is judged under that record's lock (`result.write`'s `when`), so a record that changed meanwhile is left as it is; a submission whose records changed while they were taken is given back and said as `not folding ...: its records changed while this landing took them`. The batch's first record decides the race with the folded submission's own landing: a fold takes it only while that record has no `turn_at`, and its own landing marks `turn_at` only while the record is folded into none, so exactly one of the two wins. A submission given back whose own landing process has ended is finished REFUSED (`... was folded into the batch of the landing run <id> and given back (<why>), and its own landing process (pid <n>) has ended: submit it again; nothing was changed`).

**Dropped units.** A folded submission whose branch does not merge cleanly onto the batch before it is dropped (`dropping <branches> (run <id>) from the batch: <conflict line>`; `Lander.merge_batch`): given back with `fold_dropped` set, the landing tree put back at the base and the rest merged again. A conflict on a branch of the landing's own is the CONFLICT outcome of Landing step 5, and every fold is given back. A red merged gate of a batch holding folds (`Lander.regate_alone`) says its lines, gives every fold back dropped, says `the merged gate of the batch <a+b+...> failed: each folded submission is given back to land alone, at its own turn; gating <own branches> alone`, and merges and gates the landing's own branches again in the same slot: no bisecting. A dropped submission lands alone at its own turn and is never folded again, nor folds anything itself. Any other outcome that does not land (FAILED, REFUSED, NOT LANDED after an exception under the lock, or an exception before the merge or a Ctrl+C before the push, either raised again) gives every fold back to land at its own turn (`Lander.unfold_unlanded`), so only the landing's own records end `error`; a landing that lands, or is STUCK, keeps them, and each folded branch's final record is the batch's, with its `batch` key.

**The folded submission's own landing.** Its process checks its turn before anything else, right after USAGE (`Lander.turn_check`), and again once its booking is given (`Lander.own_turn`). Folded into a landing that has finished its records, or (its booking not given) into one that still runs, it says `FOLDED: <branches> lands in the batch of the landing run <id>; its land records say how it ended` as its outcome (exit 0) and ends, its slot released: it writes no record, ledger line or other file (its output holds the line) and changes nothing, whatever outcome it would have had otherwise (BUSY, NOT RUN, a refusal). With its booking given and the landing it was folded into still running, it says `waiting: <branches> is folded into the batch of the landing run <id>, which still runs: it lands them or gives them back; booking again a look every <poll_s> s`, releases its slot and books again, a look every poll, with what is left of `--wait`: given back, it lands at its own turn. Folded into a landing whose process died, it takes its records back and lands at its own turn. Its records are written only while they are still its own run's and folded as it last read them (`Lander.still_ours`).

**Waiting.** `--wait-result` (Waiting in the same call) on a folded submission prints `FOLDED: the landing of <branches> was folded into the batch of the landing run <id>; its outcome, from that landing's output <path>:`, then that landing's output and the `RESULT` lines of its own branches, whose records the batch finished, and exits with the code in its last record. `wait-result` reads the record as usual: a folded branch's final record is the batch's. A folded submission's own landing that reads its payload only after the fold is refused (`submit.restore`, an untrusted payload): it writes no record, only its refusal line to its own output; and `submit.abandon` leaves a folded record alone.

Left open: a fold compares no tests (Batch, "Which branches batch"); under `"landing".gate_once` every fold keeps to that rule, since every merge that is not docs-only runs `--full`, while in a repository that opts out of `gate_once` but not of folding a landing may fold a submission whose tests differ from its own (a check would run each step's selector on each branch's diff, not read gate-OK records); the landing feed names each branch's own record and carries no `batch` or `folded_into` (the hub refuses unknown fields; the land ledger has them, Land ledger); the landing lock file names only the folding landing's own branches; a folded process that ended FOLDED while its folding landing still ran, and was then given back, leaves records `running` with a pid that has ended, which the first `wait-result` finishes `error`.

### Landing feed

Once a landing has landed (exit 0 with a merge), its lock released and its records closed, `Lander.post_landing` posts one event per branch to this machine's Action Hub as the agent (POST `/api/v1/landings`, docs/hub-approvals.md "landings/L-NNN"): the branch's land record picked as its ledger line is (`result.LEDGER_FIELDS`), with the repo, the main branch, the new main (a batch's branches share it), the record ids `close_pulled` closed for the branch, the merged gate's mode (its gate-OK record on the new main), the tip's `Deploy:` trailer values as a deploy note (`kitlib.hubsite.landings`) and the hub approvals its commits put on main (`approvals`, from `kitlib.hubsite.approvals.landed` over main before the landing..the tip; left out when there is none, and when git cannot tell), which the hub marks spent for its page. The post is best-effort with a 3 s timeout: a hub that is down, has no agent token here, does not answer, or is older than the route (a 404), and any other exception, Ctrl+C included, is said as `WARNING: the landing of <branch> was not posted to the hub feed (<why>); the landing stands` and the event is dropped (no pending file, no retry). The WARNING is progress, not an outcome line: the outcome, its lines, its exit code and verdict line stand. A landing that did not land posts nothing.
