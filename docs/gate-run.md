## Commands

| Command | Does |
|---|---|
| `gate.py [-C DIR] [--base REV] [--full \| --only STEP ... \| --rerun] [--plan \| --again] [--slug S] [--log-dir D]` | (`--rerun`: Targeted rerun. `--again`: a gate that would only repeat a failed gate of the same tree, refused otherwise; An unchanged red tree.) Gates the checkout under `book(<gate.kind>)` (default `test`), booked as a gate run: the build daemons it leaves that serve nothing outside its job are stopped at its end (Build daemons). The base is the default base (Default base); the merge base with HEAD is what is compared. A landing takes a branch tip with the gate-OK record of a `--full` or default-mode pass, or of a docs-only pass of a change docs-only under the base's config, which neither `--base` naming another commit nor `--only` writes (docs/gate-records.md "Gate-OK record"; docs/gate-landing.md "Landing", step 4). |
| `land.py BRANCH [BRANCH ...] --expect-tip SHA [--expect-tip SHA ...] [--expect-main SHA] [-C DIR] [--summary T] [--fresh] [--wait S] [--log-dir D] [--keep-branch] [--reviewed-by ID ... [--wait-result] --submit]` | The landing tool (tools/land.py): lands BRANCH, or a batch, from the main checkout onto `<remote>/<main>` as it is at the landing's turn (see docs/gate-landing.md "Landing"). One `--expect-tip` per branch, in the same order. `--expect-main` is optional: the main the landing was planned on, compared and never refused for (docs/gate-landing.md "Landing", step 4). `--wait` defaults to `"landing".wait_s`. `--submit` starts the landing detached and returns at once, and needs one `--reviewed-by` per branch, the reviewer id of its queued verdict (docs/gate-landing.md "Submitting a landing"); `--wait-result` before it waits in the same call and ends with the landing's result (docs/gate-landing.md "Submitting a landing", "Waiting in the same call"). Landed, each branch is cleaned up unless `--keep-branch` (see docs/gate-landing-policy.md "Branch cleanup"). |
| `land.py --sweep-landed [--apply] [-C DIR]` | The branch cleanup for every branch main already contains (`kitlib.landing.cleanup.sweep`; see docs/gate-landing-policy.md "Branch cleanup"). Without `--apply` a dry run: it changes nothing and names what would go. |
| `land.py --queue [-C DIR]` | Read-only: the landing lock file's holder, then the landings in the machine lock's queue (its entries of priority `land`), holding first, then waiting in turn order, a landing of another repository marked so (`kitlib.landing.lander.queue`; see docs/gate-landing.md "The landing queue"). |
| `land.py BRANCH [BRANCH ...] --check-strict [-C DIR]` | Read-only, no lock, no verdict: whether each branch changes a strict path, `STRICT <branch>: <paths> ...` or `NOT STRICT <branch>: ...` (`kitlib.landing.lander.check_strict`; see docs/gate-landing-policy.md "Strict paths"). |
| `gate.py land BRANCH --expect-tip SHA [--expect-main SHA] [-C DIR] [--summary T] [--fresh] [--wait S] [--log-dir D] [--keep-branch] [--reviewed-by ID --submit]` | The same landing for one branch, with `--wait` defaulting to 0, or to `"landing".wait_s` with `--submit` (see docs/gate-landing.md "Landing"). |

See Result record. |
| `gate.py stop RUN [-C DIR]` | Ends one gate run by its machine-lock run id (`r-...`, on the gate's held line and in `machine_lock.py status`): that run's process tree and lock only. A landing's is refused, but a load node's land gate shows as a plain gate on the node (docs/gate-rerun-checkout.md "Stopping a gate", Known limits). Exits 0 stopped or already gone, 1 it could not be ended, 2 USAGE, 4 refused (`tools/gate.py` `do_stop`, over `kitlib/gate/stop.py`; see docs/gate-rerun-checkout.md "Stopping a gate"). |
| `gate.py --measure --out PATH [--days N]` | Writes a proposed kinds table from the lock's run history (kitlib/gate/measure.py). It never writes the live kitlib/lock/kinds.json. Every kind's cpu in the proposal is a whole number 1..the layout's agent_cap: the p90 peak busy cpu slots rounded up, or agent_cap when the runs fill what they booked (pinned runs cannot show more). The lock measures a run's job object only, so a finished run counts as a cpu sample only when its history line shows work in the job (kitlib/gate/measure.py `skip_reason`): not `partial`, held `MIN_HELD_S` (10 s) or more, with `cpu_s` and a peak above 0, and `cpu_s` at least `MIN_BUSY_THREADS` (0.1) x `held_s`. A kind with too few runs or too few cpu samples is kept whole, warn_min included, written as the size it books on this layout now. It prints one line per kind; the line counts the skipped runs by reason. Not caught: a wrapper that itself keeps a tenth of a thread busy while its work runs outside the job. Any other flag, `-C`, `--slug` and `--log-dir` included, is USAGE (2); a refusal (4) is said on stderr. |
| `gate.py allow BRANCH --runs N --why TEXT [-C DIR]` | The coordinator's call (`tools/gate.py` `do_allow`, over `kitlib/gate/budget.py` `allow`): allows BRANCH N gate runs in all, past the branch gate budget (docs/gate-records.md "The branch gate budget"). N is a whole number above 5; `--why` is required, and an N not above 5 or an empty `--why` is `USAGE: ...` (exit 2). Prints `ALLOWED <branch>: N gate runs (<used> used); <file>`; `REFUSED: <reason>; nothing written` (exit `G.REFUSED`), on stderr, when BRANCH is not a branch of the repository or the file cannot be written. |

## Default base

`kitlib.git.refs.default_base` is the one rule every kit tool uses when no `--base` is given: `refs/remotes/<remote>/<main>` (as last fetched) when it resolves, else the local `<main>`, where `<main>` is the work base (`kitlib.config.work_base`: the staging branch when `.kit.json` "staging".branch is set, else the main branch; docs/gate-landing.md "Staging branch"). A local main lags whenever nobody pulls into the main checkout, and measuring against it counts the remote's newer commits as the branch's work. When the local main is at another commit the tool prints `base: local main <hash> is N behind <remote>/<main> <hash>; measuring against <ref>` (or ahead, or both). An explicit `--base` is always used as given. Users: gate.py, doc_budget.py, review_pack.py, forbidden.py, kit_tests.py and pytests.py `--select`; preflight.py `--board` measures its rows against `<remote>/<base>` when the two differ.

Every kit `git fetch` and `git ls-remote` runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and `GIT_HTTP_LOW_SPEED_LIMIT=1000`/`GIT_HTTP_LOW_SPEED_TIME=60` (`kitlib.git.cmd.NETWORK_ENV`): a remote that wants credentials, or a transfer stalled below 1000 bytes/s for 60 s, fails instead of hanging. An ssh passphrase prompt is not covered (forcing `ssh -o BatchMode=yes` would override the user's `core.sshCommand`, `GIT_SSH` and ssh config; see the `kitlib.git.cmd` docstring). A push keeps the user's credential prompts.

## Exit codes

From kitlib/gate/__init__.py. The machine lock's refusal codes pass through unchanged (kitlib/lock/store.py: 6 busy, 8 timeout, 10 require-lock, 11 reserved, 12 hold). Ctrl+C is 130.

| Code | Name | First line printed |
|---|---|---|
| 0 | OK | `GATE OK[ (warned: ..; skipped: ..)]` (or `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, see Auto-detected gate), `LANDED <branch> on <main> at <merge> (pushed and verified on <remote>)` (followed by a scope-check `WARNING: ...; the landing went ahead: the scope check only warns for now (kitlib.landing.checks SCOPE_REFUSES)` for a branch that changes paths outside its records' scopes while `checks.SCOPE_REFUSES` is False (docs/gate-landing.md "Landing", step 4); and by `WARNING: the landing lock could not be released: ...` and the command to break it when only the release failed), or `proposal written: <path>` |
| 1 | FAILED | `GATE FAILED: <steps> (<first>: <reason>)`, or `NOT LANDED: ...` (a red merge dropped, a step that changed the landing tree, a push refused because `<remote>/<main>` moved on, a push git refused (exit 1 with git's own `! [rejected]` or `! [remote rejected]` line) while `<remote>/<main>` is still the base, an exception, SystemExit or Ctrl+C after the merge and before the push), or for a merge that conflicted (aborted, the batch's earlier merges dropped) `<branch> does not merge cleanly into <main>: ...; the merge was aborted` and the verdict line `CONFLICT <branch> with main <base>: the author merges main` |
| 2 | USAGE | `USAGE: ...`: bad arguments, an `--only` name no step has, a `--base` that does not resolve, a machine-lock usage error such as an unknown `"gate".kind`. Never worded as a refusal (refusal-log P10). |
| 3 | STUCK | `STUCK: landing <branch> stopped in phase <phase>: ...`, then what is left and the steps to clear it (see docs/gate-landing.md "Landing"); the landing lock stays held at phase `stuck`. Only a push that may have landed and cannot be told is STUCK, an exception, SystemExit or Ctrl+C during the push included, and a push that timed out, died (exit 128), exited 1 without git's refusal line or exited 0 while `<remote>/<main>` is still the base |
| 4 | REFUSED | `REFUSED: ...; nothing was changed` or `... nothing was merged` (a config error before the merge is one); `REFUSED: no gate step selected: ...` when the steps cover none of the changed paths, or under `--full` and in the merged gate when every step is manual, or when each step left is dropped by another selected step's `skip_if_selected` (`runner.NO_STEP`, `runner.NO_STEP_FULL`); `REFUSED: no gate step ran: ...` when every selected step was skipped for a missing `requires` (it names each one and what it requires). In both, no record is written and a landing drops its merge. `REFUSED: the stash stack is not empty (refs/stash is at <sha>): ...` while the repository's stash stack holds an entry (docs/gate-rerun-checkout.md "The stash guard"). `REFUSED: this gate's output file ...` when a branch gate's stdout is a file another gate run is writing (docs/gate-records.md "Whose run a log is"). A scope-check miss is `REFUSED: <branch> changes <n> path(s) outside the scopes of the records it holds ...; nothing was merged` only once `checks.SCOPE_REFUSES` is True; until then it is a WARNING after `LANDED` (docs/gate-landing.md "Landing", step 4). |
| 5 | BUSY | `BUSY: landing lock: HELD ...; nothing was changed` (the landing lock file not had within what is left of `--wait` once the turn was given), or `BUSY: ... not broken, because ...` at once for a gone holder that left something unpushed. A turn the machine lock does not give is its own code, not BUSY (below) |
| 9 | LANDED_UNGATED | Retired: no landing gives it. The code and the `landed-ungated` verdict are kept so old result records still read (`G.LANDED_UNGATED`) |
| 16 | STOPPED | `STOPPED: gate run <id> was stopped; no verdict and no gate-OK record`, or `STOPPED: the gate was stopped while it waited for the machine lock; ...`: the exit of a stopped gate (docs/gate-rerun-checkout.md "Stopping a gate"), not of `gate.py stop` |

`gate.py wait-result` has its own codes: 0 (the record's verdict is `pass`), 1 (any other verdict, `stopped` and an old record's `landed-ungated` included), 2 (USAGE), 7 (TIMEOUT: no final record at that tip in time).

Any other machine lock refusal prints `NOT RUN: the machine lock refused the gate: ...`; for a landing's turn (docs/gate-landing.md "Landing", step 3), `NOT RUN: the machine lock did not give the landing its turn: ...; nothing was changed`, with the lock's code (6 when `--wait` is 0 and the lock cannot give it at once, 8 when `--wait` ran out; kitlib/lock/run.py `book`). Ctrl+C is 130 only when nothing is left: before the merge, or after it and before the push, once the merge was dropped and the lock released. During the push it is STUCK.

A landing's verdict is its exit code, and in text its first line starting `LANDED `, `NOT LANDED:`, `CONFLICT `, `STUCK:`, `REFUSED:`, `BUSY:`, `USAGE:` or `NOT RUN:`. Key on that line, not on `^GATE (OK|FAILED)`, which is the merged gate's own verdict (`kitlib.gate.runner.verdict`). A `GATE OK` line appears only in a landing that LANDED; a green merged gate that is then not landed prints it as `merged gate passed ...`, so no `GATE OK` line stands beside a `NOT LANDED`.

## Steps

kitlib/gate/steps.py. A step has a `cmd` (argv with `{python} {root} {base} {here} {tools}` substituted) or a `check` (a function in the repo hook module's `GATE_CHECKS`).

- **Full command.** A `cmd` step may also have `full_cmd`, an argv substituted the same way. A full run (`gate.py --full`, the merged gate of a landing whose merge changes a gate config file, `daily_full.py`) runs `full_cmd` instead of `cmd` (`steps.build(full=True)`); every other run, every other landing included, runs `cmd`. `merged_args` are appended to whichever runs, and in a staging promotion's merged gate alone a step's `promote_args` after them (`steps.build(promote=True)`; docs/modules/staging-design.md "Promotion"). Use it for a step whose `cmd` selects tests by the change: on an unchanged tree such a `cmd` selects nothing and passes without running a test.
- **Daily command.** A `cmd` step may also have `daily_cmd`, substituted and validated like `full_cmd`. The daily full run (`daily_full.py`) runs a step's `daily_cmd` when it has one, else its `full_cmd`, else its `cmd` (`steps.argv_of`, `steps.build(daily=True)`). No other run reads it, so a tier too slow for every full gate, such as the kit's `kit_tests --full --both-tiers`, can run only daily.

- **Selection.** In diff mode a step runs when it is `always`, or when a changed path (tracked diff from the merge base, plus untracked files git does not ignore) matches its `globs` and none of its `exclude`, or when its `content` regex is in a changed file. `--full` runs every step that is not `manual`. `--only` runs exactly the named steps. `skip_if_selected` drops a step. Diff mode then adds the `"gate".smoke_steps` (Smoke steps), and a docs-only change runs only the `"gate".docs_only` steps (Docs-only changes). Order: `setup`, then stages `first`, `main`, `last`, then `defer`.
- **Judging.** A step passes only when its exit code is in `ok_exits`, every `pass` pattern matches, no `fail` pattern matches, a cmd step's log is not empty, and it did not run zero tests (`Ran 0 tests` or a `zero_tests` pattern). The `errors` policy must also find no unexplained line. A `warn` step that fails, or a `warn_lines` hit, is WARN. A FAIL stops the rest unless the step has `continue`. A `requires` entry is a command name (looked up on PATH) or an argv probe that must exit 0 within 60 s (`PROBE_TIMEOUT`; on timeout its whole process tree is ended). One that is missing is SKIP, or FAIL with `requires_strict`. A gate whose selected steps were all skipped did not run anything, so it is REFUSED, not OK.
- **Zero-count warning.** Before its steps run, a branch gate (`gate.py`; a landing's merged-tree gate does not) prints a `WARNING:` line for each `pass` pattern a zero-test run also matches, in every configured step, including steps this run does not select (`steps.zero_count_passes`: it matches `Ran 0 tests` or a `zero_tests` line, or its own first count may be 0, as `\d+`). Put a floor in such a pattern, as `[1-9]\d*`. The warning never fails the gate or changes its exit code; a check that raises prints one `WARNING:` line saying so instead, a `pass` that is no string is skipped, and each line is escaped to ASCII (`runner.zero_count_warnings`).
- **Reuse.** A cmd step with `reuse` (`true`, or a group name: a group is reused whole or not at all) and declared inputs (`globs` or `content`.globs) may be counted as passed without running, in a branch-gate rerun or a landing, when a pass of the same inputs, argv, config and kit (and, for a step that declares one, the same `toolchain`) is in the gate cache (see docs/gate-landing-policy.md "Gate reuse"). A check step never is.
- **Check contract.** `GATE_CHECKS[name](ctx)`; ctx has `root base merged changed options name log run`. `run(argv, cwd=None)` runs in the slot's job and returns the exit code. A check returns 0/True to pass. Raising fails the check, and the traceback goes in the log. Calling `sys.exit` (any code, 0 included) also fails it, and the code goes in the log. Ctrl+C is not caught: it stops the gate.
- **Tested tree.** A gate's machine-lock run records the git tree it tests as `tree`, kept in its history line (`runner.tested_tree`; `book(..., tree=)`, `Slot.note_tree` for the slot a landing holds): a branch gate's HEAD tree when the work tree is clean (none otherwise), a landing's merge tree, the daily full run's commit's tree. It is a note, never a reason to refuse, except as one key of the gate queue's duplicate check (docs/gate-records.md "The gate queue"). The same run and line record the gate's mode as `gate_mode` (`book(..., gate_mode=)`, `Slot.note_tree` for a landing's slot): `select`, `full` or `docs` for a branch gate (`select` for `--only` and a partial `--base`, with `--full` too); `merged`, `full` or `docs` for a landing's gate (null when all its steps were reused); `rerun` for a targeted rerun; `daily` for the daily full run and `bisect` for its bisect probes. It is a note only.

### Smoke steps

`"gate".smoke_steps` (docs/kit-json.md) names steps that a default-mode (not `--full`) branch gate runs whatever changed: after diff selection and `skip_if_selected`, each one not already selected is added with the reason `smoke`, a manual one included, and never dropped (`steps.select`). A name no step has is a config error (`steps.unknown_names`). The gate-OK record of such a gate has `mode` `select` (docs/gate-records.md "Gate-OK record"), and a landing takes it for a tip (docs/gate-landing.md "Landing", step 4). The merged gate selects by the merge's diff as a default-mode gate does, so it adds the smoke steps too.

For the kit, `kit_tests.py --select --smoke` adds `tests/selection.json`'s `smoke` modules unless every changed path is prose (docs/test-tools.md). The kit's `.kit.json` is owner-only. Its gate config sets `smoke_steps` to `["kit-suite"]` and `docs_only` (Docs-only changes); its `"landing"` section sets `self_review_max_lines` 150. So strict paths (docs/gate-landing-policy.md "Strict paths") change how a kit branch lands, not its final gate: a branch that changes one ends on the default mode `gate.py -C <worktree>` on its tip, lands alone with a strong-tier verdict from a reviewer who is not its author, and its merged gate runs fresh; every branch ends on the optimized gate, the default mode `gate.py -C <worktree>` (diff selection and the smoke steps, plus Gate reuse for `kit-suite`, which sets `reuse: true` and `globs: ["*"]`), whose `select` record the landing takes (docs/gate-landing.md "Landing", step 4).

### The final gate

The gate a branch ends on, run once after review, on the reviewed tip, when the coordinator asks (builder, branch-sync, review; no gate runs before review): the default-mode gate `gate.py -C <worktree>` (diff selection and the smoke steps, plus Gate reuse for a step that asks for it), whatever the branch changes. Its `select` record lands the tip, and the `docs` record of a change docs-only under the base lands it too (Docs-only changes; docs/gate-landing.md "Landing", step 4). No branch needs a `--full` run (ARCHITECTURE.md "What a landing runs"): a strict branch's merged gate runs its selection fresh (docs/gate-landing-policy.md "Strict paths"), and a merge that changes a gate config file runs every step in full once, on the merged tree, at its landing (docs/gate-landing.md "Landing", step 6). A red whole run whose targeted rerun says FLAKE lands the tip as well (docs/gate-rerun-checkout.md "Targeted rerun"). `gate.py --full` is a full run by hand; its record lands a tip too. Landing refuses a tip without a record it takes. A reviewer never sends back a default-mode final gate.

Retired: `"landing".shared_paths` and `"landing".gate_once` (and the `FULL NEEDED` hint that read them) are gone. A `.kit.json` that still writes either loads, ignores it, and gets one `WARNING:` line per `gate.py` or `land.py` run (docs/kit-json.md).

### Docs-only changes

`"gate".docs_only` is `{globs, exclude, steps}` (docs/kit-json.md). A change is docs-only when it changes something and every changed path matches `globs` and none of `exclude`, and none is `.kit.json`, a config section file, the hook module, a `"landing".reuse_never` path or a strict path (`steps.docs_only`, `reuse.docs_only_change`). A docs-only branch gate (not `--full`, not `--only`) runs exactly the `docs_only` steps, plus `setup`, says `a docs-only change: only the "docs_only" steps run`, and writes its record with `mode` `docs`. `docs_only.steps` must not be empty: a `docs_only` with empty or missing `steps` is a config error (`steps.unknown_names`), since its gate would run nothing yet write a record. A branch decides this from its own config; a landing decides it from the base's (docs/gate-landing.md "Landing", steps 4 and 6). The kit sets `docs_only` to `docs/*.md` with the step `kit-suite`, so a docs-only kit change runs `kit_tests.py --select --smoke` (docs/test-tools.md).

## Auto-detected gate

With no `"gate"` section in `.kit.json` (neither inline nor in the file it names, such as `tools/gate.json`), the gate detects the stack from the checkout's files and runs its usual test and lint steps (`kitlib/gate/detect.py`). A configured `"gate"` section always wins, even an empty one: no detected step is ever added to it, and a section with no step that covers the change refuses as before. Every gate takes its steps from `detect.effective`: the branch gate (from the checkout), a landing's merged-tree gate and its check of commits on top (from the merged tree), and the daily full run (from its worktree).

The files are the ones git lists (tracked, plus untracked files it does not ignore that are under none of the build folders below); where git cannot list them, a walk that skips `node_modules`, `.venv`, `target`, `bin`, `obj` and other build folders, and any folder with a `.git` of its own. Detection only reads files: it installs, fetches and runs nothing, and looks nothing up on PATH. Each detected step is `always`, and names its tool in `requires` (Steps, Judging). A test step is `requires_strict`, so a missing test runner FAILs: a gate never passes without the tests it found. A lint step is not, so a missing linter is SKIP, named in the verdict line. `{python}` is the interpreter running the gate, not a project virtualenv; a project that needs its own interpreter, an install step or other arguments writes a `"gate"` section.

| Stack | Detected by | Steps |
|---|---|---|
| Python | a test file (`test*.py` or `*_test.py`) | `python-tests`: `{python} -m pytest` when the repository uses pytest (`pytest.ini`; a `conftest.py`; a `[tool.pytest...]`, `[tool:pytest]` or `[pytest]` section; `pytest` or a `pytest-*` plugin named in `pyproject.toml`, `setup.cfg`, `setup.py`, `tox.ini`, `Pipfile` or `requirements*.txt`; or a test file that imports it), requiring `import pytest` to work; else `{python} -m unittest discover`, with `-s tests` (or `-s test`) when the tests are in that folder |
| | `ruff.toml`, `.ruff.toml` or `[tool.ruff]` in `pyproject.toml` | `python-ruff`: `ruff check .` |
| | `.flake8`, or `[flake8]` in `setup.cfg` or `tox.ini` | `python-flake8`: `flake8` |
| Node | `package.json` at the root | `node-test`, `node-lint`, `node-typecheck`: `<pm> run <script>` for each of the scripts `test`, `lint`, `typecheck` it has (npm init's `no test specified` placeholder is not a test). `<pm>` by lockfile: `pnpm-lock.yaml` pnpm, `yarn.lock` yarn, `bun.lockb` or `bun.lock` bun, else npm (npm, pnpm and yarn run as their `.cmd` shims). Dependencies are not installed: `node_modules` must be there |
| Rust | `Cargo.toml` at the root | `rust-test`: `cargo test --workspace`; `rust-fmt`: `cargo fmt --all --check` when `rustfmt.toml` or `.rustfmt.toml` is there |
| Go | `go.mod` at the root | `go-test`: `go test ./...`; `go-vet`: `go vet ./...` |
| .NET | a `*.sln` or `*.slnx` at the root, else a test project (`*.csproj`, `*.fsproj` or `*.vbproj` named `*test*`, or referencing `Microsoft.NET.Test.Sdk`) | `dotnet-test`: `dotnet test <solution or project> -nodeReuse:false -p:UseSharedCompilation=false`, one step per solution (or per test project when there is no solution), each named `dotnet-test-<name>` when there are several (`-2`, `-3` ... when two share a name). A path starting with `-` or holding `{` is never passed |

Several stacks in one checkout run every one's steps, in the table's order. Python with no test file and no linter config, and a `package.json` with none of the three scripts, detect nothing. Only root-level manifests count: a monorepo whose `go.mod`, `Cargo.toml` or `package.json` live only in subfolders detects nothing for that stack, and writes a `"gate"` section.

**What the base owes.** The branch gate and a landing's merged-tree gate also detect over their base commit's tree (the branch gate: the merge base; a landing: its base, `<remote>/<main>` at its turn (docs/gate-landing.md "Landing", step 4), read with `git ls-tree` and `git cat-file`), and keep every step the base detects that the tree under test does not (`detect.owed`; the `dotnet-test` steps count as one). So a branch that deletes its test files, its `test` script or its manifest still runs those tests, with the base's command, and they fail. A kept lint step (`python-ruff`, `python-flake8`, `node-lint`, `node-typecheck`, `rust-fmt`, `go-vet`) is `warn`: its failure is a WARN named in the verdict. The source line names what was kept (`kept from the base, which detects them and this tree does not: ...`). Dropping a check on purpose takes a `"gate"` section. When git cannot read the base the gate is REFUSED. The daily full run, which has no base, detects over its worktree alone. Detection does not stop a branch from changing what a detected step runs (a `test` script edited to `exit 0`, a `conftest.py` that skips everything): that is a change to the tests themselves, which review sees as it would under a configured gate.

**The label.** An auto-detected gate says `source: auto (auto-detected gate: <stacks>; ...)` before it starts, and the same line is the last line of its report (`source: gate.json` for a configured gate). `gate.py --plan` ends with it too. The result record and the gate-OK record carry `source` (`auto` or `gate.json`; see Gate-OK record and Result record), so the PM sees an auto-detected gate in the record a waiting session reads, not only in the console.

**Nothing detected.** When neither the tree under test nor its base detects a stack, the gate runs no step and PASSES, saying so: `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, then `source: auto (auto-detected gate: no stack found, so it ran NO checks; ...)`. A branch gate writes the gate-OK record as usual (its `steps` empty, `source` `auto`), and a landing lands. It passes rather than refuses because an auto-detected gate exists so that a repository with nothing committed for the kit (a docs-only repository, or a stack no detector knows) can run a worker-to-landing cycle; a refusal there could only be cleared by committing a gate section, which is what auto-detection avoids. The checks it did not run are not hidden: the verdict line, the source line and both records' `source` say so wherever a pass is read. A configured gate with no step selected is still REFUSED (Exit codes), and an auto-detected gate whose detected steps were all skipped is REFUSED as any gate is (`no gate step ran`). The daily full run refuses a gate with no step either way.

**The record's hash.** `gate_config` (docs/gate-records.md "Gate-OK record") is still the configured section over its defaults, not the detected steps: they follow from the commit's tree, which the record names, its base's tree (`base`), and the kit, which its `kit` names, so the hash and the record still fix what the gate ran. `steps` lists them by name.

## Build daemons

Every locked run's Gradle builds run with the daemon off (`-Dorg.gradle.daemon=false` in `GRADLE_OPTS`), so they start no shared Gradle daemon unless a command names `--daemon`, and reuse none: docs/lock-api.md "Build daemons under the lock". What follows applies to the daemons a gate's commands still leave in its job: a Kotlin daemon, a Gradle daemon started with `--daemon`, an MSBuild node, the compiler server.

At the release of a gate run that ended "done", `kitlib/lock/run_held.py` `Slot.stop_daemons` stops the build daemons the gate's commands left in its job (policy: `machine_lock.daemons`, default `gates`, in `kitlib/lock/site.py`). A daemon is shared: any build on the machine may reuse one this gate started, so `kitlib/proc/daemons.py` `stop` ends one only when it is shown to serve the gate's job alone:

- MSBuild nodes and the C#/VB compiler server (VBCSCompiler) are always left running: their clients reach them over named pipes, and which process holds the other end cannot be read from outside.
- A Gradle or Kotlin daemon is stopped, with its children, only when the other end of every established TCP connection on this machine (`kitlib/proc/tcp.py` `peers`) of every process in its tree is in the gate's job (`kitlib/proc/job.py` `Job.contains`), in that same tree, or a process that has gone.
- Anything else is left running, never killed: a client outside the job or whose job Windows will not tell, a local connection whose other end the table does not show, a connection table or process tree that cannot be read. A daemon in the tree of a daemon left running, or serving a process in that tree, is left too.

Each daemon is said, as `run <id>: stopped the <label> (pid N) it left: <result>` or `run <id>: left the <label> (pid N) running: <why>`, and listed in the run's ended record under `daemons` (`pid`, `what`, `result`; a left one's result is `left: <why>`). A gate nested in another run says them and records none. The tree and the table are read once, before any daemon is ended, so a client that connects between that read and the kill is not seen; exactly the (pid, creation time) pairs judged are ended, children first, each by `terminate_verified`.

The kill path spares a shared daemon too. A run cancelled by `stop`, interrupted by Ctrl+C or ended in error, and a `Launcher.kill`, ends its job through `Slot.end_tree`, which calls `end_sparing`; so does a background run's `kitlib/lock/background.py` `end_child` (a stop past `bg_stop_grace_s`, a yield-late, Ctrl+C). This holds for any run booked by `book()`, not only a gate. Sparing a daemon makes the kill take up to about 2 s longer (`END_PASSES` x `END_PASS_S`, then `END_WAIT_S`), so a background run's stop frees its slots that much later. `machine_lock.daemons` is not read here: a daemon that serves only the run's job is ended, and one the rules above leave is spared with its tree.

- Nothing found, or no daemon left, or the job's processes or the daemons cannot be read: TerminateJobObject.
- `stop` raised: each daemon found is recorded and said as `not judged (<error>)`, never as left, and each one still running at its creation time is spared with its tree.
- Otherwise every process in the job outside the spared trees is ended by `terminate_verified`, oldest first, in up to `END_PASSES` (10) passes `END_PASS_S` (0.1 s) apart (`_end_others`). A target created at or after the pass's time stamp may hold a reused pid and is not ended in that pass; the next pass sees it again. A process still running after the last pass and up to `END_WAIT_S` (1 s) more is said (`WARNING: run <id>: pid N in its job could not be ended; it runs on, unpinned`); the job is then closed without a kill and the spared daemons run on. A job or process table that cannot be read part way ends the job whole, the spared daemons with it, and that is said.
- An interrupt inside `end_tree` goes up with the kill marked not done, so the release that follows judges and ends the tree again. One that interrupts the release's own `end_tree` ends the whole job, the spared daemons with it.

Known limits:

- While a run lives its job is kill-on-close, so a wrapper that dies closes it and Windows ends every process in it, a shared daemon included; no code runs then.
- An MSBuild node or the compiler server in the job is left whoever its clients are (`PIPE_LABELS`), so a cancelled `dotnet` run does not end them or what they started. Nothing in the lock ends them later: they run until they exit or are ended by hand. `python optional/procwatch/procwatch.py --kill --only msbuild-node` ends an idle MSBuild node with no living parent that is at least 5 minutes old (15 with `/nodereuse:true`); it matches only a node started with `/nodemode:`, and it reports compiler servers (rule `roslyn-server`) and never ends one. The .NET stack template's gate steps run with `-nodeReuse:false -p:UseSharedCompilation=false` (`templates/stacks/dotnet/tools/dotnet_each.py` `NO_REUSE`) so they leave no build server behind; the template's `stack.json` `BUILD_COMMAND` has only `-nodeReuse:false` and its `TEST_COMMAND` neither, so a run of those commands can leave build servers.
- A spared daemon inside a nested kill-on-close job made by a process the kill ends can die with that job although the record says it was left running (inferred from how Windows jobs behave, not tested).
- A descendant of a spared daemon whose own parent has exited no longer shows as its descendant, so it is ended. A process started after the last pass by one being ended runs on, unpinned.
- A left daemon whose creation time cannot be read and whose pid another user's or a protected process takes during the passes counts as alive, so that pid and its orphaned workers are spared and run on, unpinned. Processes can leak this way; nothing shared is killed.
- The pid-reuse test rests on Windows stamping creation times from the clock `GetSystemTimeAsFileTime` reads (inferred, not measured); a clock set back during the passes voids it.

## Console windows

Every gate run's lock run watches for console windows while its steps run: `kitlib/lock/run_held.py` `Slot.start` starts a `kitlib/platform/windows/winwatch.py` `Monitor` before the first step, and `kitlib/gate/runner.py` `window_results` stops it (`Slot.watch_stop`) after the last step and says the report, before the verdict:

```
windows opened: 1 - WARNING: a console window opened (the verdict does not count it)
  12:20:05 window pid 56324 python.exe via windowsterminal.exe CASCADIA_HOSTING_WINDOW_CLASS title "<python folder>\python.exe" [this run]
    cmd: "<python folder>\python.exe" -c "import sys; sys.stdin.read()"
    parent: pid 4410: python -m unittest tests.proc.test_x
```

- `cmd:` and `parent:` say what spawned the window: the program's command line, its parent pid and the parent's command line, read when the window's event arrives (`winwatch.proc_info`). A process gone or unreadable by then shows `(unreadable)`.

- N counts the windows the run opened (`[this run]`: the program was in the run's job, `Slot.window_owner`) and those it cannot place (`[run unknown]`: the program had exited, or could not be opened, when the window was read). A window whose program is outside the job is listed under `also seen, another run's: M` and not counted. A console host window shown and gone before it could be read is listed under `also seen: K console host window(s) ...` and not counted.
- A window warns: the verdict, the exit code and the gate-OK record do not change. `WINDOWS_FAIL = True` in `kitlib/gate/runner.py` is the one change that makes a counted window fail the gate: `window_results` then adds a FAIL result named `windows` (`GATE FAILED: windows (windows: N console window(s) opened)`), the report line reads `- FAILED: a console window opened`, and the lock run records code 1. `windows` is a reserved step name (`kitlib/gate/steps.py` `RESERVED`), so no configured step shares that result's name.
- Every gate run is watched, not only `--full`: a branch gate, a landing's merged-tree gate and the daily full run. The branch and merged-tree gates also return the windows as the outcome fact `windows` (each `Window.as_dict()`; None when no step ran).
- A monitor that cannot run, or that raises as it starts (`Slot.watch_start`), says `windows opened: unknown (the window monitor did not run: <why>)`, and the gate goes on.
- What it sees and misses (Windows Terminal hosting, the title heuristic for new tabs, other programs' windows, session 0, the events still queued when it stops): the `kitlib/platform/windows/winwatch.py` module docstring. The tests show no window the user can see (docs/test-tools.md "Window tests").
