# redfirst

`tools/redfirst.py [-C WORKTREE] --tests FILE[::FILTER] ... [--also FILE ...] [--base REV] [--head REV] [--log-dir DIR]` runs new tests against the pre-change commit and confirms they fail there: red-first evidence with no in-place mutant. `-C` defaults to the current directory; a main checkout is refused. Logic: `kitlib/redfirst` (`verdict.py` pure, `run.py` git and cleanup); the module docstrings hold the full rules. `--tests` and `--also` each take several values and may also be repeated (`--tests A --tests B` is `--tests A B`).

- The test files must be committed at `--head` (default HEAD). They are checked out into a throwaway detached worktree at `--base`, `<main checkout>/<worktrees_dir>/redfirst-<base10>-<pid>`. The default base is the merge-base with `<remote>/<main branch>`. The caller's worktree is only read. A main checkout is refused. It reads no landing lock and does no fetch, and the branch under test need not be pushed (`tests/redfirst/test_run.py`, `Runs.test_red_with_the_landing_lock_held_and_the_head_unpushed`); `new_worktree.py` points here when it refuses a `--base` with no pushed branch.
- `.kit.json` "redfirst".runners picks the runner. The first entry whose `glob` matches the path (case-blind) wins. Kinds:
  - `python`: `python -m unittest` with `PYTHONPATH=<pythonpath>`;
  - `gradle`: `<dir>/gradlew <project>:test --offline --tests <filter>`. gradlew.bat runs in cmd.exe, which reads its command line again, so a gradle word that holds a cmd.exe character (`& | < > ^ % " ( ) !`, CR or LF) is refused, exit 2, before any tree is made. The four words checked are the filter, the default `*.<stem>`, the runner's `project` and its `args` (`verdict.py`, `gradle_args`; `tests/redfirst/test_verdict.py`, `GradleCmdReparse`);
  - `dotnet`: `dotnet test <csproj>` with a trx log;
  - `command`: the runner's own `command`, a list of argv words, for a test no other kind runs (an engine test compiled into the game, say). Each word's placeholders are filled: `{selector}` the filter, else the file name without its extension; `{path}` the repo-relative path; `{stem}`; `{tree}` the throwaway root; `{head}` the head checkout, the `-C` worktree's absolute path (a runner script added after the base is run from there: `{head}/tools/x -Tree {tree}`; a first word under `{head}` is absolute, so it is not put under the tree. `{head}` is the worktree's checkout, not a commit, so a run that uses it is refused, exit 2, when `--head` is not the worktree's HEAD or when the path after `{head}` has uncommitted changes, and a `result` that resolves under `{head}` is refused (the caller's worktree is only read): `run.py`, `refuse_head_placeholder`, `refuse_tracked_results`; `verdict.py`, `fill`; `tests/redfirst/test_command.py`, `EngineAtHead`, `EngineHeadRefusals`, `EngineHeadResult`); `{log_dir}`; `{n}` the selector's number. A first word with a slash that is not absolute is under the throwaway root. The words go to the program as a list, so the selector is one argument; a program cmd.exe runs (a `.bat` or `.cmd`, a trailing dot or space dropped as Windows drops it, or `cmd` itself) gets a word after it that holds a cmd.exe character refused, exit 2, as for gradle (`verdict.py`, `runs_in_cmd`, `refuse_cmd_reparse`). With `result`, a JUnit XML file filled the same way (under the throwaway root unless absolute), the verdict comes from that file written in this run, and a run that writes none is ERROR. The file is deleted before each command; a `result` in the tree at a path the base holds, or at a file the run checks out, is refused, exit 2 (`run.py`, `refuse_tracked_results`). Without it, exit 0 is GREEN, 1 RED only when a log line matches the runner's `assertion` regex (else INCONCLUSIVE, "What counts as red" below), and any other code ERROR. A log line the `no_test` regex matches is NONE. So a run that names no test, or leaves no result, never reads as RED (`command_verdict`; `tests/redfirst/test_command.py`). Write the result under `{log_dir}`: a file the run leaves in the tree, outside the worktree build output, keeps the tree from being removed (exit 4).
  
  A runner's `args` are appended. The keys are listed in docs/kit-json.md under "`.kit.json` keys". A Godot engine test whose runner script writes a JUnit file:

  ```json
  {"glob": "tools/engine_tests/*.cs", "kind": "command",
   "command": ["godot.exe", "--headless", "--path", "{tree}", "--script", "res://tools/engine_tests/run.gd",
               "--", "--test", "{selector}", "--junit", "{log_dir}/{n}-{stem}.xml"],
   "result": "{log_dir}/{n}-{stem}.xml",
   "no_test": "^no engine test named "}
  ```

  The run is at the base, so the runner script must be there, or be named with `--also`. Prefer `result`: Godot that cannot load the script or the project writes no file, which is ERROR. In exit-code mode (no `result`), exit 1 is RED only when a log line matches the runner's `assertion` regex, and INCONCLUSIVE otherwise, so a setup failure that exits 1 is never RED as long as the pattern matches only the line the script prints for a failed assertion, never its crash or setup lines ("What counts as red" below).
- Runners not written (`kitlib/redfirst/run.py`, `runners_for`): the schema default `tests/*test_*.py`, then a python runner `<tools_dir>/*test_*.py` whose `pythonpath` is the tools folder (`"repo".tools_dir`), so a repo that keeps its tests in its tools folder needs no key. That runner imports those tests as top-level modules of the tools folder, so a test that does not import that way reports RED with the ImportError in its reason line. No glob is added when `tools_dir` is `.` or the glob equals one already listed. Written runners are used as they are; no glob is added.
- A `--tests` path no runner takes is refused, exit 2, nothing made (`run.py`, `select` and `no_runner_text`): the refusal lists each glob tried with how many files committed at `--head` it matches, says whether the globs are the written ones or the defaults, and names `"redfirst".runners` as the key to set (`tests/redfirst/test_run.py`, `UnwrittenRunners`).
- One line per selector: RED, GREEN, NONE (no test matched), ERROR, TIMEOUT or INCONCLUSIVE (failed, but not on an assertion: "What counts as red" below). A run that books no machine lock is killed with its whole process tree (its kill-on-close job) once it has run its limit, said on the `timeout` line: in the kit `RUN_TIMEOUT`, kit_tests' per-unit limit (300, `kitlib.tooldeps.selfrun.UNIT_TIMEOUT`); in another repo pytests' own, its `.kit.json` "tool_tests".unit_timeout as committed at the base, else that key's schema default (3600, `kitlib/config/schema.py`) (`run.py`, `run_timeout`; a value the schema refuses is exit 2). That selector is TIMEOUT, never RED or GREEN, the run ends `REDFIRST TIMEOUT - ...` with exit 3, and both lines are in `summary.txt` (`run.py`, `default_run`; `tests/redfirst/test_timeout.py`). A python test that does not import against the base is RED, with the final ImportError or ModuleNotFoundError line as its reason. A gradle or dotnet compile error is RED only when it names a copied test file; otherwise it is ERROR.
- Every line a run prints once its log folder exists is also written to `<log folder>/summary.txt`, and the last line, `summary   <that path>`, names it: read that file, not a redirect another run may share (`run.py`, `write_summary`; `tests/redfirst/test_run.py`, `SummaryFile`). A refusal before the log folder is made writes none.
- Cleanup runs on every exit the process controls, Ctrl-C included:
  - It runs in a child process on its own console.
  - It puts back the base's copy of each `--also` file, then removes the tree with `kitlib.worktree.remove` (the checks and `git_remove` that `worktree_remove.py` uses), never forced.
  - A tree still held after `"redfirst".hold_wait` seconds is left in place, with the `worktree_remove.py` command that removes it.
- Exit codes: 0 every selector RED, 1 any GREEN, 2 usage or refusal (`--help` too), 3 undecided, 4 throwaway left; 6, 8, 10, 11 or 12 when the machine lock refused the run ("The machine lock" below).

## What counts as red

A named test is RED only when it fails an assertion at the base. One that fails there on anything else (a crash, a NullReferenceException in setup, a missing import or asset the test needs, not the change) proves nothing about the change: its selector is INCONCLUSIVE, the line names the test and the exception, and the run ends `REDFIRST INCONCLUSIVE - ...` with exit 3 (`verdict.py`, `is_assertion`, `failures_verdict`, `python_verdict`, `command_verdict`; `tests/redfirst/test_assertion.py`).

- `python`: unittest's `FAIL:` block is an assertion; an `ERROR:` block (an exception, `setUpClass` included) is INCONCLUSIVE, unless its last exception names a name the base lacks and the base..head diff adds that name (RED). The forms (`verdict.py`, `missing_name`): `ModuleNotFoundError: No module named 'x'` (the dotted name or its last part), `ImportError: cannot import name 'x'`, `AttributeError: module '...' has no attribute 'x'`, mock.patch's `... does not have the attribute 'x'`, `'Foo' object has no attribute 'x'` (never `'NoneType'`), `type object 'Foo' has no attribute 'x'`, and `got an unexpected keyword argument 'x'`. The name counts as added when it is a whole word in the diff's added lines or the path of a new or changed file (`in_diff`; `run.py`, `added_lines`). The copied test files are left out, since their own lines name what they test. Otherwise the line is INCONCLUSIVE, and it says the diff adds no such name. An ImportError naming no name (`DLL load failed`) or a circular import is a crash: INCONCLUSIVE (`tests/redfirst/test_diff_names.py`). A test file that does not import against the base stays RED. A non-zero exit with no failure block is INCONCLUSIVE.
- `gradle`, `dotnet`, and `command` with a `result`: each failed test in the JUnit XML or `.trx` is judged. A JUnit `<error>`, or a `.trx` outcome other than Failed, is no assertion. A `<failure>` is one when its type is an assertion type (AssertionError, AssertionFailedError, ComparisonFailure, MultipleFailuresError, xUnit's XunitException, NUnit's AssertionException, MSTest's AssertFailedException: `ASSERT_TYPE`); a `.trx` message by the exception type it names on its first line (`System.NullReferenceException : ...` is none), and one naming no type is an assertion unless it says a method `threw`. A failure with neither a type nor a message (a `.trx` Failed result with no message, say) is no assertion: a real one always says what it checked. Any failure that is no assertion makes the selector INCONCLUSIVE. A compile error naming a copied test file stays RED.
- `command` with no `result`: exit 1 is RED only when a log line matches the runner's `assertion` regex; with no `assertion`, or no line matching, it is INCONCLUSIVE, since an exit code cannot tell a crash from a failed check.
- A runner's `assertion` (any kind, a regular expression, multi-line) also names more failures that count: it is matched against a failed test's `<type>: <message>` (python: its last exception line). An expected-failure marker of a framework the kit does not know goes there.

Known limits:
- With a `command` runner and no `result`, one log line matching `assertion` makes the selector RED even if another test it ran crashed; name one test per selector, or write a `result`.
- An assertion is told by its exception's type name (`ASSERT_TYPE`), not by where it was raised: an `assert` that fires in production code on a crash path reads RED, and an assertion type with no "assert" in its name (Mockito's WantedButNotInvoked, say) reads INCONCLUSIVE until the runner's `assertion` names it.
- A run that books the machine lock (`run.py`, `locked_run`: gradle, dotnet, command, or a runner's `lock`) is not timed: only the lock's stop ends its command, and past its kind's guide the lock warns but kills nothing.

## The machine lock

A run whose command is heavy books the machine lock itself, so it is a kit wrapper (skill machine-lock-run, "Machine lock" step 2) and the caller does not wrap `redfirst.py` in `machine_lock.py run` (`kitlib/redfirst/run.py`: `lock_kind`, `one_lock`, `book_slot`, `locked_run`; tests: `tests/redfirst/test_lock.py`).

- **Which kind.** A runner's `lock` (docs/kit-json.md, `redfirst.runners`) names the kinds-table kind. Without it a `command` runner books `build` (`run.py`, `COMMAND_LOCK`); any other runner books the kind of the first heavy-list entry the runner's command matches (`kitlib.config.heavy_match` over `heavy_programs`: the kit defaults, then the repo's `heavy.programs`), none for the python runner. Its `gradlew` and `dotnet test` commands are filtered (`--tests`, `--filter`), which the heavy list takes as `quick-test`; red-first books that as `build` (`run.py`, `QUICK_TEST`), since it builds a tree at both base and head. A run with no kind books nothing and runs as before (`run.py`, `default_run`).
- **One booking a run.** The run books once, before the throwaway tree is made, as `<repo name>/redfirst-<base10>` (`kitlib.lock.run.book`; the repo name is `"repo".name`, defaulted as docs/kit-json.md says), runs every command in the booked run's job, and releases before the cleanup. `--tests` values that need two different kinds are refused, exit 2, with the kind of each; run them in separate calls.
- **No wait limit.** A busy lock queues the run and it waits its turn. Ctrl-C while it waits ends the wait: the lock removes the run's entry, no tree is made, exit 3. A Ctrl-C that arrives inside `kitlib.lock.run.book` before that wait has started is only noted (`run.py`, `Interrupts`, BOOK mode): the run still joins the queue and waits, and ends with exit 3, its slots given back, once it holds them, or at a second Ctrl-C during the wait.
- **Inside a caller's run** (`MACHINE_LOCK_RUN`, as `kitlib.lock.run.nest_check` accepts it):
  - The caller's run holds as many slots as the kind needs, or more: redfirst takes nothing more and its command runs on the caller's cores. The `lock` line says `nested: run <id> already holds what it needs`.
  - The caller's run holds slots of a pool the kind needs, but fewer than it needs: the lock refuses the nested run (`kitlib.lock.run.nest_need`), and redfirst prints `refused: the machine lock: nested run refused: ...; start it outside that run`, makes no tree, runs nothing and exits 2. Run `redfirst.py` outside that run, where it books for itself.
  - The caller's run holds no slot of a pool the kind needs: redfirst books that pool itself.
- **Refusals.** When the lock refuses the run, no tree is made and nothing is run; the log folder, made first, stays. A usage refusal is exit 2: the nested one above, a `lock` kind the kinds table does not have, or a kind that takes a gpu slot of its own while a background run's wrapper (`MACHINE_LOCK_BG`) is an ancestor of the process (`kitlib.lock.run.book`: `a gpu lock inside a background run would pause that run; refused`). The others print `NOT RUN: the machine lock refused the run: <the lock's line>` and `REDFIRST NOT RUN - ...` and exit with the lock's own code (`run.py`, `LOCK_CODES`; `kitlib/lock/store.py`). None of them is 0 or 1, so a refusal never reads as RED or GREEN:
  - 10 (the `require-lock:` lines of `kitlib.lock.run.book` and `acquire`): the kinds table could not be read, or holds a kind whose `cpu` size is past the layout's `agent_cap` (`kitlib.lock.kinds.check_cap`); its run id was taken ("run id ... is taken" for a given id, "no free run id" once every draw was, `kitlib.lock.run.claim_id`) or the lock's store could not be written; the holds or the queue could not be read, or the queue could not be written or its store mutex was not had in time (`kitlib/lock/store.py`, `lock`), before the run had joined the queue. It is the one of these codes `book` gives for what `book_slot` passes, which is no wait limit and no hold.
  - 6 (busy), 8 (the wait ran out), 11 (an owner or game hold leaves too few slots past the wait limit) and 12 (a hold the run names cannot be claimed) are passed through should the lock give them; each needs a wait limit, `no_wait` or a named hold (`kitlib.lock.run.acquire`, `book`). With none of those a hold over the slots parks the run until it clears.
  - Any other failure of the lock is exit 3, a `machine_lock.py stop` of the run while it waits among them: the lock ends that wait with its own code 1, which here would read as GREEN.
- **The run's record.** The booked run ends, before the cleanup, with the code the verdicts give (0, 1 or 3), 130 after Ctrl-C, 1 after an error. A `machine_lock.py stop` of the run ends the command it is running (`kitlib/lock/run.py`, `Slot.wait`; the record ends `cancelled`, 1): the run prints `failed    the machine lock stopped run <id>; its command was ended and gives no verdict`, runs no later selector and counts the stopped one as ERROR. The exit is then what `kitlib.redfirst.verdict.exit_code` gives for the verdicts so far and that ERROR: 4 when the cleanup leaves the tree; else 1 when an earlier selector of the run was GREEN, which is that test's own pass at the base; else 3. It is never 0.
- **Build daemons.** A redfirst run's Gradle builds run with the daemon off, as every locked run's do (docs/lock-api.md "Build daemons under the lock"), so they leave no shared Gradle daemon unless a command names `--daemon`. A daemon left that way, or a Kotlin daemon, is treated as any run's (docs/gate.md "Build daemons"): `kitlib/lock/run.py` `Slot.stop_daemons` stops it at the release only when `machine_lock.daemons` says so, which the default `gates` does not for a redfirst run, so it runs on unpinned after the release.

Tests: `tests/redfirst`.
