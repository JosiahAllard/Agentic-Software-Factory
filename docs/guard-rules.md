# Shell guard: rules

Part of docs/guard.md (the index); the sections below are moved there unchanged.

## Rules

`kitlib/guard/rules.py` `decide(action, ctx)`. Its rules are split over `kitlib/guard/rules_base.py`, `rules_owner.py`, `rules_run.py`, `rules_gitcore.py`, `rules_push.py`, `rules_edit.py`, `rules_net.py`, `rules_tools.py` and `rules_write.py`, in that order (each imports only those before it); `rules.py` imports and re-exports every name in them, so a `rules.<name>` below names any of them. Every row below is a row in tests/guard/test_rules.py with the exact `Instead:` text. `<main>` is the main checkout, quoted, and `<wt>` is the session's own worktree.

`checkout -b <branch>` alone and the path forms `checkout -- <paths>` and `checkout <rev> -- <paths>` are judged as paths: `rules.checkout_moves`), `merge`, `pull`, `apply` that writes the tree and `read-tree -u` (`rules.ledger_git_moves`); a subcommand or a checkout, switch or reset word the shell computes, and git that `xargs` runs; and such a git call, or one that writes paths (`rm`, `mv`, `restore`, `checkout-index`, `checkout -- <paths>` or `checkout <rev> -- <paths>`), in a place the guard cannot tell (`GIT_DIR`, `--git-dir`, `--work-tree`, a computed `-C "$d"`), where a checkout with no `--` passes only as a branch: no positional word, or one plain name (no `.`, wildcard, magic, `~`, path separator, so `kit/x` stays refused, no part of a held path, and no `.md` name while the rulebooks' folder is held), never two words or `-p` (`rules.checkout_branch_only`); A wildcard part also matches an 8.3 short name, as FindFirstFile does (`rm A-LONG~?/LEDGER.md`, a file not written yet included: `rules.short_parts`). These wider forms bind every marked session but the PM's: a subagent, any agent's mark, `plain` and an unknown mark are bound; the owner's unmarked session and the PM's pass. One switch, `rules.ledger_wide_binds`, widens them to every session (an open owner question). While the machine config leaves a ledger key unread (docs/guard-core.md State "User config"), the guard cannot place the ledger: a main session's every edit, shell write and git path write is asked about (ASK) and a subagent's is denied (`rules.ledger_unread`); any other refusal of the call, a held path's first, wins over the ask. | `generated-file` | in any session, the owner's own too: a file tool edit or shell write, in a kit checkout, of a file `tools/render_content.py` writes (see docs/guard-jail-roles.md "Generated files") | `python "<checkout>/tools/render_content.py" --write`; the sentence before it names the file's source (the role file, the skill under `content/skills/`, `boot/`, or for a manifest `kit.json`, `hosts.json` and the host's renderer) to edit first |
| `write-jail` | an agent session's file tool edit or shell write outside its write roots, and git that changes a checkout outside them; see docs/guard-jail-roles.md "Write jail". The sentence names every root and says to ask the coordinator. Also a marked agent session's PowerShell `& (<subexpression>)` outside a repository with `kit-pm-data.json` (docs/guard-fallback.md "Fallback"), with `Instead: & <program> <arguments>`, and an agent session's .NET write to a relative or computed path ("Shell writes"), with the same call at the absolute path the PowerShell location gives (for a computed path, `<folder>/<file>`) | the same tool call or command aimed at the same file name in `<wt>` (else the temp folder); for git, `git -C <wt> <the same subcommand and arguments>`, and for a `git archive` with no `-C` the same call with `-C <wt>` after `git` (from the main checkout `-C "<worktree>"`, and an `-o` inside the main checkout aimed at `<worktree>` too: `rules.git_retarget`), so the archive is made in the checkout the call meant; for an existing file in an add-only folder, the same write to `<folder>/<new file name>` |

**Shell writes** (`kitlib/guard/rules_write.py` `write_targets`):
- Redirects.
- PowerShell write cmdlets and their aliases, with parameters matched by prefix. These include `Set-ItemProperty` (`sp`), `Start-Transcript`, `[IO.File]`/`[IO.Directory]` calls and `[IO.StreamWriter]`/`[IO.FileStream]` constructors (`::new(...)`, `New-Object`; a FileStream counts as a write even when opened only to read; `rules.net_writes`, `rules._net_ctor`). A cast (`[IO.StreamWriter]'x.txt'`) is not read: it is judged as a call whose path the guard does not read (below), an unusual spelling (docs/guard-v2.md B7). A StreamWriter constructor (`::new`, `New-Object`) whose first argument is not a plain string is judged only as such a call, so `[IO.StreamWriter]::new($stream)` from a worktree is not refused. `\\?\<drive>:\x` and `\\.\<drive>:\x` are judged as `<drive>:\x` (`rules.NET_DEVICE_RE`, `rules.net_placed`). A literal absolute path is judged where it points (`Copy` writes its destination, `Move` and `Replace` their paths), and a relative one where the PowerShell location puts it (`rules.net_relative`, tests/guard/test_dotnet_paths.py). An agent session's relative one, or a call that reads a relative path (Copy's source), is then refused under `write-jail` all the same, with the same call as the alternative, every relative path of it made absolute where the location puts it (`rules.net_process_dir`, `rules.net_retarget`, tests/guard/test_dotnet_relative_write.py): .NET reads it against the process's directory (`[Environment]::CurrentDirectory`), which `Set-Location` does not move and the guard cannot see, so a docs-writer's `[IO.File]::WriteAllText('docs/ROSTER.md', ...)` from its worktree wrote the main checkout. It is a deny, not `unplaced`, whose default warning would not have stopped that write; the absolute path is the whole fix. A path the line computes, and a relative one after a move to a location the line computes (`cd $x`), is refused for an agent session from every location under `write-jail`, with the same call at `<folder>/<file>` as the alternative: `<folder>` is the PowerShell location when it is a linked worktree the session may write, else the session's own folder (`rules.ps_drive_jail`, tests/guard/test_dotnet_var_write.py). Where the machine config holds `unplaced` at deny, a subagent's is refused under `unplaced` first; a marked session (coordinator, pm) passes that check and is refused under `write-jail` at every mode. A `$p` assigned a literal earlier on the line is not read, since anything between may change it. A docs-writer's `cd <worktree>; $p='docs\guard.md'; ...; [IO.File]::WriteAllText($p,$t)` wrote the main checkout under `unplaced`'s default warning. `OpenRead` and `OpenText` are reads. A call whose path the guard does not read (inside a quoted word, a method named with no `(` after it, as before `.Invoke`, fewer arguments read than the ones it writes, or arguments holding a smart quote, a here-string, a `#`, a `${`, or a `$(` beside a `"`, where the parse may lose its place; `rules._net_lost`) or cannot place (a driveless path, a share path `\\host\<drive>$\x`) is judged as a write to the directory the line runs in, under the repository's roles there, for every session (`rules.write_targets`, `rules.net_stand_in`): refused outside a worktree, allowed in one. For those, and for the owner's own session, the guard does not judge the process's directory (docs/guard-fallback.md "Known limits"). A path a write cmdlet takes from the pipeline, when the line binds none of the parameters the pipeline would fill (`'x.txt' | Remove-Item`, `Get-Item x | Set-Content -Value y`, `$f | New-Item -Name x.txt`; `rules.PSCmdlet` piped), is one the guard cannot place, since the text does not show what the command before the `|` sends (`rules.PIPE_UNPLACED`): refused from a main checkout, passed from a worktree (tests/guard/test_ps_drive_paths.py). The paths Copy-Item takes from the pipeline are what it reads, so for it that path is its `-Destination`.
- cp, mv, rm, touch and tee; `sed -i`, `perl -i` and `patch`; dos2unix, unix2dos, mac2unix, unix2mac and `sponge` (every operand, with no read of their options); `ruby -i` (its files, under every folder `-C` or `-x` names; `rules._ruby`). ruby, like perl, is read for options after its script operand too, so `ruby tool.rb -i <file>` is refused outside the roots: accepted strictness.
  - awk and gawk (`rules._awk`) write every file operand (not `-`, not a `var=value`) when gawk's inplace library is loaded: `-i inplace` in any spelling (`-iinplace`, `--include[=]inplace` or a unique prefix, `-W include[=]inplace`, `inplace.awk`), `-f inplace` or `-l inplace`, any `-i`, `-f` or `-l` value the line computes (so `gawk -f "$SCRIPT" <file>` writes its file), or program text holding `@include` and `inplace`. `-v inplace::enable=0` is not read, so its files still count. A file `-d`, `-o` or `-p` names (`--dump-variables`, `--pretty-print`, `--profile`) is a write too, and those options with no file write theirs in the working directory. An option the guard does not know takes no value, so the words after it count as files. awk with none of these writes nothing.
  - vi, vim, nvim, ex and ed (`rules._editor`) write every file operand, and the script output file `-w`/`-W` names. An editor run that only reads its file (`vim -es -c q <file>`) is refused all the same outside the roots: accepted strictness, since the guard does not read the commands.
  - cp, mv, ln and install (`rules.CopyArgs`) write the directory `-t` names, also inside a cluster (`-rt <dir>`, `-t<dir>`) or as `--target-directory[=]<dir>` or any unique prefix of it; else the last operand. A long option that is unknown or ambiguous, or an option that is not literal, makes every operand a target. mv also writes its sources; `install -d` writes every operand; `ln <target>` alone writes the working directory.
- `curl -o` (in `--output-dir` when given; an absolute name both as written and in that folder, since curl joins the two), `wget -O` (not `--spider`) and `rsync` (not `-n`/`--dry-run`).
- `robocopy` and `xcopy` from any shell, and cmd copy, del and move.
- These write into the working directory, or into the folder they name:
  - `Expand-Archive` with no `-DestinationPath`, and `Copy-Item` and `Move-Item` with no `-Destination` (`rules.PSCmdlet` here), unless the pipeline may give that path (above);
  - `tar -x`, from PowerShell too (Windows' own `tar.exe`), or every folder `-C` names, a relative one read from the one before it (`-C <a> -C b` is `<a>/b`; `rules._tar`). A `-C` is read in a cluster after letters that take no value (`-xvC <dir>`, `rules.TAR_FLAGS`), as `--directory` down to `--dir` and as bsdtar's `--cd` (Windows' `tar.exe`), and in an old-style first word, whose letters take their values in turn (`tar xCf <dir> a.tar`, `rules._tar_old`). A `C` that may be another option's value (`-xfC <dir>`, `-NC<dir>`, `--exclude -C<dir>`, after a letter the guard does not know) judges the working directory as well (`rules._tar_word`). An extraction to standard output writes no file and is a read: `-O` in a cluster before any letter that takes a value or that the guard does not know (`-xOf a.tar`, `-xvOf a.tar`, `-x -O`, the old-style `xOf a.tar`), or `--to-stdout`; in `-xfO` the O is the archive's name, and `--to-command` still writes (`rules._tar_stdout`);
  - `unzip` (or `-d <dir>`; not `-l`/`-t`/`-v`/`-Z`/`-p`);
  - `Start-Process` redirects.
- Code given on the line counts as a write to the working directory: `python -c` or a script on stdin (any `python`, `python3.12`, `py` or `pythonw`), `node -e`/`-p`, `ruby -e` and `perl -e`. `python -c` is read in any spelling (`-Ic`, `-cCODE`, after `-X <v>`, `-W <v>` or `--check-hash-based-pycs <v>`; `rules.py_program`). Whatever the code is, the guard does not read what it writes: a `python -c` that only reads, `-I` or not, is a write of the directory it runs in like any other (tests/guard/test_pyreads.py; tests/guard/extra_rows.py). Run it from a worktree, or read files with the Read and Grep tools.
  - PowerShell: a python run is a write of its working directory, a script or module too, when any word of a PowerShell command on the way to python (python's own, or the text of a `bash -c` around it) holds a double quote, is empty, or holds a blank and ends in a backslash (`rules.ps_native_unsure`). Windows PowerShell 5.1's native-argument quoting can hand python other words than the guard read: it passes an inner double quote unescaped, drops an empty argument (so `python '' -c "<code>"` runs code), and wraps an argument with a space in quotes without doubling a trailing backslash. So `python tools/x.py --note ''` from PowerShell is a write of its working directory.
  - Start-Process (and its aliases `start`, `saps`): a python it starts is a write of its working directory, a script or module too. It gets one command line the guard re-splits with the quotes taken out, so the words python reads are not the ones the guard read. The directory it writes is the command's own and also its `-WorkingDirectory` when one is given (`commands.run_dir`, docs/guard-core.md "Parsing").
- find `-delete` writes to find's paths.
- A writer that a bash find's `-exec`, `-execdir`, `-ok` or `-okdir` runs writes to find's paths too, when the guard cannot place its target (`rules.find_exec_writes`). That target is:
  - the `{}` find fills in;
  - a path the nested line computes, such as the `"$1"` of `sh -c 'rm "$1"' _ {}`;
  - a relative path at `-execdir`'s unknown place.

  Each start path of each find around the writer is judged as its target, or the directory find runs in when it names none, through any shell nested between (`rules.find_runs`). So `find <outside> -exec rm {} +` from a worktree is refused as `find <outside> -delete` is, and the alternative runs the same find on the worktree; `find <outside> -exec grep -l x {} +` still reads. A start path the guard cannot place passes from a worktree, as any target does (tests/guard/test_jail.py `ShellForms.test_find_exec_writer_is_judged_where_find_searches`).
- A writer fed by `xargs` with no literal target writes the working directory.

A write target that is not literal (a variable, a substitution) is denied when the command runs in a main checkout or a place the guard cannot tell (fail closed). Under PowerShell it is denied from every location (`rules.shell_writes`): a linked worktree or any other place git can tell, a main checkout, a place git cannot tell and an unknown location (after a computed `cd`) alike, since one `$p` or `(Join-Path ...)` can name the main checkout. The `main-checkout` rule refuses a role that may not edit one, and `write-jail` refuses any other agent session, the coordinator's mark in a main checkout included (`rules.ps_drive_jail`). In every shell, a relative target after a move to a location the guard cannot tell (`cd $x`) is refused the same way, as `unplaced`, for an agent session whose role may edit a main checkout (tests/guard/test_unknown_dir_jail.py). So is a write in the line a shell Start-Process starts in a computed `-WorkingDirectory`, which leaves that line no directory as an unknown `cd` does (docs/guard-core.md "Parsing"). The owner's session is not held. So `Set-Content $env:TEMP\x.txt` from a worktree is refused; name the temp path literally. `-Path: x`, a colon then a space, binds the next word as `-Path x` does, and `-Destination:$p` binds its computed rest to `-Destination` (`rules.ps_params`, `rules.PS_NAMED_DYN_RE`); an en dash, an em dash or a horizontal bar names a parameter as `-` does (`shell.PS_DASHES`). A PowerShell argument in `( )` (`Set-Content (Join-Path a b) x`, `-Path:(...)`, `-Destination(...)` touching its parameter, and a `( )` touching any other word, which PowerShell passes as the word and then the `( )` as the next argument: `Copy-Item a.txt(...)`, `Set-Content(...)`, `'x'(...)`, `$x(...)`, `[string](...)`) is one such word whose commands are read as nested ones (`shell._Scan.ps_paren_arg`), unless the command's first word, or the first after an assignment's `=`, is a keyword that takes one (`if`, `foreach`, `while`, `switch`; `shell.PS_PAREN_KEYWORDS`, `shell._ps_keyword_led`): `Copy-Item data (...)` passes an argument. A `(` that does not touch the word before it is an argument whatever stands between: a space, a comma, a redirection (`Set-Content -Value hi 2>&1 (...)`), a backtick line continuation or a `<#comment#>`. A redirection to a `( )` or a `{ }` (`'x' > (Join-Path a b)`, `'x' > { ... }`, which writes to the script block's text) is a target that is not literal, and the `( )`'s commands are read as nested ones (`shell._Scan.target`). A `( )` inside a word's `[ ]` index is part of that word (`$x[(...)]`, `shell._Scan.word`). A `(` touching a member access (`$s.Replace('a','b')`, `'abc'.Replace(...)`, `[IO.Path]::Combine(...)`, `(Get-Date).AddDays(1)`; `shell._PS_MEMBER_HEAD`, `shell._PS_MEMBER_TAIL`) is a method call: the `( )` stays a group and the word, the method's result, is not literal, judged where it binds like any other word. Every PowerShell writer is also held by one coarse rule that does not depend on how the scanner read a `(` or a `{` (`rules.ps_unread`): a write cmdlet, an `Export-*` cmdlet, a copier (`robocopy`, `xcopy`), and `curl`, `wget` or `tar` run from PowerShell write a target that is not literal, standing for what the guard does not read, when any argument is not one it reads. A cmdlet's argument must be a plain word or string, a variable, or a string holding variables (`rules.PS_CMDLET_ARG_RE`); a native program's a plain word or string (`rules.PS_PLAIN_ARG_RE`), since PowerShell spreads a splat, or an array in a variable, into its arguments. An `Export-*` cmdlet with no spec has every positional, word after a parameter and colon value judged as its path, bar the value of `-InputObject`, `-Depth`, `-Encoding` or a common parameter (`rules.ps_export_targets`). The one value of a parameter that names no path (`rules.PS_VALUE_PARAMS`: `-Value`, `-Encoding`, `-Filter`, `-NewName` and a few more) is passed over when it holds no command: a word, string or variable, a `( )` the scanner reads as one word, or a here-string with no `$( )`, with member calls on plain arguments after it (`-Value $s.Trim()`, `-Value (Get-Date)`, `-Value @'...'@`; `rules._ps_value_end`); a `$( )` (`-Value "at $(Get-Date)"`), and a positional `( )` or here-string, which could be the path, are not. A splat (`Set-Content @a hi`, `robocopy . @a`), a script block (`-Path { $p }`, a delay-bind `-NewName { ... }`), a type's member call (`[x]::y(...)`), a `( )` touching a group's `)` (`$a.M(1)(...)`), a word after an unquoted comma (an array binds to the parameter before it: `-Value 'a','b' x`), and a command that is split (below) or followed by a `( )` or `{ }` no value accounts for each make such a target. So `Remove-Item a.txt,b.txt` and `curl.exe -o x.txt -H $h` are refused from every location. A PowerShell redirection whose target is not one plain word, string or variable (`'x' > ` followed by a line continuation and `(...)`), or that has none the scanner read (`'x' > <#c#>(...)`), is a target that is not literal too (`rules.write_targets`). When more of the command follows a group, a method call's included, before a separator (`Set-Content -Value $s.Trim() -Path x`, `Sort-Object { $_.Length } -Descending`), the scanner has read the rest as commands of their own, so the command is marked split (`shell.Command.split`): `rules.ps_unread` stands for the arguments past the group, and the line is not clean (`commands.expand`), which `fallback.check` refuses as `unreadable` for a role subagent. A keyword's own `( )` and `{ }` (`if (...) { }`, `$r = if (...)`, `foreach`, `try`, `catch [T] { }`, `function f(...) { }`) split no command (`shell._ps_keyword_led`), which reads only a keyword or `=` spelled bare: a quoted `'if'` or `'='` is an argument. Two exceptions: `$PWD` or `${PWD}` with a literal rest (`"$PWD\x.txt"`) is read as the directory the command runs in plus that rest, and judged as a literal path, unless that directory is unknown or the write is not the line's only command (`rules.ps_pwd_path`). `$PWD` can be set under many spellings of its name (`sv PWD`, `-OutVariable ('P'+'WD')`, `[scriptblock]::Create(...).Invoke()`), and only code that runs before the target is read can do it, so a write fails closed when an operator stands before or after it (a `;`, `&&`, `||`, newline or pipeline, a script block or `( )` group it is inside, or one among its own arguments: a method call's `( )` or a script block `{ }`), or when a word of its own runs code (an argument `( )`, an index `[(...)]` or a `$( )`): `Set-Content "$PWD\x.txt" x` is judged as a path, and `Set-Content a.txt x; Set-Content "$PWD\x.txt" x` is refused. A line whose write target does not use `$PWD` is not held by this. And `$null` is no file. Under bash and cmd a target that is not literal is not denied from a linked worktree or any other place git can tell. A `cd` inside a PowerShell `$( )` or argument `( )` moves the location for the command holding it and every later one, so their directory is unknown (`shell.track`).

### Kit paths in advice

An alternative that runs a kit tool (`rules.lock_tool`, `rules.kit_tool`, the `wrapped-gate` alternative's `rules.bare_wrapper`) names it under one folder, `rules.advice_kit`: the installed export the session's kit tools run from, the folder the session header names as `<kit>`, when the guard can tell it, else the kit the guard runs from (`Ctx.kit`).

- The guard names the export the machine's plugin marketplace names now (`kitlib.pluginsource.current_folder` under the `plugin` `export_dir` of the user config, default `%LOCALAPPDATA%\pm-kit\plugin`, on Linux `<profile>/.local/share/pm-kit/plugin`), when that folder has a 12-hex-digit name and holds `.pm-kit-export` and `kit.json` (`rolepolicy.EXPORT_NAME_RE`, `rolepolicy.EXPORT_FILES`) and its marker names the kit checkout the guard is from (`kitlib.pluginsource.export_checkout`): for a guard that runs from a kit checkout, that checkout; for one that runs from an export (`.pm-kit-export` in `Ctx.kit`), the checkout that export's own marker names.
- Otherwise (no user config, no marketplace file, an export made from another checkout, a guard's export whose marker names no main checkout) it names `Ctx.kit`.

A session's tool hook can run from another export than its start hook did, and from one a refresh has since replaced, which prune later removes. An alternative naming the hook's own export would then send the agent to a folder that may be gone. The current export is the one prune always keeps, and the one `kitlib.host.headerfollow` tells the session its header names (it compares the header's folder with `rules.advice_kit`), so the alternative and the session's current header name the same folder. Known limit: a header written under another export root (the record lives in `<root>/headers`, so a move of `export_dir` loses it) gets no header update, and the alternative names the current export under the new root.

The hook is not told which folder the session's header named, so a session started on an older export is pointed at the current one. The `heavy` rule lets an interpreter run that export's `tools/gate.py` and `tools/machine_lock.py run` as it does the kit's own (`rules.kit_wrapper` through `rolepolicy.kit_export`, which takes any export folder right under the export root, the current one or not, that is neither inside nor holding a folder the session may write), so an alternative the guard gives is not itself refused as heavy (tests/guard/test_advice_workdir.py).
