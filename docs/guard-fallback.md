# Shell guard: fallback, lock MCP, session mark and agent names

Part of docs/guard.md (the index); the sections below are moved there unchanged.

## Fallback

`kitlib/guard/fallback.py` `check` runs only when the parse is unclean. It catches mistakes, not attackers: an unclean line is refused when it touches a main checkout, a heavy program or a protected path, and a plain line is never denied by it.

- **Modes:** the refusals below follow docs/guard-core.md "Rule modes". A pattern whose rule is off (`wrapped-gate` by default) is not looked for. `unreadable`, `heavy` and `unplaced` warn by default: the warning is kept and the check goes on to the next pattern and the steps after it, so only a kept rule's deny (a re-read one, `git-push-pmdata`) stops the line.

- **The owner's tools by name:** first, in every session but the owner's own, a line whose text names the hub tool (`hub.py`, `tools.hub`, `-m hub`, and the kit command's `kit hub`, `kit.py hub` or `tools.kit hub`) is refused as `hub-owner-verb`, one naming the lock CLI (`machine_lock.py`, `tools.machine_lock`, `-m machine_lock`, `kit machine_lock`) as `owner-tool`, and one naming the owner's delegation list (`owner-delegations`, any case) as `owner-delegations` (`fallback.NAMED`; `-m` as the parsed rule reads it, alone or ending a flag cluster such as `-Im`, its module joined or not and maybe quoted: `-m 'hub'`, `-BIm"hub"`, `fallback.PY_M`), read verbs included: the part the guard cannot read may run an owner verb or an owner-only write. Another file whose name only holds the word (`test_rules_hub.py`, `hub.pyw`, `test_machine_lock.py`) is not the tool. The part of the line holding the name (from the last `;`, `|`, `&` or newline before it to the next) is read again first (`fallback.named_reread`): a hub owner verb there (`rules.hub_owner_run`) gives the parsed rule's own refusal, its question alternative included, a lock owner-only write gives `owner-tool`'s with its `status` line, and a write of the delegation list (`rules.owner_delegations`) gives `owner-delegations`'s with its read line. Otherwise the reason says the line names the tool and `Instead:` is `fallback.plainly`'s script-file run (tests/guard/test_rules_hub.py `test_an_unclean_line_naming_the_hub_tool_is_refused`, tests/guard/test_rules.py `OwnerLockTools`).
- **The roles' tools by name:** next, for a subagent only, text naming `tools/backlog.py` (`backlog.py`, `tools.backlog`, the kit command's `kit backlog`; `fallback.BACKLOG_NAME`), not for a host's unidentified subagent, and text naming `gate.py allow` (`gate.py`, `tools.gate` or `kit gate`, then the word `allow` in the same part; `fallback.GATE_ALLOW_NAME`), unless `gaterole.may_allow` lets the session allow (`fallback.named_runs`). A name the rules have already read is passed over: one in a literal word, or a heredoc or redirect target, of a top-level command whose program is literal and runs no text (`fallback._read_at`), so a commit message or a `grep` naming the tool is a mention, unless that command's output is piped, through its pipeline, into a shell, `eval`, `source`, `Invoke-Expression`, `cmd` or a python reading standard input as code (`fallback._pipe_runner`): then the name is in the runner's code. Its heredoc or here-string (`cat <<'EOF' | bash`), or the files `cat F` or `Get-Content F` names (`fallback._piped_text`, read as a script file is, on the line only and not inside a script file), is judged as a script file is (`backlogrole.judge_text`), and any other text (`curl ... | bash`) is refused as `backlog-role` (or `gate-allow`), as the guard cannot see it. Otherwise the part of the line holding the name (from the last `;`, `|`, `&` or newline before it to the next) is read again and judged by `backlogrole.runs` or `gaterole.shell`: a refusal there is given whole, after the "could not read" sentence; a part that reads no more cleanly, or whose program is computed, is refused as `backlog-role` (or `gate-allow`), as the guard cannot judge the run for the role. Its reason asks for the tool's verb run directly, as a command of its own, and its `Instead:` is that bare command, `python <kit>/tools/backlog.py -C <worktree> <verb> <arguments>` (`backlogrole.literal_form`; `gate-allow`'s is its own, to ask the coordinator), never a script file, which is read too (docs/guard-jail-roles.md "Backlog roles"). A part read whole that the rule lets run passes (`bash -c "cd $W && python tools/backlog.py show X-1"`). A main session is not judged here: the tool's own check holds it (tests/guard/test_backlog_role.py `Unread`).
- **Patterns:** git_guard's (one repo's `git_guard.ps1`) plus the kit's git rules.
  - When the directory is a main checkout or a place git cannot tell: bulk add, `commit -a`, `checkout`/`switch`, `reset --hard`, `clean`, `stash`, `restore` (unless it only unstages); `commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `pull`, `apply`, `update-ref`.
  - Anywhere: `branch -D`, `worktree remove`, the ref writes `git-shared-ref` judges (only in a session `rules.shared_ref_held` holds; `fallback.SHARED_REF_PATTERNS`: `update-ref`, a push whose repository is `.`, a `file:` URL, a path or `--repo`, a push whose repository is computed or starts at `~`, a `fetch` or `pull` with a `:` that is not a URL's, `--prune-tags`/`-P`, `--tags`/`-t`, `--update-head-ok`/`-u` or `--stdin` (and the starts of them git reads, `--ta`, `--std`), a forced `tag <name>` (`-f` in a cluster, or `--force` down to `--fo`), a `-c remote.<name>.fetch`, `remote.<name>.pruneTags`, `fetch.pruneTags` or `rebase.updateRefs`, `symbolic-ref` with two names or `-d`, `replace` but a listing, a `notes` write verb, `branch` with `-f`, `-m`, `-M` or `-C`, `tag` with `-f` or `-d`, `checkout -B` or `--ignore-other-worktrees`, `switch -C`, `--force-create` or `--ignore-other-worktrees`, `worktree add -B` or `-f`, `rebase --update-refs`, `remote remove`, `rm`, `rename`, `set-head` or `add --mirror`, `fast-import` and `filter-branch`), push to main (with no `push_block`, only a re-read deny counts: a delete or a forced push of main), push `--no-v...`, `send-pack`, `http-push`, `remote-<helper>`, `git-send-pack`, `git-http-push`, `git-remote-<helper>`, and git push or a git subcommand with a computed word (only where the repository has `kit-pm-data.json` or git cannot place the directory, and not in the owner's own session), the wrapped gate, root searches.
- **Which directory:** the main-checkout patterns are judged in the directory of the top-level command that holds the match, following a literal `cd` before it. The call's directory is not used alone. The git pattern reads a quoted `-C "<path>"`.
- **A pattern match:** the text from the match to the next `;`, `|`, `&` or newline is read again as a command and the parsed rules run on it. For an `owner-tool` or `wrapped-gate` match, and a name in `fallback.NAMED`, the text read again starts where the match's command starts, after the `;`, `|`, `&` or newline before it (`fallback.segment_start`, `fallback.SEGMENT_RULES`), so the program word is read with it: a match on the tool's name inside `kit machine_setup ...` reads the kit command, not its arguments alone. When that read gives no refusal, the text is read again from the match itself, as for every other pattern: a computed program or an open quote at the start of the part (`$PY tools/machine_setup.py --apply`, `echo 'x python tools/machine_setup.py --apply`) leaves the run unreadable from there, and read from the name it is the owner's tool (tests/guard/test_kit_command_forms.py `Unreadable`).
  - A rule that denies gives the deny, its real `Instead:` included, after "The guard could not read this command; write the program name literally. Why: <reasons>."
  - No rule denies: rule `unreadable`. The sentence ends by saying to make every program name and nested shell text literal or to write the commands to a script file with the Write tool, and `Instead:` names that script's run in the temp folder for the line's shell (`fallback.SCRIPT`, `fallback.SCRIPT_RUNS`). The guard never rewrites the refused line. Every `unreadable` refusal, and the fallback's `write-jail` and `git-push-pmdata` ones, take their alternative from `fallback.plainly`, so none repeats the refused line.
- **A heavy program's name:** the same, unless the session holds the lock. A program named by a variable is refused as `heavy`, the `machine_lock.py run` form naming `<the program $X names> <args>`.
- **Anything else:** a subagent gets `unreadable`; with that warned, it is judged on as a jailed session is.
  - A session the write jail holds (a subagent, a mark in `guard_agent_marks`) gets `unplaced` when the line holds the word `git` (`fallback.GIT_WORD_RE`; `.git` and `GIT_DIR` are not it), read or write, from any place: the part the guard cannot read may point git at a checkout it cannot place. The PM data and main-checkout steps below still run.
  - Then every session (the jail's ones reach this step once the steps above warn) gets `unreadable` when a command runs in a main checkout, or a place git cannot tell, and that command runs one of:
    - a program the text does not name;
    - a shell (`bash`, `sh`, `powershell`, `pwsh`, `cmd` and the like), `eval`, `iex`/`Invoke-Expression` or `source`/`.`; this covers `-enc`/`-EncodedCommand` and a pipe into a shell;
    - git with a subcommand or read option the text does not name.
  - The same line from a worktree passes, unless the repository has `kit-pm-data.json`: then any session but the owner's own gets `git-push-pmdata` (deny) for such a line from any place in it, as the hidden program may be `git push --no-verify`.
- **`& (<subexpression>)`:** PowerShell's call operator on a subexpression leaves the line clean ("Known limits"), so the steps above do not judge it. `rules.call_subexpr_pmdata` gives the same answers on a clean line: `git-push-pmdata` in a repository with `kit-pm-data.json`, else `unplaced` (warn by default) for a session the jail holds, whether or not the line holds `git`.

Tests: tests/guard/test_rules.py ROWS, tests/guard/shell_rows.py, tests/guard/review_rows.py and tests/guard/extra_rows.py (428 rows at the time of writing); tests/guard/test_session.py for the rules that read the session mark.

### Known limits

The guard reads the command line, not the shell's state:

- **Aliases and functions** are not seen; the name is read as a program. This holds whether they are defined in an earlier call, in a profile, or earlier on the same line (`alias g=git; g push`). It also holds for git aliases in `~/.gitconfig` (only `-c alias.x=` on the command line is read: `git-alias` warns and the command it runs is judged; a shell alias, `!`, ends the expansion). Aliases in git's config are not looked up (the guard catches honest mistakes, not evasion). `rules.GIT_BUILTINS` is git 2.55's builtin list, the names an inline alias cannot hide.
- **`& (Get-Command x)`** and other PowerShell calls of a computed command object are not resolved to the program they run. The parser reads `& (<anything>)` as a program the text does not name, with the subexpression's commands read as nested ones (`kitlib/guard/shell.py`), but the line stays clean (`commands_nested.call_subexpr`): only `rules.call_subexpr_pmdata` judges that program, as `git-push-pmdata` in a repository with `kit-pm-data.json` and, anywhere else, by denying it to an agent session (`unreadable` for a subagent, `write-jail` for a marked one). For the owner and `plain` no other rule (`heavy` included) sees what it runs. A dot-source of one (`. (Get-Command x)`) is not read so.
- **Direct edits of a repository's config:** `git-remote-rewrite` reads `git remote` and `git config`. An edit of `<git common dir>/config` by a file tool or a shell write (`sed -i`, `Set-Content`) is judged only by the path rules (`main-checkout`, `write-jail`), which do not hold every session, so it can repoint a remote unseen.
- **`coproc`** is not modelled; the command after it is read as a program named `coproc` (`coproc git stash` parses clean, as one command `coproc`).
- **Pre-push config load:** when the clone has no base commit at all, neither the replaced remote main commit nor any default-branch ref, `kitlib/guard/prepush.py` falls back to the defaults: no `push_block`, main read from the git files (docs/kit-json.md "With no file"). The gate-OK check is then skipped; the fast-forward and delete refusals still apply to main, and to `main` itself whatever `<remote>/HEAD` names (read from the code; no test covers it). A base `.kit.json` that sets no `repo.main_branch` names main the same way (`test_a_base_that_names_no_main_branch_reads_origin_head`).
- **Brace groups read as written:** a bash brace group with a quoted, escaped, `$` or space alternative (`{a,"b"}`, `{a,$x}`), and a sequence (`{a..c}`, `{1..9}`), is left as written, so the words bash makes from it are not judged: a path rule sees the one word with its braces (kitlib/guard/shell.py `_brace_group`).
- **`Invoke-Expression`/`iex`, `eval` of a computed string:** the string is not evaluated; a literal argument is parsed, a computed one leaves the parse unclean.
- **`case` statements** are read as unclean (an unmatched `)`), so a subagent's `case` line is refused as `unreadable` and a jailed session's as `unplaced` when it holds `git` (both warn by default); a session the jail does not hold is not refused.
- **Known gaps, not judged (the guard is a speed bump, not a jail):** network writers (cast and rest forms and others); PowerShell `iex` with hidden env values; long hub paths folded; role-lock bypasses, PowerShell 5.1 quote splitting and the inner command of `run`; `cd` spellings; git holes (round 4) and unjudged git ref writes (a `symbolic-ref` then `update-ref`, an alias, a link made earlier on the same line); write-jail writer gaps and the jail refusal's read-only text; computed `hooksPath` keys.
- **What git-shared-ref does not read:** refspecs and remotes git takes from its config files (`remote.<name>.fetch`/`push`, `branch.<x>.remote` of `.`, `push.default`, `url.<base>.insteadOf`/`pushInsteadOf`, `remote.<name>.pushurl`, an include, `GIT_CONFIG_*`), so a named remote whose URL is this repository is judged as a remote; a fetch, pull or `remote update`/`prune` on config the line sets that the rule does not read (`-c` of `include.*`, `includeIf.*`, `url.*` or `remote.*` other than `remote.<name>.fetch` and `*.pruneTags`, or a line that moves `HOME`) is refused instead, per git call, so `fetch --all` too, but not in a scratch repository (`rules_gitref._injected_config`), and git re-pointed by `GIT_DIR`, `GIT_CONFIG_*` or `--config-env` is the write jail's for every session the rule holds; `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` on the line are not read there, so a refspec they give that writes the checked-out main is not seen (git refuses that fetch only without `--update-head-ok`, a flag the rule does not refuse by itself); a push into another local repository by its path (a remote too); a symbolic ref made earlier and written through later; `GIT_NOTES_REF` and `core.notesRef`; `rebase.updateRefs`, `pull.rebase` and `branch.<x>.rebase` set in a config file (only a `-c` on the line is read; a pull with `-c rebase.updateRefs` on and no word on the line that it merges is taken to rebase); `rebase <upstream> <branch>`, which checks out and moves that branch; `git replay`, `git filter-repo` and `git history` (git 2.55: its `--update-refs` moves branches); a push to `~<user>/` (refused as unread). A refspec the shell computes whole, or one beside an option the guard does not know, is refused as unread. The coordinator's stray-ref allowance reads the session mark, which a host gives only a main session it can tell apart; on Codex, where a call the host cannot tell apart counts as a subagent's, a coordinator gets no allowance, and its stray-ref delete is refused as a worker's.
- **Rules the fallback does not run:** `busy-wait`, `git-hooks-path`, `owner-identity`, `kill-by-name`, `git-plain-commit`, `interpreter-git` and `cmd-reparse` are not in `fallback.PARSED_RULES`; an unclean line meets only the fallback's own patterns, and `cmd-reparse` judges only the commands the parser read (docs/guard-jail-roles.md "Batch files and cmd.exe").
- **cmd-reparse:** its limits are in docs/guard-jail-roles.md "Batch files and cmd.exe" (**Limits**).
- **busy-wait:** off by default (docs/guard-core.md "Rule modes"); when on, a loop in a script file, or in the Monitor tool, is not read. A bound the rule does not know (an `-eq` count, a check inside a called script) reads as none, so that loop is denied. Any `-lt`/`-le`/`-gt`/`-ge` reads as a bound, so `while [ $(pgrep -c x) -gt 0 ]; do sleep 1; done` passes though nothing ends it. A loop behind `time` or `nohup` (`time while true; do sleep 1; done`) is read as that program's arguments and passes. The alternative for a loop on the call's own line is the bounded loop alone: what came before it on the line (`F=x;`, `cd x &&`) is not kept.
- **git-hooks-path:** `git clone --template` and `git init --template` with hooks in the template are not seen. Abbreviated long options (`git clone --conf=core.hooksPath=x`) are not seen.
- **owner-identity:** an identity in the environment the session started with, in `GIT_CONFIG_PARAMETERS` or a `GIT_CONFIG_KEY_<n>=user.email` / `GIT_CONFIG_VALUE_<n>` pair, or set inside a script or program the line runs, is not seen. `git commit --author=<name only>` is not caught: git fills in the email from an earlier commit by that author, which can be the owner's; the rule matches the email, not the name.
- **kill-by-name:** `pkill` and `killall` that end processes by user, parent, group or terminal with no name (`pkill -u <user>`) pass.
- **git-stash-shared:** a tagged `push -m <tag>` still adds an entry, and while it is there the gate's stash guard refuses every gate and landing (docs/gate-rerun-checkout.md "The stash guard"). The fallback has no pattern of its own for it, so a stash the parser cannot pick out of a line (`echo 'x; git stash`), or one after a `cd` it cannot follow, meets only `unreadable` or `unplaced`, which warn by default. A stash run by a script or program the line runs is not seen.
- **git-plain-commit:** not read (`rules.py` above `COMMIT_VERBS`): a git alias from git's config files; a verb the shell computes or a script runs; `commit-tree` and `rebase`; a computed `-C`, `--git-dir` or `--work-tree`, which the unplaced handling judges. A word the shell computes after a hold (`git cherry-pick -n $X`) is read as a commit, though it may be `--commit`, which undoes the hold. A `--continue` of a sequence started with `--no-commit` makes no commit but is refused: git keeps that mode in the sequence's state, which is not read.
- **interpreter-git:** not read (`rules.py` above `INTERPRETER_LAUNCH_RE`): a script file, one in a temp or scratch folder too, and `python -m`; a program or a git name the code builds at run time (`'g' + 'it'`, `importlib`, `getattr`); other interpreters (ruby, perl, deno) and compiled programs; PowerShell's `Start-Process` and .NET's `Process`; a library that writes the repository itself (dulwich, pygit2, `open('.git/refs/...')`); a git command that is not at the start of its string (`'cd x && git commit'`); a git name the code is given from outside its text, as an argument (`python -c "...subprocess.run(sys.argv[1:])" git commit ...`) or through an environment variable (`G=git python -c "...os.environ['G']..."`); python or node run by a launcher (`uv run python -c ...`, `npx node -e ...`), whose code is the launcher's argument and not read; an option that takes the next word as its value and that the guard does not name (python's `--check-hash-based-pycs always`, a node option outside `rules.NODE_VALUE_OPTS`), whose value is read as the script, so the code after it is not read; a line the parser cannot read. It refuses honest code in two ways, both kept: a git read (`rev-parse`, `log`) is refused like a write, and a `'git ...'` string in code whose launch runs another program is read as git.
- **Hub writer code** (`backlogrole.HUB_WRITER_RE`): names only, so code built to evade it passes: `getattr(h, 'recordwrite')`, `importlib` with a built string, `from kitlib.hubsite import *`, the `serveviews.py` Views wrappers, a `)` in a comment inside the import's parentheses, a backslash before a CRLF.
- **Clearing the mark:** a marked session can start a child agent session with `PM_KIT_ROLE` cleared (`PM_KIT_ROLE= claude ...`, `env -u PM_KIT_ROLE claude ...`, `Remove-Item env:PM_KIT_ROLE`); the child is unmarked and counts as the owner. No rule denies it.
- **Environment changes beside git:** a change the guard does not read leaves git where the line shows it, in every session: `set -a` or `-o allexport`, a sourced script, a nameref, an assignment or `export` whose name the shell computes (`export $n=x`), `Set-Alias git`, `Start-Process -Environment`, and a `GIT_*` name outside `commands_env.GIT_ENV_NAMES` (`GIT_CONFIG_GLOBAL`, `GIT_EXEC_PATH`). So `. ./env.sh; git reset --hard` from a worktree passes, though the script may point `GIT_DIR` at a main checkout (docs/guard-fallback.md "Weakened checks, by row" A4, B4, B10 to B14). A literal assignment of a `GIT_ENV_NAMES` name (`GIT_DIR=x`, `export GIT_DIR=x`, `$env:GIT_DIR = 'x'`) still leaves that git's place unknown, so its write is refused as at an unknown place. Any git on a line the guard cannot read at all (`eval "$c"; git status`) is refused as `unplaced`, which warns by default ("Fallback"). The owner's unmarked session on Claude and the marks the jail does not hold (`plain`) are not jailed (`rules.git_jail` returns before `git_jail_unknown`), so their line passes.
- **Startup files:** a nested shell runs files the line does not show before its text: `bash --rcfile <f>` or `--init-file <f>`, and a login or interactive shell under a `HOME=<dir>` the line sets (`HOME=/x bash -l -c '...'`) reads that folder's profile. They are not read; git in the nested text is placed as written.
- **PATH and the exec path:** a `PATH` the line sets, or `git --exec-path=<dir>`, may make `git` or a git subcommand another program. The guard reads the word `git` as git and does not judge `PATH`.
- **Environment the line does not show:** a program the line runs that runs git itself (`python tools/commit.py`) gets the line's environment, but is not judged as git (git that python or node code on the line runs is `interpreter-git`'s, docs/guard-rules.md "Rules"). A PowerShell `function git`, `git -c include.path=`, a .NET `ProcessStartInfo` and a variable persisted by an earlier call (`setx`, User scope) are not seen.
- **PowerShell provider items:** only a literal item of a provider-aware item or content cmdlet (`PS_PROVIDER_CMDLETS`), on a line whose every command is a plain call of such a cmdlet, a listed read-only one or git (`ps_line_plain`), skips the path rules; any other env: item (computed, given to a native program or to Out-File, Compress-Archive, Invoke-WebRequest -OutFile, or on a line with an assignment, a member or static call, `&` or a dot-source) is judged as a file path. A literal one (`PS_PROVIDER_ITEM_RE`) is then a drive or provider path the guard cannot place (next item): refused in a main checkout, passed from a worktree (kitlib/guard/rules.py `shell_writes`; docs/guard-fallback.md "Weakened checks, by row" B16). When a provider-aware cmdlet's literal item is refused only because of its line, the refusal says so in one sentence and its Instead is the whole line run from the worktree (`rules.whole_line`: a statement before the call that sets what it reads stays with it; a `cd`, `Set-Location` or `Push-Location` into the top of a main checkout at the start of the line and a comment after its last command are left out, and a line with any other one, or a `Pop-Location`, gives the call alone, since it would move off the worktree), not a file to write (`rules.PROVIDER_ITEM_WHY`, `rules.ps_provider_word`; tests/guard/test_provider_paths.py).
- **PowerShell provider and drive paths in a write:** a PowerShell `FileSystem::<abs>` (bare or `Microsoft.PowerShell.Core\FileSystem::`) is read as `<abs>`, after a leading separator too (`\FileSystem::<abs>`, which PowerShell takes; `shell.resolve_path` with the shell, also for `cd` and the root search). A relative `FileSystem::<rel>`, bare or after a leading `\`, is read from the location, as a relative .NET path is (`shell.ps_filesystem_relative`; PowerShell reads it from the process's directory: "The .NET process directory" below). A relative path whose first folder is `.` or `..` is no provider path: `.\x.txt::$DATA` is a stream of `x.txt` in the location, placed as that file (`shell._ps_provider`); `..\x.txt::$DATA` PowerShell reads as a provider named `..\x.txt` and refuses, writing nothing, so placing it as the stream of `x.txt` in the folder above is the stricter reading; while `x.txt::$DATA` and `sub\x.txt::$DATA`, where PowerShell reads `x.txt` as a provider's name, cannot be placed. Any other `Provider::` path, or a drive whose name is anything but one ASCII letter (`Main:\x` after `New-PSDrive`, `1:\x`, `_:\x`, a non-ASCII letter), cannot be placed (`shell.ps_unplaceable`), unless the provider-items skip above already let it pass. It is judged as any target the guard cannot place: refused in a main checkout, passed from a worktree. A `cd`, `Set-Location` or `Push-Location` into such a place leaves the directory unknown, as bash's `cd $x` does, so a relative write after it is refused as running in an unknown directory; so does one to a relative `FileSystem::<rel>` (`FileSystem::.` included), which PowerShell reads from the process's directory, not the location (`shell.cd_target`), so a git write after it is judged as one in an unknown directory. The PowerShell-drive jail that refused these from a worktree and in a session that may edit a main checkout is cut: an unusual spelling, not an honest mistake (docs/guard-fallback.md "Weakened checks, by row" B16). Bash and cmd words and one-letter drives are read as before (kitlib/guard/shell.py, kitlib/guard/rules.py; tests/guard/test_ps_drive_paths.py).
- **The .NET process directory:** .NET reads a relative or driveless path against the process's directory (`[Environment]::CurrentDirectory`), which `Set-Location` does not move. The guard cannot see that directory. It refuses an agent session's relative or computed .NET path (docs/guard-rules.md "Shell writes"), but judges a driveless one, an unread call and the owner's own session's relative path where the PowerShell location puts them (docs/guard-fallback.md "Weakened checks, by row" B17), so the owner's session started in the main checkout that runs `Set-Location <worktree>; [IO.File]::WriteAllText('x', ...)` is allowed and writes the main checkout.
- **.NET writes an agent session may still aim at the process directory:** from a worktree, a StreamWriter constructor whose first argument the line computes (`[IO.StreamWriter]::new($p)`: it may be a Stream), a driveless or share path, and a call the guard does not read (`[IO.File]::WriteAllText.Invoke('x', ...)`) pass, since each is judged as a write to the directory the line runs in (docs/guard-rules.md "Shell writes"). Refusing a call the guard does not read would also refuse a line that only names one inside a string, such as a commit message.
- **A relative `FileSystem::` path and the process directory:** PowerShell reads a relative `FileSystem::<rel>` (and `\FileSystem::<rel>`) against the process's directory, as .NET does, not the location. The guard reads it from the location (`shell.ps_filesystem_relative`), so a session started in the main checkout that runs `cd <worktree>; Set-Content FileSystem::x.txt y` is allowed and writes the main checkout: a provider-path form, cut with the rest (docs/guard-fallback.md "Weakened checks, by row" B16), the same risk as the .NET one above. A `cd` to such a path is not read from the location: it leaves the directory unknown (the item above).
- **Start-Process -FilePath:** `rules.kit_script` reads the program word of a Start-Process call with a `-WorkingDirectory` from that folder, as it reads a script in `-ArgumentList`; PowerShell resolves a relative `-FilePath` from its location instead. It matters only when the program word is itself a kit tool and the repository lists it as heavy.
- **What the guard stops chasing:** the guard catches honest mistakes, not evasion, so each rule judges the form a mistake takes and names no workaround ("Weakened checks, by row" below). Besides the items above: an owner verb reached from python code that imports the hub tool rather than a parsed run of it (A1, docs/guard-owner.md "Hub secrets"); a token file named in a shell word with no literal path into the token folder (A2, docs/guard-owner.md "Hub secrets"); the reserve UI, the lock window or machine setup started from python code, standard input or a variable (A3, docs/guard-owner.md "Owner lock tools" and docs/guard-owner.md "Owner machine setup", their Limits); a lock verb handed on by a variable, a copy or standard input in a role session (B5, docs/guard-jail-roles.md "Role policy"); an alias in git's config (B1, "Aliases and functions" above); a ref reached through another symbolic ref, a link in the git directory, or a reftable (B6, B18, B19, the `git-shared-ref` row); a `[IO.StreamWriter]` cast (B7, docs/guard-rules.md "Shell writes"); a drive path with single backslashes in a python heredoc (B8, no rule); and, from a worktree, a PowerShell write target that is computed, a path on another provider or on a drive name longer than one letter, or a relative `FileSystem::` path, and the owner's own session's relative .NET path (B15 to B17, the items above).
- **Heavy `when_args`:** an argument counts at any position, so `dotnet new console -n build` is heavy.
- **write-jail reads the line, not the program:** a script or program the agent runs (a `.py` it wrote, `python -c`, a build tool) can write anywhere; the jail judges only the targets the command line names. What such a write puts in a repository reaches main only through a commit and a push, where `tools/commit.py` (docs/commit.md) and the pre-push owner-only paths (docs/guard-hooks.md "Owner-only commits") still check it; a write outside every repository is not checked at all. A target that is not literal goes unjudged under bash and cmd in a linked worktree or another place git can tell (docs/guard-rules.md "Rules"), as does a path a PowerShell cmdlet takes from the pipeline (docs/guard-rules.md "Shell writes"); a computed git subcommand is refused (`commands_git.git_dyn_word`).
- **In-place editors the guard does not read:** an `awk -f <progfile>` whose file holds `@include "inplace"` (the guard reads no program file); `sort -o`, uniq's output operand, split and csplit, gzip, bzip2 and xz, `iconv -o` and `emacs --batch`; vim's `-i <viminfo>`, written on exit, and its `-V<n><file>` verbose log; a write named inside a `-c` command or an ed command (`w <other path>`); the editor names view, rvim, vimdiff, gvim and red; and awk, gawk, ruby -i, the editors, dos2unix and sponge run from PowerShell, as sed and perl there (`rules.write_targets`).
- **BSD `xargs -S <size>`** is not read as taking a value: the size is read as the program, so the command after it (`sh -c '...'`) is not read.
- **A trap handler or `find -execdir` at an unknown place:** a relative write in it is judged as at an unknown place, so a subagent is denied `cd sub && trap 'rm -f x' EXIT` and `find . -execdir rm {} +`.
- **What the ledger rule does not read:** a recursive wildcard that does not pass through the ledger's folders (`del /s *.md`), since a wildcard is matched only at its own depth or above (`rules.ledger_glob`); a second hard-link name of the ledger, a rulebook or the digest; and shell wildcard syntax that `fnmatch` does not share (`[^x]`, `[[:alpha:]]`, cmd's trailing `?` and trailing dot), which is matched as `fnmatch` reads it. Git that rewrites the work tree but is none of the forms the Rules table names is not this rule's; `rebase`, `cherry-pick`, `revert` and `am` are among them. Other rules refuse them only in a main checkout or a place git cannot tell (`rules.git_main_rules`: `git-checkout`, `git-main-history`), and in a linked worktree or outside git none of them is refused for the ledger's sake.
- **write-jail with a git top at the home folder or above:** such a checkout holds the machine config folders, so the session gets no checkout root (docs/guard-jail-roles.md "No root on a machine config folder") and the alternative a refusal names writes to temp instead (`jail.destination`).
- **machine-config and git in another checkout:** git's pathspec into `.pm-kit/` is judged only in the PM repository's work tree (`delegfile.git_config`); in another checkout, `git checkout -- .pm-kit`, `git rm -r .pm-kit` and the like are not this rule's. Such a change reaches a remote only through a commit and a push, where the pre-push machine config secrets stage refuses the secrets (docs/guard-hooks.md "Pre-push").
- **machine-config and a program's own writes:** a script, build tool or `python -c` that writes into a machine config folder is not judged; only a file tool and the shell write targets the line names are.
- **machine-config and code on the line:** python or node code given on the line (`-c`, `-e`, standard input) that names `.pm-kit` is not read as a write (`rules.NAME_RE` is unchanged).
- **machine-config and a wildcard above the folder:** a wildcard whose literal folder is above `.pm-kit` is refused when its parts can match, on disk, an existing path that is or lies in the folder (`delegfile.glob_config_below`: `rm -r .pm*`, `Remove-Item <pointer>\*`, and PowerShell's top-level `Remove-Item *` in a checkout that has a `.pm-kit`, whose wildcards match a leading dot; in bash a part that starts with `*`, `?` or `[` skips dot-names, as bash without dotglob does, so `rm -rf *` is not this rule's). A path that does not exist is not judged (`rm -rf */__pycache__`), nor is one that matches no existing `.pm-kit`. A wildcard whose match reads more than `delegfile.WALK_LIMIT` folder entries is refused (fail closed), with its own text (`delegfile.walk_limit_refusal`): the word was too wide to check, so narrow it or name the files; it does not give the machine config folder's wording or say to ask the owner. `owner-delegations` still refuses one that can match the delegation list, and is checked first.
- **machine-config and the folder's parent:** a delete or move of a folder that only holds a `.pm-kit` (the checkout itself, the PM repository) is not this rule's; the write jail and `main-checkout` judge it as they judge any folder.
- **machine-config and pipelines:** a pipeline or `xargs` writer (`ls | xargs rm`, `Get-ChildItem | Remove-Item`) is judged for the delegation list only (docs/guard-owner.md "Owner delegation list"), not for a machine config folder.
- **machine-config by name:** a `.pm-kit` at the top of a checkout other than the pointer's is held for literal targets only; a wildcard there is held when its literal folder is that `.pm-kit`, or when its parts after the literal folder, folder parts included, match an existing path in that `.pm-kit` on disk (`delegfile.glob_config`, `glob_config_below`), and git there is not judged (above).
- **What the Dev Drive bound does not see:** writes the line does not name, so they land off the drive unjudged: tool caches under the user profile (pip, npm, NuGet, `.godot`, `%APPDATA%`; the owner moves them, docs/machine-setup.md), `git config --global` (`~/.gitconfig`), and writes made inside python or node code or any program the line runs ("write-jail reads the line, not the program").
- **write-jail temp is shared:** every session's temp root is the same folder, so one agent session may write another's scratch folder.
- **write-jail copy into an add-only folder:** only cp, mv, ln, install, `Copy-Item`, `Move-Item` and cmd copy and move are judged by the source's name. `robocopy`, `xcopy` and `rsync` into the existing folder, a source that is not literal, holds a wildcard or is drive-qualified (`D:name`), `-T`, and any option off the list in docs/guard-jail-roles.md "Write jail" are judged as the folder itself, so they are denied.
- **write-jail and options that are not literal:** cp, mv, ln and install read a word that is not literal (`"$F"`) as an operand, though the shell may expand it to an option such as `-t<dir>`.
- **write-jail and a lander in the main checkout:** a lander whose `cwd` is the main checkout gets the whole checkout as its root, so the jail adds nothing there; the `main-checkout` rule and `roles.lander` decide what it may write.
- **The lander's agent type:** the exception for landing verbs matches the payload's `agent_type` `pm-kit:lander`, the kit's own lander, which the coordinator dispatches by that name (skill land-branch), and `lander`, a repo's own `.claude/agents/lander.md` (docs/ROSTER.md); nothing else does ("Agent names"), so a lander another plugin registers is held like any subagent. The `<plugin>:<name>` form is INFERRED from Claude Code's plugin naming, not observed; check one real payload after the plugin install.
- **write-jail and a session's working directory:** the roots follow the payload's `cwd`. An agent started in another repository's checkout (a subagent of a session that runs there) gets that checkout, not the worktree it was told to work in, and is denied there.
- **Backlog roles and code:** `backlog-raw-write` reads code given on the line (`-c`, standard input, `-m`) and a subagent's script file one level deep, its first 256 KB (docs/guard-jail-roles.md "Backlog roles"): a script that script runs, a file the same line writes before it runs it (it is not there yet when the guard reads), a file named by a computed word and the rest of a file past 256 KB are not read, and a file in a code folder of the kit (`backlogrole._kit_code`) is not judged, so in the kit's own checkout a scratch python file importing `kitlib.backlog` under `tools/` or `tests/` is not refused. A main session's python importing it is not judged either: only the tool's own check holds a main session. Code that imports another kitlib module and gives it a `kitlib/backlog` path only as data passes (`backlogrole._tree_reach`): the guard reads the code, not what the kitlib function does with that path, so one that loads or runs it is not seen. The other way, a false refusal: a subagent's script that only reads the backlog's library (`from kitlib.backlog import store` to print a record) is refused as `backlog-raw-write` like one that writes, as the guard does not tell a read from a write in code; run the tool's read verbs (`show`, `next`) instead. So are honest shapes `backlogrole.piped_script` judges by the name alone: a script naming the tool is refused in `out=$(python gen.py)`, `echo "$(python gen.py)"` and `(cd sub && python gen.py)`; run it plainly. A script whose code holds nothing on the runner lists passes however else it loads code: a module it writes and then imports, a file it writes that a later command runs, and the like. A landed script (docs/guard-jail-roles.md "Landed scripts") is not judged at all, an owner-accepted limit (Q-2180): one that imports a helper module the worktree edited, or runs a script the subagent wrote (one that runs `git update-ref`, say), is not read past it. The trust adds no reach that a script a script runs lacks today. It also rests on the local main holding landed code, which the guard does not fully hold: a refspec written to a config file is not read (`git config remote.origin.fetch +refs/heads/x:refs/heads/main`, then a `fetch --update-head-ok`), nor is `git config receive.denyCurrentBranch ignore` followed by `git push . HEAD:main` while a gate-OK record exists for that commit; either moves main to a commit no landing made, and a script there then counts as landed.
- **Script files the guard does not see:** these forms of a subagent's line still pass `backlog-role` unread:
  - a script the same line writes, then runs (`cat > x.sh <<EOF ... EOF` then `bash x.sh`): the file is not there yet, or holds its old text, when the guard reads it;
  - a script path the line computes (`bash "$S/x.sh"`): the path is not read, so neither is the file;
  - a script run after a `cd` the line computes (`cd "$W" && bash x.sh`): the guard cannot tell the folder, so `x.sh` does not resolve and is not read;
  - a part of an unreadable line read again on its own (`fallback.named_runs`) is read in the folder the line leaves it in (`fallback.cwd_at`); after a `cd` the line computes, that folder is lost and the part is read in the call's own folder, so a relative script path or `-C` there may be placed in the wrong one.
- **Backlog roles by name:** any script named `backlog.py` a subagent runs is judged as the kit's tool, wherever it lives.
- **Backlog roles and another branch's worktree:** the own pull compares `pulled_by` only with the branch checked out at the run's `-C` folder, so a builder that names another branch's linked worktree acts as that branch and passes on that branch's pull. The cd form reached as far. The guard knows no session's branch to compare it with (tests/guard/test_backlog_role.py `RealStore`).
- **Backlog roles and a computed script:** a script path the line computes is judged by `backlog-role` only when its text ends in a literal `/backlog.py` or `\backlog.py` (`rules.computed_script`); any other (`python $p close X-1`, `python "$K/tools/$T.py" close X-1`, `python -m $M`, `kit $t`) is not, as `rules.tool_run` gives no run for it. On a line the guard cannot read, a subagent's part naming the tool that does not read either is refused ("Fallback"); a clean line with such a word is not. The tool's own check then holds it, by the session mark (PM_KIT_ROLE), which a subagent inherits from its main session: under a coordinator's or the PM's session the tool lets a subagent's write through as that lead's (docs/backlog.md "Roles").
- **Backlog roles on Codex:** Codex's hooks send no subagent identity, so its subagents carry their session's mark and meet only the tool's own check (docs/guard-jail-roles.md "Backlog roles"). The kit-tool broker (`hosts/codex/adapter/runtime.py`) holds a root binding the same way, as its marked session; only a child binding, whose role the broker checked, meets `backlog-role`.
- **Gate allow on Codex:** Codex's hooks send no subagent identity (`kitlib.hookrun.main.UNIDENTIFIED`), so a Codex subagent carries its session's mark, and one under a coordinator's or the PM's session is judged as that session: `gate-allow` lets its `gate.py allow` run (`gaterole.session_mark`; tests/guard/test_gaterole.py `test_an_unidentified_call_is_judged_by_its_mark`). The kit-tool broker's child binding names its thread and is refused as a subagent.
- **Codex's own sandbox failing, and its escalated route (2026-10-31):** in the Codex sitting that wrote `.kit.json` (kit 0.4.0-main.5564), every sandboxed process failed before it started: `exec_command` and the node_repl kernel answered "MXC launcher: failed to create the process security environment: CreateProcessSecurityEnvironment failed (HRESULT = 0x8007000F)", Win32 ERROR_INVALID_DRIVE. - **Linux paths:** a symlink swapped between the guard's check and the write is not seen (a race no command-line guard closes). The per-folder casefold of ext4 and f2fs (`chattr +F`) is not read: such a folder is judged case-sensitive. An fstype the guard does not list, nfs, nfs4 and zfs among them (they fold or not by the server or dataset, which the guard does not read), or a mount table it cannot read, folds case only for what the guard refuses, never to widen what it allows (docs/guard-jail-roles.md "Write jail" "Paths"; `rules._in_temp` and `rules._under_temp`, which lift checks, compare as the allow side does). A mount made after the hook process read the table is not seen (the table is read once per process). A ledger glob (`rules.ledger_glob`) folds each part of its pattern by the mount its literal path names, so a wildcard part that matches into a mount of another kind below it (`/media/usb/**` reaching an ext4 mount) compares by the pattern's mount, not the matched path's. A `CDPATH`, `SHELLOPTS`, `BASHOPTS` or `cdable_vars` the shell inherits from its environment or a host's shell snapshot is not on the line, so the guard cannot see it and reads bash's cd as without it.
- **A failed cd is still tracked:** the folder a cd names is kept whether the cd succeeds or not, on Windows and Linux alike, so `cd missing; echo x > ../f` is judged as written from `missing`, though the shell writes from the folder before it.
- **A cd in eval or source:** a cd inside an `eval` text or a script run by `source` (or `.`) moves the outer shell, but the guard does not carry it to the commands after it.
- **Wildcard targets:** a write target with a wildcard (`d*/f`) is judged as written: links and junctions are not resolved through the wildcard part (on Windows as on Linux).
- **Backlog roles and a reason:** the map's `NEEDS_WHY` (a HIGH write must say why) is not built; the owner's ruling a write carries is the only reason the tool records.
- **Backlog roles are a speed bump, not a credential.** The guard's backlog roles (docs/guard-jail-roles.md "Backlog roles") and the tool's own role check read a role the session states, so they hold an honest agent to its role; a write boundary an agent cannot step around (a credential the writer must hold) stays with its own record.

| B17 | PowerShell: a .NET write with a relative, driveless or computed path | A driveless path, a call the guard does not read, and the owner's own session's relative or computed path, from a worktree, judged only where the PowerShell location puts it; an agent session's relative or computed path is refused (docs/guard-jail-roles.md "Shell writes"). .NET resolves a relative path against the process's directory ("The .NET process directory" above) | None from a worktree | Medium |
| B18 | git-shared-ref: a ref reached through a link in the git directory | An `update-ref` of an allowed ref whose file a junction or symbolic link sends to a shared ref (a junction from `refs/tmp` to `refs/heads`, then `update-ref refs/tmp/main <sha>`); `--no-deref` does not help. The option is a link check on the ref being written | The pre-push fast-forward check on the remote's main only | Low-medium: it takes a link made first |
| B19 | git-shared-ref: a repository whose refs are in a reftable | A reftable repository is judged by the ref's name alone (except for a coordinator's stray-ref delete), so a symbolic ref there (B6) is not seen. The option is to keep the refusal | B6's option, if taken | Low: git makes a reftable repository only when asked |

Open: counting a `python -c` as a read. It would cut the same code and every refusal of its class, but it would let a `python -c` write into a main checkout, so it needs the owner's go; the prover (`-I`, module allowlist, AST walk) stays as it is, and the advice for such a command is the one line `cd "<worktree>" && python -c ...` or the Read and Grep tools, never a `cd` for a worker already in a worktree.

The pm-data checks are not made redundant by the pre-push leak check, in four ways:

- It needs the record. The leak stage runs only when the repository's git common dir holds `kit-pm-data.json` (`prepush.leak_refusal`); a clone or copy has none in its own common dir (docs/guard-hooks.md "Pre-push").
- It needs the hook. `core.hooksPath` is per-repository config, so a clone may not run the kit's hook, and `--no-verify` skips it.
- It reads the push's own config. The hook runs with the push's environment: `HOME`, `XDG_CONFIG_HOME` or `USERPROFILE` pointing at another folder (or `GIT_CONFIG_GLOBAL` at another file, B10) moves the `.gitconfig` that `git remote get-url --push` reads. Inference, not tested: a `url.<public>.pushInsteadOf = <private>` there makes the public URL count as the record's own push URL, so the leak stage lets the data branch through.
- owner-only commits is no leak check: it checks commits that touch owner-only paths, by author, and does not look at the data branch.

That these checks defend only against a deliberate evader is inference; nothing shows an agent could not take the steps by mistake while working around another refusal.

A relative write after a `cd` to a location the guard cannot tell, by a session the write jail holds whose role may edit a main checkout (a coordinator or pm mark), is refused as `unplaced` in every shell (`rules._write_from`, `ps_drive_jail`), as a computed PowerShell target is. The same holds for a shell that Start-Process starts in a computed `-WorkingDirectory` (`commands_nested._sp_shell_text`).

### Kit tools may be piped

A kit tool's output may be piped or redirected like any program's (`backlog.py list | head`, `doc_index.py ... > <file in worktree>`, `machine_lock.py run --help | head`).

- **wrapped-gate** (off by default) fires only on the runs that hold the machine or wait on it for minutes, piped, chained into another command, or wrapped: `gate.py` when it runs steps (no mode option, `--full`, `--only <steps>`, `land` in any form, `wait-result`) and `machine_lock.py run <...> -- <command>`. `gate.py` runs no steps with `-h`/`--help`, `--plan` and `--measure` (`rules.GATE_NOTHING`, `gate_runs_nothing`); these, `machine_lock.py run --help` (`lock_run_help`) and every other verb of either tool may be piped (B9). The reason for the rule stays for the runs that hold the machine: to the classifier, a piped gate reads as something else.
- **Every other kit tool** has no pipe rule. A parsed `hub.py` read verb, or a lock CLI read verb, may be piped or chained. A hub owner verb or a lock owner write is refused in any parsed form, and any hub or lock call on a line the parser cannot read is refused.
- **Redirects** of a kit tool's output are judged by the write rules on the target, as for any program. A literal path in the worktree or temp passes.
- Rule order: wrapped-gate stays before heavy. Tests: `tests/guard/test_kit_tool_forms.py`.

## Lock MCP

The lock MCP server ships read-only (docs/lock-mcp.md "No write tools"); its owner-only write names are retired (`kitlib.lock.names.OWNER_ONLY`) and stay refused here, for a server started from an older release.

Open: no real PreToolUse payload has been captured for the lock MCP tool names (the Claude plugin's MCP prefix, `kitlib.lockmcp.tool_prefix()`). After the plugin install, read one and set `guard_mcp_prefix` and `guard_mcp_tools` if the names differ.

- **Which tools:** a tool named `<prefix><owner-only tool>` is caught, so is any `mcp__*__<owner-only tool>`, and so is any full name listed in the user config `guard_mcp_tools`.
- **Prefix:** the default is the asking host's: its `hosts.json` profile `mcp_tool_format` with the kit plugin (`kitlib.host.registry.PLUGIN_NAME`) and the lock server's name filled in (`rules.host_mcp_prefix`; the same text as `kitlib.lockmcp.tool_prefix()`), and "any other server name" is the tail after the format's server separator (`__`). The Claude one is INFERRED from Claude Code's plugin MCP naming; no real PreToolUse payload has been captured, as the server is not installed. The user config `guard_mcp_prefix` replaces it and `guard_mcp_tools` adds names, so an observed name goes in config, not code (tests/guard/test_session.py `LockMcpByMark`).
- **Who is asking:** `Ctx.session_role(action)` decides (see "Session mark"); it is replaceable through `role_resolver`.
  - `subagent`, or any mark (pm, coordinator): deny.
  - Unmarked, the owner's own session: allowed. The lock's own owner check still applies.

## Session mark

`kitlib/host/sessionmark.py`. The launcher that starts an agent session sets `PM_KIT_ROLE` to its kind (`tools/launch.py`, docs/launcher.md "The window": `pm`, `coordinator`, `deep-worker`, `consultant`, `plain`, `topic` (a plain session `launch.py topic` starts, docs/launcher.md "Topic"), or another agent's name); a subagent is told apart by the hook payload's `agent_id` (`Action.agent`). `kitlib/guard/context.py` `default_session_role` gives `subagent`, else the mark, else `owner`. The mark is the hook's own environment's, unless the host's adapter hands it over as `Action.role` (Claude's does not: the hook inherits the session's environment).

- **Unmarked is the owner on the default host:** a main session nothing marks is the owner's own on Claude (`rules.is_owner_session`), exempt from `owner-tool`, `lock-mcp`, the hub rules (`hub-mcp`, `hub-browser`, `hub-owner-verb`, `hub-secrets`), `owner-identity`, `owner-delegations` and `git-push-pmdata`, and on Claude also from `kill-by-name`, `git-stash-shared`, `git-plain-commit`, `interpreter-git`, `lock-state`, `kit-json` and `write-jail` (on Codex those hold every chat: "On Codex no chat is the owner" below). Until the kit launcher is live, sessions the old launcher starts are unmarked and count as the owner on Claude (docs/guard-hooks.md "Go-live", step 4).
- **Reserved values:** a mark of `owner` or `subagent` reads as `marked-<value>`, never as that standing.
- **The plugin prefix:** a mark is read without the kit plugin's agent prefix, before the reserved check ("Agent names"): `<plugin>:coordinator` is held as `coordinator`, `<plugin>:owner` reads as `marked-owner`. The launcher writes bare marks (docs/launcher.md "The window").
- **Agent sessions:** `kill-by-name`, `git-stash-shared`, `git-plain-commit`, `interpreter-git`, `lock-state`, `kit-json` and `write-jail` hold subagents and the marks in the user config `guard_agent_marks` (default `kitlib/guard/rules_base.py` `AGENT_MARKS`: `coordinator`, `deep-worker`, `consultant` and `pm`; compared without case); other marks (`plain`, `topic`, another agent's name) are not held to them. Setting `guard_agent_marks` replaces the default list rather than adding to it, so a value must also list every default mark it keeps holding (`ctx.user().get('guard_agent_marks') or AGENT_MARKS`). `owner-tool`, `lock-mcp`, the hub rules, `owner-identity` and `owner-delegations` hold every marked session.
- **On Codex no chat is the owner, and every chat is an agent session:** the unmarked main chat too, so the owner-only rules (`owner-tool`, the hub rules and the rest of the first bullet) and the agent-session rules above (`kit-json`, `write-jail` and the rest) both hold it. Owner actions are done from the owner's chat on the default host, or by hand (tests/guard/test_codex_never_owner.py). `rules.is_owner_session` and `rules.agent_session` read the same `hosts.json` capability: a host whose hooks carry no subagent identity (capabilities `subagent_identity_in_hooks` false, which is Codex), or a host profile that no `hosts.json` entry has (fail closed), makes every session an agent session. On Claude an unmarked main chat is still the owner's (tests/guard/test_host_agent_session.py).
- **The PM's mark:** only the session the kit launcher resumes carries `pm` (docs/launcher.md "The window"); a PM session opened by hand or in the desktop app is unmarked and counts as the owner's own on Claude (on Codex every chat is held, none is the owner's). The jailed PM keeps the folders it writes outside its checkout through `guard_mark_roots` (docs/guard-jail-roles.md "Write jail"), which the owner sets.
- **Where it is read:** only where the session cannot change it once started: the guard hook, started with the session's environment (INFERRED; not yet observed live). The lock CLI and the lock MCP server do not read it: the server ships read-only (docs/lock-mcp.md "No write tools"), and an agent sets the environment of every command it runs.
- **Limits:** a session the launcher did not start is unmarked and counts as the owner, on Claude only ("On Codex no chat is the owner"). The lock's holds and tree roles do not read the mark.
- **Tests:** tests/guard/test_session.py.

## Agent names

`kitlib/host/agentname.py`. Claude Code names an agent a plugin bundles `<plugin>:<name>` (INFERRED from its plugin naming, not observed); the kit's plugin is `kitlib.host.registry.PLUGIN_NAME`, and `agentname.PREFIX` is that name and a colon. Every place the guard compares an agent name accepts the bare name and that one prefixed form:

- **Agent types** (`agentname.bare`): Claude's adapter (`hosts/claude/adapter/events.py`) drops the prefix once, into `Action.agent_role`, which `kitlib/config/policy.py` `role_name` (so the `roles` table, and through it `main-checkout`, `git-main-history` and `rules.lander_check`) and `rules.lander_check` itself read. Exactly one leading `PREFIX`, in its exact case, is dropped. Any other form keeps its name, which no role names, and is held as `subagent`: another plugin's prefix, the prefix twice, another case, the prefix alone, `PREFIX` + `main`. An event without `agent_id` is `main` whatever its `agent_type`.
- **Session marks** (`agentname.bare_mark`): `kitlib/host/sessionmark.py` `mark`, and again `rules.agent_session` and `rules.session_mark` (a `role_resolver` that does not strip it). The prefix is dropped in any case and as often as it repeats, since a mark that names a known kind is the restrictive reading; a mark that would be left empty keeps its value, since an empty mark would be the owner's.
- **Tests:** tests/host/test_agentname.py, tests/config/test_policy.py, tests/guard/test_session.py, and tests/guard/test_prefix_parity.py, which runs the rule table, role policy and session tests again (its `SENTINEL_MODULES`) with each subagent's `agent_type` and each mark prefixed and expects the same decisions.
