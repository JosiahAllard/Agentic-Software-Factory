# Shell guard: owner tools and hub secrets

Part of docs/guard.md (the index); the sections below are moved there unchanged.

## Owner lock tools

Owner-only lock tools are run by the owner, not agents: `reserve_ui.pyw` and the lock CLI's owner writes. The lock's own owner check (`kitlib/lock/api.py` `who`, `default_owner_check`: no Claude ancestor) can be forged by a detached process, so the guard stops agents from starting them at all. That check stays as a second layer.

- **The rule:** `owner-tool` (`kitlib/guard/rules_owner.py` `owner_tool`, `owner_tool_run`) reads the file a command runs as `rules.tool_run` reads it: the program's base name (any case, any path, without `.exe`); the script of `python`, `pythonw`, `py` or `pyw` (their own options skipped), or its `-m` module as `<last dotted part>.py`; a `.ps1` given to a PowerShell shell; the file an opener runs (`Invoke-Item`/`ii`, `explorer`, Git Bash's or cmd's `start` with its `/b` and other options skipped, a `Start-Process -FilePath`, and a `Start-Process -ArgumentList` string, split at its spaces). Wrappers the parser unwraps (`nohup`, `cmd /c`, a nested `bash -c`) are read as the command they run.
- **The kit command:** a run of the kit command reads as the tool it names (`rules.kit_run`, `commands.kit_tool`), so every rule that keys on a kit tool's name judges `kit X` exactly as `python <kit>/tools/X.py`: the program `kit` (`kit.cmd`, `kit.exe`, `kit.bat`, `kit.com`, any case, any path), `python <kit>/tools/kit.py X` and `python -m tools.kit X` (or `-m runpy tools.kit X`, `rules.script_run`) all read as `X.py` with the words after `X`. The first token after the kit names the tool, lower-cased: the words are split at blanks and double quotes and empty tokens skipped, and the rest of the word that holds the name is split the same way into words of its own. Windows PowerShell 5.1 passes a word holding a double quote on unescaped and drops an empty word, so `kit 'hub" answer EX-1'`, `kit '""hub' answer EX-1` and `kit '' hub answer EX-1` all read as `hub.py answer EX-1`: every token the program may see is read as the tool or an argument (it fails closed). The fallback's names (`fallback.KIT_WORD`) take the same quotes and empty words before the tool's name, and each suffix `commands.base_name` takes off a program. A computed tool word (`kit $t ...`) gives no run, as a computed script does (docs/guard-fallback.md "Known limits"), and the bare kit command with it is refused as `cmd-reparse` (docs/guard-jail-roles.md "Batch files and cmd.exe"), while `python <kit>/tools/kit.py $t ...` gives no run and no refusal; a kit run naming no tool (`kit`, `kit --help`) is the kit command itself. `commands.tool_at` gives the same reading with the word's place, for `commands.wrapper`, `rules.lock_run_help`, `rules.gate_runs_nothing` and `rules.bare_wrapper`. Tests: tests/guard/test_kit_command_forms.py (every rule in each spelling), tests/guard/test_kit_tool_forms.py (parity with the script forms).
- **reserve_ui:** denied when that file is `reserve_ui` (with or without `.pyw`): `pythonw reserve_ui.pyw`, `start pythonw reserve_ui.pyw`, `& "<lock>/reserve_ui"`, `ii reserve_ui.pyw`, `python -m reserve_ui`. Reading it and git on it stay open: `cat`, `type`, `Get-Content`, `rg`, `grep`, `git add`, `diff`, `show`, `log`, `commit`, and so does any other `-m` module (`python -m py_compile reserve_ui.pyw`, `python -m pytest -k reserve_ui`), so work on the UI's own code is not blocked.
- **Lock CLI owner writes:** a run of `machine_lock.py`, read as above, whose words before `--` hold (`rules.lock_owner_write`):
  - the installed lock CLI: `reserve`, `release`, `stop --force`, `unbook --force`;
  - the kit CLI (`tools/machine_lock.py`): `hold whole|half|slots`, `division --set|--default`, `game on|off|set`, `top` (move a waiting run to the front), `stop --force`.
- **Still open:** `status`, `run`, `background`, `book`, `unbook` and `stop` without `--force`, `hold agent|list|end|edit`, bare `division` and `game`/`game show`. Ending one's own hold or run is an agent's right (`kitlib.lock.api.authorize`); the text cannot tell whose hold an id names, so the lock decides.
- **Who:** every session but the owner's own (unmarked; see docs/guard-fallback.md "Session mark"), with no ask. A process the owner's session starts still has an agent host above it, so the lock CLI's own check refuses it there.
- **Limits:** not read, as the guard reads what a line runs, not what it builds (the guard catches honest mistakes, not evasion): `python -c` code, python's standard input (a pipe, `<`, a heredoc or here-string), a program or script named by a variable, a glob (`pythonw reserve_u*.pyw`), a program the guard does not know as a launcher (a `.py` script that runs the UI), copy-then-run under another name, `[Diagnostics.Process]::Start(...)` and other .NET process calls (git that such code runs is `interpreter-git`'s, docs/guard-rules.md "Rules").
- **Unreadable lines:** `kitlib/guard/fallback.py` runs this rule first when it re-reads a text-pattern match (`PARSED_RULES`). An unreadable line whose text names the lock CLI (`machine_lock.py`, `tools.machine_lock`, `-m machine_lock`, `kit machine_lock`) is refused as `owner-tool` whatever its verb, in every session but the owner's own (docs/guard-fallback.md "Fallback", "The owner's tools by name"); reserve_ui has no name pattern, so an unreadable line reaches the rule for it only when another rule's text pattern (machine setup, wrapped gate, git, root search, heavy) matches.
- **Tests:** tests/guard/test_rules.py `OwnerLockTools`.

## Owner machine setup

Machine setup's `--apply` writes the machine config, and its `owner_email` decides which commits count as the owner's (owner-only paths, `owner-identity`; docs/machine-setup.md "Owner email"). An agent that ran it could store its own address as the owner's, so the `owner-tool` rule (`kitlib/guard/rules_owner.py` `owner_tool`, `owner_tool_run`) denies it to every session but the owner's own:

- a run, as `rules.tool_run` reads it ("Owner lock tools"), of `machine_setup.py`, `machine-setup.ps1`, `new-repo.ps1` or the Linux `installer/machine-setup.sh` (`SETUP_SCRIPTS`; the program, python's script, `python -m <...>machine_setup`, `powershell -File`, `sh` or `bash` running the script, directly or after a `sudo` or `env` prefix, `&`, a `Start-Process -ArgumentList` string), followed by `--apply` or a prefix argparse takes for it (`--ap`, `--app`, `--appl`), or for a `.ps1` a prefix of `-Apply` (`-a`, `-App`, `-Apply:$true`), any case; words after `--` are not read.

The dry run (no `--apply`), `--help`, reads and git on its files stay open. The `--repo` mode is held the same way: it writes `.kit.json` "owner".email. An agent session's file edit or shell write of the home machine config folders is the write jail's: they are never a write root (docs/guard-jail-roles.md "Write jail"). An unreadable line that names an entry point with a `-a...` word is matched by the fallback's own pattern and re-read through this rule; the owner's own session skips it.

**The machine config in a checkout** (rule `machine-config`, `kitlib/guard/rules_edit.py` `machine_config`, `machine_config_folder`). The machine config is moving into the PM repository, as `<pointer>/.pm-kit` (docs/machine-setup.md), and a branch of any repository could carry a `.pm-kit` folder of its own. Every session but the owner's own (subagents and every mark, `plain` included, as `owner-tool`; docs/guard-fallback.md "Session mark") is denied:

- a file tool edit or a literal shell write target (`rules.edit_target`) in the PM repository's folder, `<pointer>/.pm-kit` (`jail.pointer_config_dir`, compared as `jail.real` resolves both), whether or not git places it; and one in a folder named `.pm-kit` (case ignored) right at the top of a main checkout or a linked worktree (`Ctx.place`), whatever the pointer names. A `.pm-kit` deeper in a checkout, a folder that only holds one (a delete or move of the checkout) and one outside git are not this rule's; the home folders are the write jail's.
- a wildcard write target whose literal folder is, or lies in, such a folder (`delegfile.glob_config`: `rm <pointer>/.pm-kit/*.json`, `Remove-Item .pm-kit\*` at a checkout's top), or whose parts after its literal folder match on disk an existing path that is or lies in one (`delegfile.glob_config_below`: each part, folder parts and the last, matched as FindFirstFile matches, long or 8.3 short name, case folded; for bash a leading `*`, `?` or `[` skips dot-names and `[^` negates: `rm .pm-k*t/config.json`, `Remove-Item .pm-k?t\local.json`, `Remove-Item */config.json`, `rm -rf .pm-k*`; past `delegfile.WALK_LIMIT` folder entries read, refused, fail closed), judged after the delegation list's own wildcard check (tests/guard/test_delegfile.py `FolderWildcards`, `WalkLimitText`).
- git whose work tree is the PM repository (as "Owner delegation list" reads it): `rm`, `mv` and `checkout-index` of a pathspec that lands in `<pointer>/.pm-kit`, `restore` of one unless it only unstages (`--staged` without `--worktree`, as `git-restore` reads it), `checkout` of one after `--`, and `clean` of one without `-n` (`delegfile.git_config`, `delegfile.lands_in`: a glob by its literal folder; other magic and a computed word fail closed; an exclusion never lands). The delegation list's own git check runs first.

The reason names the folder and why (`rules.MACHINE_CONFIG_WHY`), and the `Instead:` lists it: `Get-ChildItem -Force "<folder>"`. The one exception is a wildcard whose walk passed `delegfile.WALK_LIMIT`: its reason (`delegfile.walk_limit_refusal`) says the word was too wide to check and to narrow it or name the files, with no `rules.MACHINE_CONFIG_WHY` and no ask-the-owner, and its `Instead:` is `Get-ChildItem -Force -Name "<folder>"`. Reads stay open. Precedence: a target the delegation list's rule can reach (the list itself, a wildcard that can match it) is refused as `owner-delegations`, and one in `<pointer>/.pm-kit/hub` as `hub-secrets` (its second token folder, "Hub secrets"); `machine-config` takes the rest of the folder. Pre-push refuses a push that sends a checkout's `.pm-kit/hub/` or `.pm-kit/local.json` (docs/guard-hooks.md "Pre-push", "Machine config secrets").

- **Limits:** not caught (the guard catches honest mistakes, not evasion): `python -c` code or python's standard input importing `kitlib.machinesetup`, an entry point or its words named by a variable, a script of the agent's own that writes the machine config file (`python my.py`), a copy of the tool under another name, `[Diagnostics.Process]::Start(...)`. The write jail and `machine-config` stop a file tool or a shell write target into a machine config folder, not a program's own writes. For `machine-config` also (docs/guard-fallback.md "Known limits"): python or node code on the line that names `.pm-kit`; a wildcard whose literal folder is above `.pm-kit`; a pipeline or `xargs` writer; git in another checkout than the pointer's; a git pathspec in the forms not listed above.
- **Tests:** tests/guard/test_rules.py `OwnerSetup`; tests/guard/test_machine_config.py (`PointerFolder`, `ByName`, `Wildcards`, `PointerGit`, `PrePushSecrets`); tests/guard/test_home_config.py `ConfigMove`.

## Owner delegation list

The owner's delegation list says which owner operations an agent may run for the owner (docs/delegations.md), so an agent that could change it could grant itself any of them. The `owner-delegations` rule (`kitlib/guard/delegfile.py`, wired in `kitlib/guard/rules.py` `owner_delegations` and `kitlib/guard/rules_edit.py` `delegations_edit`) denies a write, move or delete of it to every session but the owner's own: every subagent and every marked main session, `plain` included (docs/guard-fallback.md "Session mark"). Two copies are held: the home one the loader reads (`kitlib.delegations.delegations_file`, `~/.pm-kit/owner-delegations.json`), and the PM repository's (`<pointer>/.pm-kit/owner-delegations.json`, the PM-repo pointer's value as stored, `kitlib.config.pointer.read_raw`; a value the pointer check refuses is still held). With no pointer only the home copy is.

- a file tool edit of either copy, or a shell write target the shell rules place (`rules.edit_target`) that is either copy or a folder holding one (a delete or move of `~/.pm-kit` or the PM repository). Paths are read with the home folder's spellings and after a cd home, as `hub-secrets` reads them, and compared as the filesystem reaches them (case, links and junctions).
- a wildcard write target that can match either copy or a folder above it (`delegfile.glob_reaches`: `rm ~/.pm-kit/*.json`, `Remove-Item .pm-kit\*` in the PM repository, `rm -rf ~/*`). Each part after the literal folder is matched against the copy's path below that folder, case folded and with a leading dot matched like any other character (bash would skip it: fail closed); `**` or `..` after the wildcard matches any copy below the folder. The DOS wildcards `<`, `>` and `"` count as `*` (`rm -r .pm-ki\<`; the path is also read as the literal name, `delegfile.word_reaches`), and a part also matches the copy's 8.3 short name (`rm .pm-kit/OWNER-~?.JSO`, `rules.glob_part`), as FindFirstFile matches.
- the folder a program that writes there runs in (a stand-in target, `rules.here`: `tar -x`, `unzip`, `curl -O`, `ln`, `Copy-Item` with no `-Destination`), when it is a copy's folder or a folder above it (home, the PM repository): `git archive HEAD~3 | tar -x` in the PM repository, `cd ~ && tar -xf backup.tar`. A stand-in whose writes the guard does not read (`rules.unread_write`: python, node, ruby or perl code, a .NET call) counts only as the file: python run in the PM repository is not a write of the list.
- a writer that takes its paths from the pipeline (a cmdlet's `-Path` from `|`) or from `xargs`, judged by the commands before the `|` (`delegfile.upstream`): a path-like word of theirs (a separator, a wildcard, a leading `.`, `~` or `$`) that reaches a copy, read as git reads a pathspec when the command is git; a command that names `owner-delegations` or `.pm-kit` (fail closed); and, with no path-like literal word, the folder the first of them runs in when a copy is in it or below it (`git ls-files | xargs rm` and `Get-ChildItem | Remove-Item` in the PM repository).
- python or node code on the line (`rules.inline_code`: `-c`, `-e`, a heredoc or here-string) that names the list (`owner-delegations`, `delegations_file`) and writes, moves or deletes a file (`delegfile.WRITE_RE`); code that names the list and writes another file is refused too.
- git whose work tree is the PM repository (`-C`, a cd, or a folder below it): `rm`, `mv`, `restore` (unless it only unstages) and `checkout-index` of a pathspec that can reach the file (the file, a folder above it, a glob whose literal folder is above it, `:/` and `:(top)` from the top, other magic and a computed word fail closed, an exclusion never), `checkout-index -a`, `checkout` with no `--` or a reaching path after it, `switch`, `reset --hard`/`--merge`/`--keep`, `read-tree -u`, `clean` (not `-n`) of a reaching path or of no path, `stash` (not `list` or `show`), `sparse-checkout` (not `list` or `check-rules`) and `bisect` (not `log`, `visualize`, `view`, `terms` or `help`); and `worktree remove` or `move` of the PM repository's work tree from any place.

Reads stay open: a Read or Grep, `cat`, `Get-Content`, `git show`, python that only reads, a copy of the list to somewhere else. An unreadable line that names the list is refused even for a read (docs/guard-fallback.md "Fallback"); the owner's own session skips every check here.

- **Limits:** not caught (the guard catches honest mistakes, not evasion): `merge`, `pull`, `rebase`, `cherry-pick`, `revert`, `am` and `apply` in the PM repository are left to the owner-only commit check (docs/guard-hooks.md "Owner-only commits"); a script file python or node runs (`python my.py`) is not read; when the guard cannot tell which repository git acts on (`-C` with a computed path, `--git-dir` or `--work-tree`, `GIT_DIR` or the like, an alias it cannot expand, a computed subcommand) the git check is skipped; a path-like word before a `|` that reaches no copy lets the piped writer through, whatever the command makes of it; the inline check reads names, not data flow (a path built from parts that never spell the list passes).
- **The machine config folder:** `delegfile` also judges two forms for `machine-config` ("Owner machine setup"), each after this list's own check, so a target that can reach the list keeps `owner-delegations`: a wildcard write target that starts in a machine config folder, and git in the PM repository's work tree whose pathspec lands in `<pointer>/.pm-kit` (tests/guard/test_machine_config.py `Wildcards`, `PointerGit`).
- **Tests:** tests/guard/test_delegfile.py; tests/guard/test_cheap.py `KeptDenies` `test_the_owners_delegation_list_is_a_kept_deny`.

## Hub secrets

The Action Hub (`kitlib/hubsite`) keeps its tokens in a folder named `hub` beside the machine config file (`kitlib/hubclient/token.py`); the guard also holds `<pointer>/.pm-kit/hub`, the PM repository's machine config folder's, where machine setup copies the hub's files before the hub reads them from there (`rules.hub_secret_folders`; every rule below holds each token folder; tests/guard/test_machine_config.py `test_a_hub_token_in_the_pointer_folder_is_a_hub_secret`): `owner.token` answers as the owner, `agent.token` is every agent's, and `approval.key` signs the owner's approval decisions (`kitlib/ownerfiles/approvals.py` `sign`) and binds strong sessions (`kitlib/hubsite/auth.py` "The approval key"). Its store is the machine config's `hub.store`, unset: `<pm_data.path>/hub` (`kitlib/hubsite/settings.py`). Agents reach the hub only through `tools/hub.py`'s agent verbs and the hub MCP server, which read `agent.token` in their own process, and the hub server's git sync writes the store; an agent's own access to those files is owner power. Four rules hold every session but the owner's own (subagents and every mark, `plain` included, as `owner-tool` does; docs/guard-fallback.md "Session mark"). They live in `kitlib/guard/rules.py` (section "the Action Hub"), with pure helpers in `kitlib/guard/hub.py`, which copies the hub site's names rather than importing it (tests/guard/test_rules_hub.py `Plumbing` checks they match).

- **hub-secrets, edits:** a file tool edit of a path in the token folder or a store, judged by the resolved path (`jail.real`). Both stores count, an explicit `hub.store` and `<pm_data.path>/hub`, since the hub may move to the default one. The store and port are read from the machine config's `hub` object even when the strict read refuses the file for a fault elsewhere (`rules.hub_config`).
- **hub-secrets, shell:** a command (`rules.hub_secret_shell`) with:
  - a literal path (redirect targets included, `--opt=<path>` and PowerShell's `-Opt:<path>` read; `rules.hub_path_texts`) in the token folder, in the words of any program. A word that only names a token file or looks like the folder, with no path into it, passes (`echo owner.token`, `cat x/owner.token`, `cat foo.pm-kit/hub-x`); a word the shell computes is not read. A wildcard path is read as the literal folder before the separator ahead of its first wildcard (`rules.glob_folder`), so `cat ~/.pm-kit/hub/*` is refused and `cat ~/.pm-kit/h*` is not; a path holding a DOS wildcard (`<`, `>`, `"`) is read that way too, with those counted (`rules.hub_texts`: `cat ~/.pm-kit/hub/o\</../../x` is refused). The word `hub` and the store are not read (a shell write into the store is the write rules'; a file tool's edit there is still hub-secrets'). A path may start with the home folder spelled as `~`, `$HOME`, `${HOME}`, `$env:USERPROFILE`, `$env:HOME`, `%USERPROFILE%`, or the drive and path pair `$env:HOMEDRIVE$env:HOMEPATH` (`${env:...}` too) or `%HOMEDRIVE%%HOMEPATH%`, read as the guard's own home and only when nothing after it is a variable (`shell.HOME_VAR_RE`, `shell.home_text`). A relative path is read from where a `cd`, `Set-Location`, `sl`, `pushd` or `Push-Location` to such a home path moved the line, and a bash or PowerShell `cd` or `Set-Location` with no place, or PowerShell's `cd $null`, counts as a move home, as bash's and PowerShell 7's do (bash cd's own options and a `--` are passed over: `cd -- ~`, `cd -P`; a bash `builtin cd` or `command cd` is the cd itself, `shell.cd_words`). That is `shell.track`'s `cwd_home` (`shell.cd_target` with `home_vars`); every other rule still treats that line's directory as unknown, so a relative `hub` run from `~/.pm-kit` counts;
  - python or node code given on the line (`-c`, `-e`, a heredoc, a here-string, the command piped in) naming a token file or the folder literally (`hub.INLINE_RE`; `rules.inline_code`). `hub.py` and `hubsite` are not secrets, so `python "<kit>/tools/hub.py" questions --json | python -c "import json,sys; print(json.load(sys.stdin))"` passes. A parsed hub tool run of an agent verb piped into code given on the command line is that code's data, not code, so a token file's name in its words is not read (`rules.hub_run_verb`); piped into code read from standard input (`python -`) it is the code and still read, and any other program piped in is still read. A name the code builds or reaches through a library is not read.
- **hub-secrets, read tools** (`rules.hub_secret_read`, an Action of kind `read`): paths are resolved as the edit rule's are (`jail.real`), and only the token folder is held, so the store stays readable.
  - Read: a file in the token folder, or the folder itself.
  - Grep starting in the folder (its `path`, else `cwd`).
  - Grep from a parent of the folder: denied with no `glob`. With one, it is denied when any of its pieces (split on spaces and commas, braces written out at most `hub.BRACE_LIMIT` forms, case and backslashes dropped) can take in a name in the folder (the token files' names, `hub.SECRET_FILES`, and everything the folder holds, `rules.hub_secret_names`; past `rules.HUB_NAMES_LIMIT` names it counts as reaching) or name a folder on the way there (`hub.filter_reaches`); a `!` exclusion, and a brace it cannot write out, count as reaching. A Grep from anywhere else passes: it cannot reach the folder.
  - Glob is not hooked (a names search lists names and reads no token's text), so it passes anywhere, the token folder included.
- **hub-owner-verb:** a parsed hub tool run, at any depth of the line (`rules.hub_run_args`, `rules.hub_owner_run`): python with a script whose last part is `hub.py`, or with `-m tools.hub` (`-m hub`, a flag cluster ending in `m`, `-m runpy tools.hub`), its arguments read as `tools/hub.py`'s argparse parser reads them (`hub.owner_verb`). An owner verb in the Rules table (`hub.OWNER_VERBS`, `hub.OWNER_SUBS`, `todos add --owner`) is denied; a word the guard cannot read where the verb could be counts as one, and so does a PowerShell word holding a double quote. Only a run counts: text that names the hub tool without running it (a search pattern, a file a reader reads, a quoted argument of another program, a note written with `echo`) passes, and so does an agent verb whatever follows its pipe (`python "<kit>/tools/hub.py" todos --json | ConvertFrom-Json`). On a line the parser cannot read, the fallback refuses any text naming the hub tool, read verbs included (docs/guard-fallback.md "Fallback", "The owner's tools by name"). A script or module word the guard cannot read is no run, and a launcher that runs the tool some other way is not read. The agent verbs stay open: `questions` (list, `show`, `add`, `log`, `done`, `file`, `bind`, `edit`, `withdraw`), `todos` (list, `add`, `ack`, `edit`, `withdraw`), `stories` (list, `set`), `to-pm` (list, `reply`), `inbox` (list, `add`), `pages` (list, `publish`, `show`), `approvals` (list, `show`, `add`, `withdraw`), `pending`, `wait`, `status`, `validate`, `serve`, `setup`. `approvals apply` (the owner has the hub apply an approved change again, docs/hub-approvals.md "Applying") is held, and so is `approvals approve`/`deny` though `tools/hub.py` has no such verb. The owner's token is no protection here, since `kitlib/hubsite/client.py` reads `owner.token` itself (tests/guard/test_rules_hub.py `OwnerVerbs`, `ParsedRuns`).
- **hub-mcp:** an MCP tool whose last part (after the host's server separator, `__` on Claude) is in `hub.OWNER_MCP_TOOLS`, under any server name, or a hub tool (named `hub_*`, or served by a server named `hub`) whose name holds `decide` or `approve`. The list is `kitlib.hubvalidate.OWNER_ONLY`, imported (the hub MCP server re-exports it as `kitlib.hubmcp.OWNER_ONLY`; the guard never loads the server: `test_the_guard_does_not_load_the_server`).
- **hub-browser:** an MCP call to a server whose name holds `chrome`, `browser`, `playwright`, `puppeteer` or `computer-use` whose input (`Action.params`, every string up to 8 levels deep) holds `host:port` with a loopback host on a hub port (`hub.hub_origins`): 8790 and 8791 and the configured `hub.port` and `hub.tunnel_port`. Loopback is `localhost`, `*.localhost`, 127/8, `0.0.0.0`, `[::1]`, IPv4-mapped IPv6, and IPv4 in a browser's other spellings (`127.1`, `2130706433`, `0x7f.0.0.1`, percent-encoded). `Action.params` is the tool's input, which the Claude and Codex adapters pass (`hosts/*/adapter/events.py`); it takes no part in an Action's equality or hash (`kitlib/host/__init__.py`).

- **Limits:** not caught:
  - Read and Grep in an account whose PreToolUse matcher is older than the one in docs/guard-hooks.md "Go-live", step 1: Claude Code does not send them to the guard (the settings are the owner's to change);
  - Glob, which is not hooked (a names search reads no token's text): it can list the token folder's names, never their text;
  - a link or junction below a search's start that leads into the token folder: only the start and the folder are resolved, not what the search walks through;
  - Grep's other ways to pick files (`type`) are not read: a Grep from a parent with a `type` and no `glob` is denied (over-reach), not judged by its type;
  - a script the agent wrote and then runs, or any program that reads the files itself (as the write jail: docs/guard-fallback.md "Known limits");
  - python or node code on the line that never spells a name `hub.INLINE_RE` knows: a wildcard (`glob.glob(...)`), a name built from pieces (`'own' + 'er.token'`, `chr(...)`) or read from elsewhere (an environment variable, a file). `INLINE_RE` matches the code's text, not what it does;
  - a recursive read of a parent folder (`grep -r x ~/.pm-kit`, `Copy-Item -Recurse ~\.pm-kit`), a wildcard at or above the folder (`cat ~/.pm-kit/h*/owner.token`), and `Join-Path` pieces (`Join-Path $d 'owner.token'`);
  - a token file's name in a word with no literal path into the token folder (`cat $d/owner.token`; docs/guard-fallback.md "Weakened checks, by row" A2);
  - a shell command's read of the store, which is not held (its writes are the write rules'), and a relative path after a `cd` the text cannot place;
  - the home folder computed rather than spelled, which no reading of the text closes: `[Environment]::GetFolderPath('UserProfile')`, `Join-Path $HOME ...`, `$HOME + '\...'`, a variable set from it (`H=$HOME; cat $H/...`), a substitution or subshell whose output is the home folder (`$(echo ~)`, `"$(cd; pwd)"/...`); and a return home the guard does not follow: `cd -`, `popd` and `Pop-Location` (the directory after them is unknown);
  - hub-owner-verb, which reads only a parsed run: a launcher that runs the tool another way (`python -c "import tools.hub ..."`, a script the agent wrote, a copy of the tool under another name), and a name built at run time (string concatenation, an encoding, a variable's value: `python -m $m answer Q-1`). The rule catches mistakes and is not an adversary boundary;
  - a machine config the guard cannot read as JSON at all: an explicit `hub.store` and configured ports are then unknown, so only `<pm_data.path>/hub` (when the guard can tell `pm_data`) and the default ports are held;
  - text the parser never reads: the hub rules run on what the parser did read of an unclean line (tests/guard/test_rules_hub.py `test_unclean_lines_are_judged_on_what_was_read`), and the fallback refuses such a line that names the hub tool (docs/guard-fallback.md "Fallback", "The owner's tools by name"); a line that never spells the name, such as an encoded command (`powershell -EncodedCommand <base64>`, which is not decoded), is not held by it, so a subagent is only warned (`unreadable`) and a marked session in a worktree passes;
  - hub-browser: a click, key or form input on a hub tab already open (its input names no origin), raw screen pixels, a host that resolves to loopback (`nip.io`, the machine's own name, a LAN address), a port the config does not name (`serve --port 0`, a one-off `--port`), an origin with no port (port 80 implied), obfuscated script text, and the tunnel's public hostname.
- **Over-reach:** denied though nothing secret is read:
  - hub-browser: a browser MCP call to a loopback origin on 8790 or 8791 (or the configured hub ports) when something other than the hub serves there;
  - a word of any program, git's commit message included, that is itself a path into the token folder (`git commit -m "~/.pm-kit/hub"`), as paths are read in every word;
  - from `~/.pm-kit`, a bare `hub` as any word, search patterns included (`grep -n hub x`), because there it names the token folder;
  - hub-owner-verb: an agent verb whose value is a variable (`--title "$t"`) or, on PowerShell, a word holding a double quote, since either may split into `--owner`;
  - a Windows PowerShell 5.1 `cd` with no place or `cd $null`, which stays where it is;
  - read tools: a Grep with no `glob` from any parent of a token folder (home, or the drive root); the PM repository (the pointer) is the parent of `<pointer>/.pm-kit/hub`, so a held session's Grep over its root with no `glob` is denied.
